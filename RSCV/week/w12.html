上午段

设计 5 个消融配置

1先垫概念（消融是什么、为什么每次只改一个变量）

  • 消融实验(ablation)= 每次只去掉/替换你方法的一个部分，看性能变化，从而证明“这个部分有没有用、有多大用”。核心原则：每个消融只改一个变量（控制变量）——这样性能变化才能干净地归因到那一个改动。
  • 和通用 CV 一样、但对你更关键：消融是所有方法类论文的标配证据。审稿人会问“你这几个组件，哪个真有用？会不会去掉两个性能也一样？”——消融表就是回答。对你尤其重要：你的卖点之一是“单卡高效”，消融能证明“我没堆无用组件”，每个组件都名副其实。
  • 常见 5 个:A1 去掉你的核心组件 / A2 把某组件换成简单版 / A3 换 loss / A4 换 backbone / A5 换数据增强策略。命名要清晰(A1_wo_hrbranch、A2_simple_fuse)，日志完整。

在 docs/消融设计.md 列出 5 个消融配置，每个写清“改了哪一个变量、预期说明什么”；为每个建一个 config（基于 v1 的 config 只改一处）。建 config 的正确姿势：

3这一步合格的样子

5 个消融配置定义清晰，每个只改一个变量，命名规范，且能 diff 出“相对 v1 只差一处”。

4最常踩的坑

① 一个消融改了多处 → 无法归因（性能变了不知是哪个改动的功劳）;② 消融和你的 contribution 对不上（每个核心组件都该有一个对应消融，否则审稿人会问“这个 contribution 凭什么”）。

5卡住怎么自救（决策树）

不知设哪些? → 你方法的每个创新组件配一个“去掉它”的消融（对应一条 contribution），再加 backbone/loss/增强各一个凑够 5 个；config 不会继承? → 用框架的 _base_ 继承机制，只写要覆盖的字段。

6今天（这一步）你同时学会了什么

你学会设计控制变量的消融实验。做了（消融设计文档 + 5 个 config）、学了（消融定义、每次只改一个变量、消融对应 contribution）、会了（为方法的每个组件设计可归因的对应消融）。

技能卡｜消融设计原则：每个消融只改一个变量(用 config 继承 _base_ 只覆盖一个字段)。每个核心组件配一个“去掉它”的消融，对应一条 contribution；再加 backbone/loss/增强维度。命名规范(A1_wo_X),diff 可见“只差一处”。改多处=无法归因。

A1 结果分析（并判断显著性）

1先垫概念（怎么从消融判断组件价值 + 显著性）

A1 训完，看“去掉核心组件后性能下降多少”。下降越多 → 组件越有用；几乎不降 → 组件可有可无（考虑删）。关键：下降是否“显著”——要和 baseline 的 std 比，降幅 > std 才算真有贡献，否则可能只是噪声。

2手把手带做

评估 A1，和完整方法(v1)对比；算“去掉组件的性能损失”；和 std 比判断显著性；写一句结论（组件贡献多大、是否显著）。

4坑

去掉组件反而更好 → 那它可能有害，大胆考虑删（论文要“每个组件都有用”，留着有害组件反而扣分）；降幅在 std 内 → 补多 seed 确认，或归到“贡献有限”。

★★ W12-D79 的核心：+0.4 到底算不算提升

原文说“A1 结果分析（并判断显著性）”，但全书没有一处说怎么判断。这是 M3 最重要的一个技能，因为判断错了，你后面所有工作都建立在幻觉上。

完整判定工具（接在上面的 seed_tools.py 后面）
★ 实测四种情形（我跑过，结论会让你意外）

情形 1：mAP 涨了 0.4，但两组各自的标准差是 0.6

★ 这个结果和直觉相反。 只看“提升 0.4 < 标准差 0.6”会判定为不可信——但这是错的。

原因：两组的标准差主要来自 seed 本身造成的共同波动（同一个 seed 下 baseline 和你的方法会一起高、一起低）。同 seed 逐对相减，这部分共同波动被消掉了，剩下的 0.40±0.10 才是真正的效应。

这就是“配对比较”比“边际比较”更有力的原因。 学术界报 mean±std 是惯例，但判断有效性时一定要看配对差。很多人在这里误杀了自己真正有效的方法。

情形 2：涨了 0.73，但配对差波动大

情形 3：有一个 seed 输了

情形 4：只跑了 1 个 seed

★ 情形 4 是新手最常犯的错。 跑一次涨了 0.9 就以为成功了——单次实验的波动本身就可能超过 0.9。

★ 三条判定纪律
  1. 少于 3 个 seed 不下任何结论。 这是底线。
  2. 看配对差，不要只看 mean±std。 边际比较会误杀真正有效的方法。
  3. 每个 seed 都赢，比“平均涨得多”更有说服力。 前者说明稳定，后者可能是某一次运气。

  • ★ “理性止损”和“轻易放弃”是两回事（go/no-go 的真正智慧）：设置 go/no-go 决策点，目的是给你一个“理性检视、避免在死方向上无限耗下去”的机制——但它绝不是“一遇到不顺就换方向”的借口。这两者的区别，恰恰是科研成熟度的体现:① 理性止损是有明确证据（toy 全无信号 + 消融证明核心组件无效 + 找不到任何改进方向）时，果断承认方向不行、及时转向——这是对有限时间负责;② 轻易放弃则是“v1 提升没到惊艳的程度就慌、就想换个新方向试试”——这是个人研究者最常见、也最致命的陷阱。为什么轻易 pivot 致命：研究的提升往往是渐进的（v1 小涨、v2 加强、v3 接近完整），如果你在 v1 阶段（提升还小、但消融已显示组件有效、且有清晰改进方向）就放弃，等于把几个月积累的框架、数据、领域理解全部清零，从头再来——而新方向同样会在早期“提升不惊艳”，你又想换……陷入“永远在开头、永远不深入”的恶性循环，最终一事无成。所以这个决策点的默认倾向应该是 go：只要消融证明你的组件确实在起作用、且你能看到下一步怎么改进，就坚持下去、在 M4 把它做强。真正该 no-go 的情况（全无信号 + 方法被证伪）是少数，且前提是你前面 toy 验证过（所以本来就不太会发生）。学会区分“该坚持的渐进”和“该止损的死路”，是你能不能做出成果的关键判断力之一。

🟡 PIVOT 不是失败（这一段原文完全没有）

M3 结束时拿到黄灯是很常见的，而且黄灯往往是好事——它说明你发现了一个真实存在但比想象中难的问题。

黄灯时的三种转法：

转法 具体做什么 产出还能是什么
从“提性能”转“做分析” 系统研究“为什么这个问题难”、“现有方法在什么条件下失效” 分析类论文，GRSL 这类 Letters 很欢迎
从“通用改进”转“特定条件” 你的方法可能只在某个子集上有效——那就把范围收窄，把那个子集讲透 更聚焦的贡献
从“新方法”转“新基准” 把你搭的实验框架和公平对比做成一个基准 基准类工作，引用往往不低

★ 关键认知：研究的产出不只是“性能提升”。 一个诚实的负结果 + 扎实的分析，价值高于一个可疑的 +0.3。

八、进阶：按“类别”读消融（找出方法对哪些遥感目标有效）

总 mAP 只是一个数。把消融的提升拆到每个类别，才知道你的方法到底帮了谁、伤了谁——这是定性负面案例的来源，也是 M4 改进的精确制导。

怎么用这张按类表:① 验证动机——高分辨率分支应在小目标类(small-vehicle/ship)提升最大，结果吻合就坐实了“机制如预期”;② 找负面案例——掉点的大目标类(plane)就是 D81 定性负面案例的来源;③ 指导 M4——若发现“小目标涨、大目标略降”,M4 可考虑“只在小目标尺度启用该分支”，把副作用消掉。一句话：总 mAP 告诉你“行不行”，按类 mAP 告诉你“为什么、接下来改哪里”。

技能卡｜按类别读结果：别只看总 mAP，把提升拆到每个类(per_class_delta)。① 提升最大的类应吻合你的方法动机（验证机制）;② 掉点的类=定性负面案例来源 + M4 精确改进目标。遥感类别尺度悬殊，按类分析尤其能暴露“方法只帮了某尺度”这类规律。
