第 2 遍：它比前人多做了什么

★ 对答案 · 这篇的核心创新（一句话）：

把“生成旋转候选框”这件事，从一个昂贵的独立步骤，变成 RPN 里几乎免费的一步。

具体怎么做的（这是你笔记第 2 段该写的，用自己的话）：

传统 RPN 输出的是水平框（4 个数：x, y, w, h）。Oriented RPN 的做法是：在水平框的基础上，再多回归两个偏移量，用这两个数把水平框“掰”成一个平行四边形，再规整成旋转框。

这个设计的巧妙之处：

别人的做法 代价 Oriented R-CNN 的做法
用旋转 anchor（每个位置放多个不同角度的锚框） anchor 数量翻好几倍，计算量爆炸 仍用水平 anchor，只多回归 2 个数
先出水平 RoI，再用一个模块学着转成旋转 RoI（RoI Transformer 的做法） 多一个模块，多一段计算 一步到位

所以它的卖点是“几乎零成本” —— 这就是摘要里 “nearly cost-free” 的含义。

★ 自检三问（答不出就回去重读）

  1. 它说前人的瓶颈是什么？（答：生成旋转候选框太慢）
  2. 它的 oriented RPN 和普通 RPN 差在哪？（答：多回归两个偏移量，把水平框掰成旋转框）
  3. 为什么不用旋转 anchor？（答：anchor 数量爆炸，计算量吃不消）

第 3 遍：消融表怎么读

★ 读消融表的通用方法（这一招你后面每篇方法论文都用）：

带着这个方法去读它的消融表，你会发现：它的性能提升主要来自 oriented RPN 本身，而不是一堆小 trick 堆出来的。这是一篇“干净”的论文——干净的论文才值得当 baseline，因为你改动之后能清楚归因。

2.3 五大块，在展开版里各自长什么样

① backbone（主干：提特征）

frozen_stages=1 和 norm_eval=True 这两行原文完全没提，但它们解释了一个你会问的问题：为什么 batch size 只有 2 也能训得动？因为 BN 层根本没在更新统计量（norm_eval=True），所以不受小 batch 影响。这是检测框架的标准做法。

② neck（脖子：多尺度融合）

FPN 是什么、为什么需要它，见 《检测与训练概念详解》§2.3——全书正文出现 49 次，没有一句解释。

2.4 ★ 纠正原文的自相矛盾：lr 到底是 0.0025 还是 0.005

原文中午段的示意代码写 lr=0.0025，但同一段的合格样例里说“lr=0.005”。两个数不一样，新手会懵。

正确答案：MMRotate 的 DOTA config 里是 lr=0.005。

它对应的是“单卡 × 每卡 2 张 = 总 batch 2”。 这一点和 MMDetection 的 COCO config 不同（那边默认 8 卡 × 2 张 = 16）。

你的设置 总 batch lr 应该是
单卡，samples_per_gpu=2 2 0.005（默认值，不用改）
单卡，samples_per_gpu=1 1 0.0025
单卡，samples_per_gpu=4 4 0.01

所以原文那个 0.0025，其实是 batch=1 时的值。 完整说明见 W2 实操 §4.3。

第 2 步：★ 今晚怎么 dry-run（原文没解决这个时序问题）

原文让你 D8 晚上 dry-run，但切图是 D9 中午的事——今晚你手上根本没有训练数据。 这是原计划的一个时序漏洞。

两个选择：

选择 A（推荐）：今晚只做“配置层面的 dry-run”

期望输出里应该看到你改的路径、samples_per_gpu=2、lr=0.005、num_classes=15、max_epochs=12。

这一步能抓出 80% 的 config 错误，而且不需要数据。

选择 B：把切图提前到今晚

如果你 D5 下的 val 已经解压好，今晚就可以切（W2 实操 §3），切完立刻能真 dry-run。这样 D9 中午就腾出来了，可以提前启动正式训练——整周节奏会宽松很多，推荐这么干。

第 3 步：真 dry-run（有数据之后）

⑥ 你同时学会了什么

做了：一份自己的 config + 一份 config 注释文档。 学了：config 的继承机制、五大块各是什么、frozen_stages 和 norm_eval 为什么让小 batch 也能训、lr 与 batch 的配比。 会了：用 print_config.py 展开继承链、把论文的一句话指到 config 的一行。
