第一部分 · W13–W14 方法迭代

★ D88 的真问题：三个改进单独都有效，合起来却不涨

原文 D88 说“启动 v2 完整训练（所有有效改进合并）+ 验证不冲突”。“验证不冲突”这四个字背后是方法迭代最常遇到的情况，原文没展开。

为什么会不叠加

原因 表现 怎么判断
改进解决的是同一个问题 A 单独 +1.0，B 单独 +0.9，合起来只有 +1.1 看 per-class AP：A 和 B 提升的是不是同一批类别
改进互相干扰 合起来反而低于单个 常见于两个都改标签分配 / 都改 NMS
超参不再适配 合起来训练不稳定 loss 曲线抖动明显变大
只是噪声 单独的 +0.9 本来就在噪声范围内 回到 M3 的配对判定 重新审

★ 冲突时的处理顺序（原文没有）

★ 一个重要的心态：“三个改进只有两个能合并”不是失败，是发现。

而且这个发现本身就是论文素材——在消融表里如实展示“A+B 有效但 A+B+C 不叠加”，比藏起来更有说服力。审稿人见得多了，一个所有组件都完美叠加的消融表反而可疑。

★ D94 第三个数据集怎么选（原文没给标准）

加第三个数据集的目的是证明泛化。所以它必须和前两个“足够不同”，否则加了等于没加。

三条选择标准

标准 说明 反例
① 分布要有实质差异 传感器 / 分辨率 / 场景 / 类别体系至少差一样 DOTA-v1.0 和 DOTA-v1.5 —— 几乎是同一批数据，不算
② 有公认的 baseline 结果可比 别人在上面报过数字，你才能证明自己没跑歪 冷门数据集没人用过，你的数字没有参照
③ 规模适中 单卡跑得完，别选比前两个大 5 倍的

具体怎么搭配（按你的方向）

你的方向 数据集 1 数据集 2 ★ 数据集 3 该选什么
光学旋转检测 DOTA DIOR-R HRSC2016（单类船舶、场景差异大）或 UCAS-AOD
SAR 检测 SSDD HRSID SAR-Ship-Dataset（不同传感器/分辨率）
变化检测 LEVIR-CD WHU-CD SYSU-CD 或 S2Looking（视角/分辨率不同）
语义分割 LoveDA Potsdam Vaihingen 或 iSAID

★ 一句会被审稿人问到的话：“你的方法在三个数据集上都有效” 只有在这三个数据集确实不同时才成立。如果三个都是同一来源的光学航拍图，那你证明的只是“在这一类数据上有效” —— 这一点要在论文的 Limitation 里诚实写出来。

第二部分 · ★ W15 的基础设施（全书零字）

W15 让你写 Intro、Related Work、Method 一共几千字。但全书没有任何一处说这些字写在哪里、用什么排版、参考文献怎么管。

2.1 用什么排版：LaTeX，不是 Word

Word LaTeX
公式 难写、难改 ✅ 天生为此设计
参考文献 手工维护，改一处全乱 ✅ BibTeX 自动编号和格式化
图表交叉引用 手工，容易错 ✅ \ref{} 自动
期刊模板 少数有 ✅ IEEE / Elsevier 都提供官方 LaTeX 模板
投稿接受度 部分接受 ✅ 几乎所有 CV / 遥感期刊会议都要 LaTeX

★ 你的方向（TGRS / GRSL / CVPR）基本都要 LaTeX。现在就学，不要拖到投稿前。

2.2 用 Overleaf（在线，不用装环境）

地址：overleaf.com

为什么用它而不是本地装 TeX Live： - 装 TeX Live 要好几 GB 和不少时间，你现在的时间应该花在研究上 - Overleaf 自带所有期刊模板 - 云端保存，随时能给导师/朋友看

免费版够用（单人写作、有限的协作者数量）。编译超时的话，把图片压缩一下通常就够。

2.3 模板去哪拿

目标期刊/会议 去哪拿模板
IEEE TGRS / GRSL / JSTARS Overleaf 首页搜 “IEEE Transactions”，或去 IEEE Author Center 下载官方 LaTeX 模板包
CVPR / ICCV / ECCV 各会议官网每年发布 Author Kit，里面有 .tex 模板；Overleaf 也有
ISPRS J / RSE（Elsevier） Overleaf 搜 “Elsevier”，或用 elsarticle 文档类

★ 一定要用目标期刊的官方模板，不要用通用模板凑合——页数、字号、图表格式都是按模板算的，换模板会导致超页。

2.4 参考文献：Zotero + BibTeX（全书提 Zotero 1 次，0 个说明）

为什么现在就要建：你已经读了 30+ 篇论文，再攒下去手工管理就来不及了。

★ 一个能省你大量时间的习惯：从今天起，每读一篇论文就顺手用 Zotero 存一次题录（10 秒）。等到写论文时，refs.bib 已经现成了。

BibTeX 的常见坑： - 条目 key 不要用中文或空格，用 xie2021oriented 这种格式 - 从 Google Scholar 复制的 BibTeX 常常缺字段（缺页码、缺卷号），以 IEEE Xplore / 出版社官网的为准 - 会议论文别写成 @article，要用 @inproceedings

2.5 架构图用什么画（D103 让你画，没说工具）

工具 适合 说明
draw.io / diagrams.net ★ 推荐，免费、能导出 PDF/SVG 矢量图 学习成本最低
PowerPoint / Keynote 很多人真的用这个 能导出 PDF；注意导出时选“矢量”
Inkscape 需要精细控制时 免费，专业矢量编辑
TikZ（LaTeX 内置） 追求极致一致性 ★ 学习成本高，第一篇论文不建议

★ 画架构图的三条规范： 1. 必须导出矢量格式（PDF / SVG），不要 PNG 截图——放大会糊，审稿人会注意到 2. 图里的字号，缩到论文栏宽后要和正文字号相当（约 8pt），不能更小 3. 数据流方向统一（一般左→右或上→下），箭头不要交叉打结

★ 八条图表规范（每条都有具体理由）

# 规范 为什么
1 导出矢量（PDF/SVG），不用 PNG 放大不糊；出版社偏好；文件还更小
2 图内字号 ≥ 7pt（缩放后） 缩到单栏 3.5 英寸后，小于这个印出来看不清
3 pdf.fonttype = 42 字体嵌入为 TrueType，否则部分出版社系统会报错退回
4 用色盲友好配色，不用纯红绿对比 约 8% 男性有红绿色觉障碍，IEEE 明确建议
5 不靠颜色单独区分，配合线型/标记 打印成黑白也要能读
6 多 seed 画均值线 + std 阴影带，不画单条 单条曲线不诚实；阴影带一眼看出稳定性
7 y 轴不从 0 开始时，图注必须声明 不声明是误导性作图，审稿人会挑
8 表格用三线表（顶线/表头线/底线，无竖线） 学术出版惯例；LaTeX 用 booktabs 宏包

第四部分 · W16 收官

D107 · reproduce.sh 该长什么样（原文说“写一键复现脚本”）

★ 三条设计原则： 1. 每一步打印在做什么、预计多久 —— 别人跑的时候心里有数 2. 数据不打包进仓库，给下载地址 + 目录结构要求 + 校验命令 3. set -e —— 任何一步失败立刻停，不要带着错误往下跑

D107 · 上传 checkpoint 到 HuggingFace（原文没给方法）

★ 为什么用 HuggingFace 而不是 GitHub：GitHub 单文件限制 100 MB，你的 .pth 通常超过。HF 专门为大模型文件设计，而且是学术界现在的通行做法。

D110 · 开源前的敏感信息检查（原文说“检查敏感信息”，没说查什么）

★ 第 ③ 条特别注意：如果大文件已经被 commit 过，从 .gitignore 里加进去是没用的——它还在 git 历史里。要用 git filter-repo 或 BFG 清理历史，或者干脆重开一个干净的仓库。第一篇论文的代码，重开仓库通常更省事。

D108 · 《阶段一总结报告》（≥4000 字）骨架

D111 · 关于“休息日”

原文安排了 D111 整天休息，并写“允许自己放松一天”。

★ 这一天不要跳过。 理由不是鸡汤，是实际的：

  • 你已经连续做了 16 周，这是 104 周里的第一个完整休息日
  • 阶段二（M5–M8）强度更大（主实验 + 论文定稿 + 投稿）
  • 在长跑里，主动休息是配速的一部分，不是奖励

唯一的建议：真的不碰研究。看半天的休息 + 半天的“轻松看点别的”，效果不如整天彻底断开。

技能卡｜方法迭代的四条纪律 ① 一次只加一个改进，和上一版只差一处 → ② 每个改进独立验证 3 seed，别急着合并 → ③ 合并不叠加时，逐对组合定位冲突，而不是全推翻 → ④ 贡献小于 0.2 的组件要砍掉 —— 更简洁的方法更容易被接受。

最容易犯的错：一次加三个改进，涨了 2 个点，但你说不清是哪个在起作用。审稿人一问就露馅，而且你自己后面也没法继续优化。

下一个阶段（M5–M8，W17–W32）：主实验 → 论文定稿 → 投稿 → 竞赛/开源。W17 开始要同时管理几十组实验——你 W11 接的 wandb、W12 建的实验命名规范，那时候才真正兑现价值。
