D71

周一 · 设计仓库结构 + git/GitHub 私仓初始化

0/3

预期管理：今天不写算法，而是搭“地基”——仓库目录结构 + 版本管理。这看起来不如写模型激动人心，但一个清晰的框架会让你后面 6 个月的实验都受益（找得到、改得动、回溯得了）。今天的产物是“骨架”，后面几天往里填肉。

上午段

设计代码仓库目录结构

1先垫概念（为什么要自己搭框架，而不是把代码堆一个文件）

  • 做研究要有一套可复用的实验框架，而不是把所有代码堆在一个 main.py 里。标准目录:configs/(配置)datasets/(数据加载)models/(模型)utils/(工具：日志/指标)scripts/(训练/评估脚本)experiments/(实验记录)docs/(文档)。
  • 和“直接改别人代码”对比：改别人的代码快，但你不理解底层、出 bug 难定位、想加自己的模块处处掣肘；自己搭框架（哪怕只是在 MMRotate 上封一层）能让你对每一行代码负责——这是工程能力的分水岭，也是你后面快速迭代方法的前提。
  • 为什么现在需要：你 W12 要做 5 组消融、M5 要做几十组实验。没有 configs/ + experiments/ 的组织，几十组实验会乱成一团（"这个结果是哪个配置跑的?"）。框架是为后面的规模化实验铺路。

2手把手带做

画出目录树（标注每个文件夹用途），在工作区 mkdir 建好这套结构；在 docs/结构说明.md 写清每个目录放什么；在 models/ 里预留 baseline.py 和 your_method.py 两个空文件，在 configs/ 放一个示例 config。

3这一步合格的样子

一棵清晰的目录树 + 每个目录的用途说明；空壳文件和示例 config 就位，结构一眼能看懂。

4最常踩的坑

  • 所有代码堆 main.py → 后面无法复用/扩展，改一处牵动全身。
  • 目录过度设计（建一堆用不到的空壳、嵌套五层）→ 够用即可，六块起步，按需再加。

5卡住怎么自救（决策树）

不知怎么分? → 就按“配置/数据/模型/工具/脚本/实验”六块起步；纠结某个文件放哪? → 按“它属于哪一层职责”放（数据相关进 datasets，通用工具进 utils），实在拿不准先放着，后面重构。

6今天（这一步）你同时学会了什么

你学会设计可复用的实验框架结构——这是规模化实验的前提。做了（目录树 + 结构说明）、学了（标准实验仓库的组织）、会了（为一个研究项目规划工程结构）。

技能卡｜可复用实验框架结构:configs/(配置)datasets/(数据+transforms)models/(baseline + your_method)utils/(logger + metric)scripts/(train + eval)experiments/(每实验一目录)tests/(单测)docs/。原则：够用即可、按职责分层、为规模化实验（几十组）预留组织方式。

中午段

初始化 git + GitHub 私仓 + 写 .gitignore

1先垫概念（git / 私仓 / .gitignore 各是什么）

  • git 是代码的“存档 + 时光机”（随时回到任意历史版本）；GitHub 私仓是云端存档（私有，别人看不到，防丢）；.gitignore 写明“哪些不纳入版本管理”。
  • 为什么数据/权重/日志绝不进仓库：这些是大文件（几个 G），提交进去会撑爆仓库、push 极慢、还可能泄露数据。代码进仓库，数据/权重/日志留本地——这是铁律。
  • 为什么现在就要做：从框架第一天起就版本管理，后面任何一次“改坏了”都能回滚；等代码多了再补 git，丢失的历史就找不回了。

2手把手带做

git init → 建 GitHub 私仓并关联 → 写 .gitignore(排除 data/ checkpoints/ *.log work_dirs/ __pycache__/ *.pth)→ 第一次 git add . && git commit -m "feat: init repo structure" && git push。

3这一步合格的样子

私仓建好、首次提交成功;.gitignore 正确排除了大文件目录(用 git status 确认 data/checkpoints 不在待提交列表里)。

4最常踩的坑

  • 把数据/权重 commit 进去 → 仓库爆炸，且可能泄露；提交前务必 git status 检查。
  • 仓库设成 public（未发表代码）→ 设 private（你的方法还没发表，公开有被抢跑风险）。

5卡住怎么自救（决策树）

push 报权限错 → 配 SSH key 或用 personal access token；不小心 add 了大文件 → git rm --cached <file> 移除并补进 .gitignore，再 commit。

6今天（这一步）你同时学会了什么

你学会用 git/GitHub 管理研究代码 + 正确配 .gitignore。做了（私仓 + 首次提交 + .gitignore）、学了（git 版本管理、忽略大文件）、会了（把研究代码纳入可追溯的版本管理）。

技能卡｜git + .gitignore 规范：从项目第一天 git init + GitHub 私仓。.gitignore 必排除 data/ checkpoints/ *.pth *.log work_dirs/ __pycache__/。提交前 git status 确认无大文件。commit message 带 feat:/fix:/exp: 前缀，便于回溯。

晚上段

写 README 模板 + 提交规范

1先垫概念

README 是仓库门面（项目简介/安装/用法/结果/引用）——未来开源或给老师看，它是第一印象。养成“每次有意义的改动就 commit（带清晰 message）”的习惯，日后能精确回溯“哪次改动引入了什么”。

2手把手带做

写 README 模板（项目简介、安装步骤、如何训练/评估、结果表占位、引用格式）；定一个简单的 commit message 规范(feat: 新功能 / fix: 修 bug / exp: 跑实验 / docs: 文档)，写进 docs/。

3合格样例

README 模板成形（有骨架，可边做边填）;commit 规范写进 docs/。

4坑

① README 一直空着 → 至少有骨架;② commit message 全写 “update” → 以后无法回溯，用有信息的 message(如 feat: add high-res branch to your_method)。

5自救

不知 README 写什么 → 仿照你 M2 复现过的优秀开源仓库的 README 结构照搬骨架。

6今天（这一步）你同时学会了什么

你建立了仓库门面(README)+ 提交规范。做了（README 模板 + commit 规范）、学了（README 的作用、有信息的提交）、会了（让仓库可读、改动可追溯）。

周二 · 写数据层 + 单元测试

0/3

预期管理：今天写“数据层”——把磁盘上的图和标注读成模型能吃的张量，还要做单元测试验证它对不对。数据层是最容易藏 bug 的地方（标注解析、增强同步），所以今天的单元测试不是走形式，而是帮你在训练几小时前就抓住错误。

上午段

写 datasets 模块（支持 ≥2 个数据集的 loader）

1先垫概念（数据层是什么、为什么要统一接口）

  • 数据层负责“把磁盘上的图/标注读成模型能吃的张量 (image, target)”。你 Proposal 里选了 ≥2 个数据集，最好统一接口（同一套调用方式加载不同数据集），后面换数据集零成本。
  • 和通用 CV 对比：通用 CV 数据集格式统一(COCO json)，一个 loader 走天下；遥感数据集格式五花八门（DOTA 的 8 点旋转框 txt、HRSC 的 xml、不同分辨率），所以你更需要“为每个数据集写解析、但暴露统一接口”。

2手把手带做

在 datasets/ 写一个统一的 Dataset 类（或为每个数据集写一个、共享接口），实现“读图 + 读标注 → 返回 (image_tensor, target)”；支持你选的 ≥2 个数据集。复用你 M1 写的旋转框解析逻辑。骨架：

3合格样例

能用同一套接口加载 ≥2 个数据集，返回正确的 (图, 标注) 张量(HRSCDataset 只需再写一个 _load_anno 解析 xml)。

4最常踩的坑

① 每个数据集写一套完全不同的调用方式 → 难维护，尽量统一接口;② 标注解析错（回想 M1 的 8 点旋转框解析，顺序/弧度制易错）。

5卡住怎么自救（决策树）

标注格式不熟 → 回用 M1 写的解析逻辑，打印前几条标注核对；接口设计纠结 → 先让一个数据集能跑，再抽象共性（别一上来就追求完美抽象）。

6今天（这一步）你同时学会了什么

你学会写统一的多数据集数据层。做了（datasets 模块）、学了（统一数据接口）、会了（把多个数据集封装成可复用 loader）。

中午段

写 transforms（数据增强）

1先垫概念（数据增强是什么、遥感的特殊之处）

数据增强(transforms)= 训练时对图做随机变换（裁剪/翻转/旋转/颜色抖动），让模型见更多变化、更鲁棒。遥感的特殊性：遥感目标无固定朝向（俯视拍摄），所以随机 0/90/180/270 旋转特别有用（通用 CV 一般不大角度旋转，因为地面物体有“上下”）；还有多尺度（遥感目标尺度悬殊）。

2手把手带做

在 datasets/transforms.py 写增强：随机裁剪/翻转/旋转/颜色抖动 + 遥感特有（多尺度、90° 倍数旋转）；可视化几张增强后的图 + 标注框，确认效果合理。关键是几何增强要图和框同步：

可视化自检：转完把框画回图上，目标应仍被框住(框没“飞走”=同步对了)。

3合格样例

增强可配置、可视化后效果合理（目标没被增强没了、框跟着转对了）。

4坑

增强太猛（把目标裁出画面 / 旋转后标注没同步）→ 几何增强必须同步变换标注（框/mask 跟着转）。

5自救

增强后框对不上 → 检查标注是否跟图做了同样的几何变换；先关掉几何增强跑通，再逐个加回来定位是哪个增强出的问题。

6今天（这一步）你同时学会了什么

你学会写（含遥感特有的）数据增强并验证。做了(transforms)、学了（增强的作用、几何增强要同步标注、遥感无固定朝向）、会了（配置并可视化检查数据增强）。

晚上段

写数据层单元测试

1先垫概念（单元测试是什么、为什么数据层必须测）

单元测试= 用一小段代码验证你写的函数是否正确。例：输入一张 512×512 图，经 DataLoader 输出应是 (batch, 3, 512, 512) 张量；形状不对 = 有 bug。为什么数据层尤其要测：数据 bug（标注错位、增强没同步）在训练几小时后才以“指标异常低”的形式暴露，极难倒查；单元测试能在训练前几秒就抓住它。

2手把手带做

写 tests/test_dataset.py：验证 ① DataLoader 输出张量形状正确 ② 标注数量/范围合理（框坐标在图内、角度在合法范围）③ 增强可视化无误；用 pytest 运行确保通过。

3合格样例

单元测试通过（形状/标注/增强都对）。

4坑

① 不写测试直接训 → bug 在训练几小时后才暴露，更难查;② 测试只测“能跑”不测“对不对”（只看不报错，不断言形状/数值）。

5自救

测试失败 → 正是它的价值（早抓 bug）；按报错定位是读图/解析/增强哪一步出的问题。

6今天（这一步）你同时学会了什么

你学会写单元测试守护数据层。做了（数据层单元测试）、学了（单元测试的意义）、会了（用测试在早期抓住数据层 bug）。

技能卡｜单元测试守护：用一小段代码 assert 关键函数的输出（形状/数值/标注范围）。数据层和模型层都要测——bug 在训练前几秒被抓，胜过训练几小时后倒查。测“对不对”（断言），不只测“能跑”（不报错）。

今日交付:✅ 数据层完成 ✅ 增强 ✅ 单元测试通过。

your_method 能实例化、forward 出正确形状（和 baseline 同接口）。

6今天（这一步）你同时学会了什么

你第一次把自己的 idea 实现成可跑的模型。做了（方法 v1 代码）、学了（"先能跑再优化"、最小改动实现）、会了（在 baseline 上实现自己的创新模块）。

技能卡｜先能跑再优化：实现新方法 v1 时，第一目标是“能跑通 + 输出正确形状”，不是“完美/复杂”。先用最简实现打通链路（哪怕一个额外卷积），确认框架通，再换成真正的设计逐步迭代。保持和 baseline 同接口，方便公平对比。

晚上段

模型层单元测试

1先垫概念

模型层也要测——model.forward(dummy_input) 能否正常输出正确形状（baseline 和 your_method 都测，且两者输出接口要一致，这是后面能用同一套 eval 公平对比的前提）。

2手把手带做

写 tests/test_model.py：对 baseline 和 your_method 各喂 dummy 输入，断言输出形状正确且两者接口一致；pytest 运行通过。

3合格样例

两个模型的单元测试都通过，接口一致。

4坑

三、读懂 wandb / TensorBoard 的多实验横向对比

搭好日志后，学会“读”比“记”更重要。多次实验该怎么横向看：

  • 同图叠多条曲线：在 wandb 里把 baseline 的 3 个 seed 和 v1 的 3 个 seed 拉到同一张 loss/mAP 图，看 v1 的曲线带是否整体在 baseline 之上（而不是只比单条）——带状重叠说明提升在噪声内。
  • Parallel coordinates（平行坐标）:wandb 的这个视图能一眼看出“哪个超参和高 mAP 相关”（为 W12 调参埋伏笔）。
  • 按 commit 过滤:meta.json 记了 commit，出现异常结果时按 commit 分组，定位是哪次代码改动引入的。
  • TensorBoard 本地版:tensorboard --logdir experiments/ 一次性加载所有实验目录，左侧勾选要对比的 run。 判读口诀：看曲线带不看线（多 seed 的包络），提升要“带不重叠”才稳。

六、对比分析范例（D77 中午交付物的范本，200–400 字）

给你一个“好的对比分析长什么样”的样板——不是只报数，而是有数字、有规律、有下一步。
