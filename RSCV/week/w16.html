周一 · 完整跑最终 pipeline 做 sanity check + 记录可复现

0/3

预期管理：今天从头完整跑一遍最终 pipeline（数据→训练→评估→可视化），确认整条链路无断点、结果和记录一致，并把“怎么复现”记下来。提醒：可先用小规模快速版验证链路通，再全量；可复现的关键是记全“命令+环境+seed”三样，缺一样半年后就跑不起来。

上午段

完整跑一遍最终 pipeline（数据→训练→评估→可视化）

1先垫概念（端到端 sanity check 是什么、为什么是底线）

  • 端到端 sanity check= 从头完整跑一遍（数据加载 → 训练 → 评估 → 可视化），确认整条链路无断点、结果和你记录的一致。这是“成果可信”的底线。
  • 为什么收官时必须做：这几个月你是分阶段做的（数据层 W11、训练评估 W11-12、方法迭代 W13-14），各部分单独跑过，但很久没有从头到尾完整跑一遍了——中间改了很多东西，可能某处接口对不上、某个路径失效了。端到端跑一遍，确保“整个项目作为一个整体能跑通”，而不是“各零件分别能跑”。
  • 和软件交付前的集成测试一个道理：模块测试通过 ≠ 系统能跑；必须做一次完整的集成验证。对你尤其重要：论文要声称“我们的方法达到 X”，这个 X 必须是从干净流程跑出来、可复现的，不能是某次手动东拼西凑的结果。

2手把手带做

用最终方法配置，完整跑一遍 pipeline（可用小规模快速版先验证链路通），核对各阶段输出正常。

3这一步合格的样子

pipeline 端到端跑通（数据→训练→评估→可视化每一环都有正常输出），小规模验证通过后全量结果和你记录的主结果一致。

4最常踩的坑

① 直接全量跑、错在最后一环才发现、白等几小时 → 先小规模（少量数据/1 epoch）验证链路;② 全量结果和记录对不上 → 检查是不是配置/seed/数据版本变了。

5卡住怎么自救（决策树）

某阶段断? → 定位是数据/训练/评估/可视化哪一环（看在哪一步报错），单独修那一环；结果对不上记录? → 核对配置、seed、数据划分是否和当时一致；链路太慢不好调? → 先用极小子集把“能从头跑到尾”验证通，再谈数值。

6今天（这一步）你同时学会了什么

你学会端到端验证整条实验链路。做了（pipeline 完整跑）、学了（端到端 sanity check、集成验证、先小后全）、会了（从头到尾验证一个项目能跑通）。

技能卡｜端到端 sanity check：收官/交付前从头完整跑一遍（数据→训练→评估→可视化），确认整条链路无断点、结果与记录一致。先小规模（少量数据/1 epoch）验证链路通，再全量——避免错在最后一环白等。模块各自能跑 ≠ 系统能跑，集成验证是成果可信的底线。

中午段

修复发现的任何问题

1先垫概念

端到端跑一遍往往会暴露一些“平时没注意”的问题（某路径硬编码、某依赖缺失、某小 bug）。把它们修掉、再验证一遍，让 pipeline 真正稳定。这是收尾的价值：平时赶进度留下的小毛病，趁现在一次清理干净，别带进产出期（M5 起更忙，没空回头修这些）。“技术债”现在还不还：每个临时硬编码、每个没处理的边界情况，都是欠下的技术债；阶段一末是还债的最佳时机——你对代码还熟悉、产出期还没压上来。带着一堆技术债进产出期，会在最忙的时候被这些小问题反复绊倒。修复也要有取舍：阻断流程的（pipeline 跑不通）必须现在修；不影响跑通但不优雅的（代码风格、可优化处）记入 backlog，别在收尾时陷入完美主义的无底洞。

2手把手带做

修复 sanity check 暴露的问题（路径/依赖/小 bug）；修完再跑一遍验证。

3合格样例

问题修复、pipeline 稳定（再跑一遍无报错）。

4坑

① 修了一个没回归测试、引入新问题 → 修完整体再跑一遍;② 把“小毛病”留着说以后再说 → 现在不修，产出期更没空。

5自救

问题太多一时修不完 → 按“阻断链路的优先修、不影响跑通的记 backlog”；不确定改动有没有副作用 → 改完跑小规模验证。

6今天（这一步）你同时学会了什么

你清理了链路上的遗留问题。做了（修复）、学了（收尾排错、修完回归验证）、会了（让 pipeline 稳定可跑）。

晚上段

确保可复现：记录完整运行命令 + 环境版本

1先垫概念（可复现三要素）

可复现= 别人（或半年后的你）按你记录的命令 + 环境能重现结果。要记三样：完整运行命令、依赖版本(pip freeze/conda env export)、随机 seed（外加数据准备步骤）。为什么这三样缺一不可：命令缺了→不知道怎么跑；环境缺了→半年后依赖一更新，代码可能就跑不了（版本不兼容是复现的头号杀手）;seed 缺了→每次结果有随机波动，对不上你报的数字。可复现是科研诚信的底线，也是审稿人/同行评估你工作的前提（"你的结果能重现吗"）。

2手把手带做

在 docs/复现.md 记录完整命令 + 环境 + 数据准备 + seed。

3合格样例

一份“照着就能复现”的记录（命令+环境+seed+数据准备）+ requirements.txt/environment.yml。

4最常踩的坑

① 不记环境版本 → 半年后依赖更新就跑不了;② 不记 seed → 结果对不上;③ 记了命令但漏了数据准备步骤 → 别人卡在第一步。

5卡住怎么自救

依赖太多记不全 → 用 pip freeze/conda env export 自动导出，别手写；不确定记得全不全 → 想象“一个陌生人只有这份文档，他能跑出我的结果吗”，缺什么补什么。

6今天（这一步）你同时学会了什么

你学会把成果做成可复现的记录。做了（复现记录+requirements）、学了（可复现三要素、环境锁定、复现是诚信底线）、会了（锁定环境与命令）。

技能卡｜可复现三要素：可复现 = 记全“完整命令 + 依赖版本(pip freeze/conda export)+ 随机 seed”（外加数据准备）。环境缺失是复现头号杀手（半年后依赖更新就跑不了）,seed 缺失导致数字对不上。检验标准：陌生人只凭这份记录能跑出你的结果吗？

上午段

整理代码仓库（安装文档 + demo notebook）

1先垫概念

一个“可用”的仓库要有：清晰 README、安装文档（怎么配环境）、demo notebook（让人几分钟跑个示例看到效果）。这决定别人（和未来的你）能否快速上手。demo notebook 是仓库的“试用装”：很多人看你仓库会先跑 demo，几分钟内看到效果（加载权重→对一张图推理→可视化出框），就愿意继续深入；如果上手要折腾半天环境数据，大多数人就走了。好的开源 = 低上手门槛,demo 越简单越好。“未来的你”也是受益者：半年后你想基于这个仓库做新工作，如果当初没整理，你自己都要花半天重新理清“这堆脚本哪个是干嘛的”；整理好的仓库让未来的你几分钟就能重新上手。整理仓库不是额外负担，而是对自己和他人时间的尊重——它把“只有我能跑、只有现在能跑”的代码，变成“任何人、任何时候都能跑”的资产。

4坑

中午段

写 reproduce.sh（一键复现脚本）

1先垫概念

reproduce.sh 把“准备数据→训练→评估”串成一键脚本，别人/你一条命令就能复现主结果——这是高质量开源的标志。为什么一键脚本这么重要：把多步流程固化成一个脚本，既消除“我是不是漏了某步”的不确定，也让复现门槛降到最低(bash reproduce.sh 就行)。关键是别硬编码本机路径：用变量/相对路径，否则脚本到别人机器（路径不同）就跑不了。

2手把手带做

写 scripts/reproduce.sh(下载/准备数据 → 训练 → 评估 → 打印主结果)，用变量、注释清楚。

3合格样例

reproduce.sh 能一键跑出主结果（或主流程），无硬编码路径。

4坑

① 脚本里硬编码本机绝对路径 → 用相对路径/变量;② 数据需手动下载却没说明 → 在脚本里给下载命令或在注释里说明来源;③ 没 set -e，中间出错继续跑 → 加上，出错即停。

5自救

数据集不能自动下（需授权）→ 脚本里打印“请先从 X 下载到 $DATA_DIR”并退出；脚本在别人机器报错 → 多半是路径/数据问题，检查是否都参数化了。

6今天（这一步）你同时学会了什么

你学会写一键复现脚本。做了(reproduce.sh)、学了（一键复现、参数化路径、set -e）、会了（把复现流程脚本化）。

技能卡｜一键复现 reproduce.sh：把“准备数据→训练→评估”固化成一条命令(bash reproduce.sh)。路径用变量/相对路径（不硬编码本机路径），加 set -e(出错即停)，数据需手动下就在脚本里给说明。一键脚本既消除“漏步骤”的不确定，也把复现门槛降到最低——高质量开源的标志。

晚上段

1先垫概念
