D260

周一 · 收到朋友 review → 逐条处理 + 改稿

0/3

预期管理：今天的任务是处理上周日发给朋友的那份 review，并据此改稿。提醒：朋友 review 是“投稿前的自家质量门”——和正式审稿不同，朋友是站在你这边的、目的是帮你在审稿人之前把问题修掉，所以心态可以放松（不用像读正式审稿那样先平复情绪）。但处理的纪律要一样严：逐条读、标三类（必改 / 可改 / 可不改）、按优先级动手。一个好用的认知：朋友读不懂的地方，审稿人大概率也读不懂——朋友 review 暴露的每个“卡壳点”，都是你投稿前白赚的一次修补机会。

上午段

逐条读朋友 review、标三类、列改稿清单

1先垫概念（投稿前的朋友 review 是干什么用的，和正式审稿有什么不同）

  • 朋友 review = 投稿前的“预审”：投稿前找懂科研的朋友通读，提“哪里读不懂、逻辑跳、图表不清”。价值在于用一次低成本的外部视角，提前发现你自己看不到的问题——你写久了会“脑补”（自己知道的默认读者也知道），朋友不会，他卡住处就是你表达不清处。
  • 和正式审稿的三个不同：① 立场——朋友帮你、审稿人挑你（所以不用先“管理情绪”，但要珍惜每条意见）；② 深度——朋友给“可读性”反馈，正式审稿到“创新性/严谨性”；③ 时机——朋友 review 在投稿前（从容改），正式审稿在投稿后（有时限）。这是你投稿前最舒服的一次修改机会，要用足——朋友能发现的问题现在全修掉，正式审稿时就能把审稿人注意力留给学术讨论而非“这句话什么意思”。

2手把手带做

把朋友的 review 逐条列出来（一条一行）；给每条标三类——【必改】（朋友读不懂/明显错误/图表缺失，这类一定改）、【可改】（朋友建议但非必须，如换个表述更顺，权衡后改）、【可不改】（朋友的个人偏好或误解，你有充分理由保留，但要想清楚理由）；按“必改优先”排出改稿清单（每条写明：在论文哪个位置、怎么改）。

3这一步合格的样子

一张“review 处理表”——每条意见对应一个分类（必改/可改/可不改）+ 一句改稿方案 + 论文中的位置。判断标准：看着这张表就能直接动手改，不用再回去重读 review。

4最常踩的坑

  • 朋友说什么都改 / 什么都不改 → 都不对。标三类、有判断地改：必改的认真改，可不改的想清楚保留理由（“我保留是因为……”）。
  • 只在脑子里记着改、不落表 → 改着改着漏掉几条。逐条落表、改一条勾一条，才不遗漏。

5卡住怎么自救（决策树）

拿不准某条是“必改”还是“可不改”？→ 问自己“如果审稿人也这么说，我改不改？”——会改就是必改；朋友的意见你不认同？→ 不是无条件接受，但先想“他为什么会这么理解”（往往暴露你表述有歧义，即使不按他说的改、也该把那句话改得不产生歧义）。

6今天（这一步）你同时学会了什么

你学会用投稿前的外部 review 提升论文质量（标三类、有判断地处理）。做了（review 处理表 + 改稿清单）、学了（朋友 review 的价值与边界、必改/可改/可不改三分法）、会了（把外部反馈转化为可执行的改稿计划）。

技能卡｜投稿前朋友 review 怎么用：投稿前找懂科研的朋友通读，提“读不懂/逻辑跳/图表不清”。逐条标三类：【必改】（读不懂/错误/缺图）/【可改】（建议非必须）/【可不改】（偏好或误解，但想清保留理由）。核心认知：朋友读不懂处=审稿人大概率也读不懂，是投稿前白赚的修补机会。和正式审稿不同（朋友帮你、给可读性反馈、在投稿前），心态放松但纪律照严。

中午段

按“必改优先”动手改稿

1先垫概念（改稿为什么要按优先级，不是从头改到尾）

  • 改稿不是“从第一页顺着改到最后一页”，而是按影响优先级改：先改【必改】（影响读者能否读懂的硬问题），再处理【可改】（锦上添花），【可不改】的只需在心里记着理由。这样即使时间不够，也保证最关键的问题先被解决。
  • 和“逐字顺改”对比：顺着改容易把时间花在无关紧要的措辞上，结果真正重要的“读者卡壳点”反而没时间改透。按优先级改 = 把有限的精力投在回报最高的地方——这和你做实验时“先验证最关键假设”是同一个道理。

2手把手带做

打开 review 处理表，从【必改】开始逐条改：每改一条，定位到论文对应位置、按方案修改、改完在表上勾掉；改“读不懂”类问题时，重点是把那段话拆得更清楚（加一句过渡、补一个定义、拆一个长句）；改图表问题时，确保图注/坐标轴/图例完整。改完所有【必改】，再看时间决定处理多少【可改】。

3这一步合格的样子

所有【必改】已改完并在表上勾掉；改后的段落重读一遍确实更清楚了（最好的验证：想象朋友再读一遍，他还会卡在这里吗？）。

4最常踩的坑

  • 改 A 处引入 B 处的不一致（如改了方法名称，但别处没同步）→ 改完做一次“波及检查”：这个改动还影响哪里？
  • 把“读不懂”理解成“加更多术语显得专业” → 恰恰相反，读不懂往往是话太绕，要改简单（拆长句、去黑话、补一句大白话解释）。

5卡住怎么自救（决策树）

某段怎么改都觉得绕？→ 试着“用一句话先说结论，再展开”（先给读者锚点）；不确定改完是否更清楚？→ 放一会儿再读，或念出声（拗口=没改顺）。

6今天（这一步）你同时学会了什么

你学会按优先级高效改稿。做了（按必改优先逐条改 + 波及检查）、学了（改稿的优先级思维、“读不懂=改简单不是加术语”）、会了（把改稿清单落实成更清楚的论文）。

技能卡｜改稿三类优先级：按影响排序，不顺着从头改到尾。必改（读不懂/硬错误/缺图表）先改透；可改（措辞）有余力再改；可不改（偏好/误解）记理由即可。改“读不懂”的正解是改简单（拆长句、补大白话、加过渡），不是堆术语。每改一处做“波及检查”（还影响哪里），避免新的不一致。

晚上段

继续改稿 + 通读一遍确认改顺了

1先垫概念

改完【必改】后，再通读一遍全文很重要——单点修改容易顾此失彼（改了这段忘了那段的衔接），通读能发现“局部改对了但整体读起来卡”的问题。这一遍读的是连贯性（段落之间过渡顺不顺、改动有没有破坏原有逻辑流）。

2手把手带做

处理剩余的【可改】项（挑回报高的改）；然后从头通读一遍改后的论文，重点看：改动处和上下文衔接顺不顺、有没有改出新的不一致（术语/数字/编号）、整体读下来是否比 v0.6 更清楚；把通读中新发现的小问题随手记下、顺手改掉。

3合格样例

一份处理完朋友 review 的改稿——【必改】全改、【可改】择优改、全文通读一遍连贯无新坑。这版可以叫 v0.7（比 v0.6 更清楚，但还没到定稿 v1.0）。

4坑

① 改完不通读 → 容易留下“局部对、整体卡”的衔接问题；② 通读时又开始大改结构 → 现在是打磨不是重写，发现结构性大问题先记下、别这周推翻重来（除非是硬伤）。

5自救

通读发现某处逻辑确实断了 → 加一两句过渡句承接（“基于上述……，我们进一步……”）；发现某个改动其实让原文更差了 → 回退到原版（git 留着 v0.6，可对比）。

6今天（这一步）你同时学会了什么

你学会改稿后通读把关连贯性。做了（处理可改项 + 全文通读 + 顺手修）、学了（单点修改易顾此失彼、通读看连贯性、打磨期不轻易推翻重来）、会了（把“改过的稿”收敛成“读起来顺的稿”）。

D261

周二 · 补充实验（如 review 指出需要）+ 更新表格文字

0/3

预期管理：今天判断“要不要补实验、补什么”，并把补出来的结果更新进表格和文字。提醒：补实验是“按需”的，不是“必须”——如果朋友 review（或你自己 self-check）指出了可预见的审稿质疑（最典型：“和最近的方法比过吗？”），那就补；如果没有明显缺口，不要为补而补（你 M8–M9 已经做了完整的实验矩阵，方法已是最终版，不需要再大改）。今天的活儿大概率是“小补”——加 1–2 个最新方法的对比、或补一个朋友提到的设置——复用你 M8–M9 搭好的实验框架，半天到一天能搞定。

上午段

判断要不要补实验 + 补什么

1先垫概念（投稿前“补实验”补的是什么，为什么大多是小补）

  • 投稿前补实验，补的是“可预见的审稿质疑”对应的证据缺口——最常见：① 和最新方法对比（审稿人最爱问“为什么没和今年的 XXX 比？”）；② 一个被 review 点到的设置/数据集；③ 一个让结论更稳的额外验证（多加一个 seed/数据集）。它不是推翻方法重做（M8–M9 已定最终版）。
  • 和主实验阶段对比：M8–M9 是“从无到有跑出方法+baseline+完整消融”（大工程）；投稿前补实验是“在已完整实验上打补丁”（小工程）——框架和 baseline 现成，补一个对比往往只是改个 config 跑一次，这是你前面搭扎实框架的回报。
  • 为什么“不为补而补”：补实验有成本、而你下周要投稿。判断口诀：这实验缺了，审稿人会不会用它拒稿？ 会就补；不会（只是“有更好”）→ 记进未来工作/supplementary，别卡住投稿。

2手把手带做

列出“候选补实验清单”（来自朋友 review + 你自己 self-check 的疑虑）；逐条判断【必补】（不补会被审稿人当硬伤，如缺最新方法对比）/ 【可补】（补了更好但非必须，时间够再补）/ 【不补】（可放 supplementary 或未来工作）；对【必补】项，写清楚要跑什么（哪个方法、哪个数据集、什么设置）。如果判断下来“无必补项”（M8–M9 已足够完整），那就跳过补实验，直接进入 D262 定稿——这完全合理。

3这一步合格的样子

一张“补实验判断表”（候选项 + 必补/可补/不补 + 理由）；【必补】项有明确的执行方案（或明确判断“本周无必补项”）。

4最常踩的坑

  • 看到 review 提“要不要试试 X”就无条件去补 → 先判断“不补会不会被当拒稿理由”，是建议性的就别让它拖住投稿。
  • 借补实验之名又开始大改方法 → 投稿前方法已封版，补实验是打补丁不是重做；真有大改想法，记进第三课题/未来工作。

5卡住怎么自救（决策树）

不确定某个对比要不要补？→ 看目标期刊近一年同方向论文“标配比哪些方法”，那些就是审稿人的预期；补实验会不会来不及？→ 只补【必补】、用现成框架最快路径跑（小数据集先验证、能说明问题即可）。

6今天（这一步）你同时学会了什么

你学会判断投稿前该不该补实验（按“会不会被当拒稿理由”决策）。做了（补实验判断表 + 必补项方案）、学了（补的是可预见审稿质疑、不为补而补、用现成框架小补）、会了（在“补充严谨”和“按时投稿”之间做出合理取舍）。

技能卡｜投稿前补实验的判断：补的是“可预见审稿质疑”对应的证据缺口（最典型：和最新方法对比、被 review 点到的设置、让结论更稳的额外验证），不是重做方法。三分法：【必补】（不补会被当拒稿理由）/【可补】（更好但非必须）/【不补】（放 supplementary 或未来工作）。口诀：这实验缺了，审稿人会不会拒稿？ 复用现成框架，小补半天搞定。

中午段

补跑实验（复用现成框架，最快路径）

1先垫概念（为什么补实验能这么快）

  • 补一个“和最新方法 X 对比”的实验，本质就是：拿 X 的开源代码（或你的框架里实现 X）、用你统一的数据集和评测脚本跑一遍、拿到它的指标填进表。因为你的数据加载、评测、日志全是现成的（M3-W11 搭的框架 + M5 起规模化跑的经验），新增一个对比往往只是“加一个 config / 跑一个 baseline”。
  • 和第一次跑实验对比：第一次（M2 复现 baseline）你要从环境配起、踩遍坑；现在你框架熟、坑趟过，补一个对比是“熟练工的活儿”——这就是把基本功打扎实后的复利：越往后，每个新实验的边际成本越低。

2手把手带做

对【必补】项，用最快路径跑——优先用现成开源实现（核对它的设置和你的公平对比口径一致：同数据集、同评测、同 train/test 划分）；先在小数据集/小设置上跑通确认无误，再跑完整设置；跑的同时记录（超参 + git commit hash + 结果），保持和你 M5 起的实验日志规范一致。如果【必补】是“加一个 seed/数据集”，直接复用你的训练脚本换参数即可。

3这一步合格的样子

补的实验跑出了可用的结果（指标合理、和你方法可公平对比）；结果已记录在实验日志里（可追溯）。

4最常踩的坑

四、本周报错 / 坑 速查表（现象 → 根因 → 解法）

# 现象 根因 解法
1 朋友说什么都改，改完论文反而乱了 没标三类、无判断地全改 标【必改/可改/可不改】，必改优先、可不改记理由保留
2 改了 A 处，B 处出现不一致（方法名/数字对不上） 单点修改没做波及检查 每改一处问“还影响哪里”，改完全文搜该项核对
3 看到 review 提“要不要试 X”就去补实验，拖住投稿 没判断是必补还是建议 口诀：“不补会被当拒稿理由吗”——不会就别卡投稿
4 补的对比方法指标和你的不可比 设置不一致（数据划分/输入尺寸不同） 对齐公平对比口径：同 config 只换 method
5 Abstract 写“提升 X”，但补实验后最强 baseline 变了没同步 全文数字没一致性检查 全文搜该数字逐处核对（Abstract=Intro=表格）
6 self-check 凭感觉读一遍，漏了某图没被正文引用 没用清单逐项打勾 用固定 self-check 清单逐项核（或跑 self-check 脚本）
7 参考文献格式乱（期刊名时全称时缩写、作者漏） Scholar 导出的 BibTeX 没核对 逐条核对 .bib，用期刊官方 .bst 自动套格式
8 LaTeX 编译报 undefined reference / citation 正文引了文末没有，或 label 拼错 跑 self-check 脚本查孤儿引用，补齐或改对 label
9 套目标刊模板后宽表/宽图溢出页边 双栏模板下未用跨栏环境 用 table*/figure* 跨栏，或缩排
10 论文超页，紧急删了核心内容 没按压缩优先级 优先：精简表述>挪 supplementary>删次要图表>（最后）核心
11 Cover Letter 贡献和论文 v1.0 对不上 论文改了 Cover Letter 没同步 据 v1.0 同步贡献和数字；漏原创声明要补
12 投稿当天发现缺 graphical abstract / 传了旧版 文件没提前按清单备齐/版本混 提前列清单逐项备齐、命名带版本号、只留定稿版
13 一激动把第二篇核心代码/实现细节开源了 没守“未发表核心延后开源” 框架开放、核心延后；README 诚实标“接收后开源”
15 投稿系统当天登不进/流程不熟卡住 没提前测登录/回顾流程 投稿前一天登一次确认、回顾第一篇 ScholarOne 流程笔记
