# D148 周一 · 自己做 mock review(5 维打分)

> 今天你既是作者也是审稿人。狠一点给自己挑刺,挑得越全,后面被真审稿人挑的就越少。
>
> **预期管理**:M6 续,本周用审稿人视角自审、找朋友 mock review、按问题分级修改,并启动竞赛。今天自己当审稿人(5维打分+≥500字意见+问题分级)。提醒:自审最大障碍是"对自己手下留情"——你太爱自己的论文,会下意识给高分、回避硬伤;要刻意当一个挑剔的审稿人,**越狠越值钱**(你自己挑出的,就是真审稿人挑不到的)。意见要具体到某节某句,别泛泛说"写作可以更好"。

## 上午段 · 假装审稿人给论文打分(5 维度,≥500 字)

**① 先垫概念(审稿人通常看什么)**:核心关注四点——① **创新性**(是 incremental 小改进还是 novel 新东西)② **实验是否 fair**(baseline 够不够新、消融够不够充分)③ **写作是否清晰** ④ **是否 overclaim**(夸大结论)。提前用这视角审自己,等于"自己先当一次审稿人"。按 5 个维度(创新 / 技术完善 / 实验充分 / 写作 / 展示)各打 1–5 分,并写 ≥500 字意见。
- **为什么"提前自审"能大幅提高中稿率**:真实审稿时,审稿人会用上面四个视角挑你的毛病——挑到的硬伤可能直接导致拒稿。**如果你提前用同样的视角审自己,把硬伤先挑出来、先修掉,等论文到真审稿人手里时,这些问题已经不存在了**。本质上,自审是"把审稿人会做的事提前自己做一遍",你挑出并修复的每个问题,都是真审稿人少了一个拒你的理由。**自审越狠、越全,中稿率越高**——这是性价比极高的一步。
- **为什么"对自己手下留情"是最大的障碍**:你花了几个月做这个工作、写这篇论文,**你太爱它了**——自审时会下意识给自己高分、把硬伤看成小问题、回避那些"改起来麻烦"的地方。这是人之常情,但对提高论文质量有害。**破解办法:刻意切换身份,假装你是一个"想拒掉这篇论文"的挑剔审稿人**,带着"我要挑出这篇的毛病"的心态去读。越狠越好——你现在对自己狠一点,真审稿人就对你狠不起来(因为问题你都先修了)。
- **5 维打分要诚实(别放水)**:按创新性/技术完善度/实验充分性/写作/展示五个维度,各打1-5分,**诚实打分**——如果某维度确实弱(如创新性只是incremental),就打低分并指出来,而非自我安慰打高分。低分维度正是你要重点改进的地方。**打分的意义不是"给自己评级",而是定位哪个维度最弱、最需要加强**。
- **审稿意见要"先优点后问题、且具体"**:写≥500字审稿意见时,像真审稿那样**先简述优点(这工作的价值),再逐条挑问题**。关键是**问题要具体**——不是"写作可以更好"(这等于没说),而是"4.2第二段只报了数字没解释为什么提升、Table 1缺少最新的某baseline、Abstract里'显著优于'缺数字支撑"。**具体到某节、某句、某个缺失,才能据此修改**。泛泛的意见无法行动。
**② 手把手带做**
1. 把自己当陌生审稿人,对论文 5 维度各打分(诚实,别放水)。
2. 写 ≥500 字"审稿意见",像真审稿那样**先说优点、再逐条挑问题**。
3. 每个问题尽量具体(指到某节某句)。
**③ 合格样例**:5 维打分 + ≥500 字审稿意见(具体指出创新性/实验/写作/overclaim 的问题)。
**④ 常踩的坑**
- **给自己放水**(全打 5 分、只夸不挑)→ 自审越严越值钱;假装"想拒掉这篇"地挑。
- **意见太泛**("写作可以更好")→ 指到具体处("4.2 第二段只报数字没解释")。
**⑤ 卡住自救(决策树)**:挑不出问题?→ 用四问逐条审:创新够吗?baseline 最新吗?消融全吗?有没有 overclaim?还挑不出 → 把论文给"假想的最严审稿人"读,他会先骂哪句。
**⑥ 今天(这一步)你同时学会了什么**:你学会**用审稿人视角自审**。**做了**(自审报告:5 维打分 + ≥500 字意见)、**学了**(审稿四关注点、自审要狠)、**会了**(像审稿人一样评自己的论文)。

> **技能卡｜审稿人四关注**:① 创新性(novel vs incremental)② 实验 fair(baseline 新、消融全)③ 写作清晰 ④ 有无 overclaim。自审、互审、将来审别人,都用这四条。

## 中午段 · 列出自审发现的所有问题(10–20 个)

**① 先垫概念**:把自审发现的问题**全列出来**(预计 10–20 个),先穷举不漏,后面再分级。**为什么"先穷举、后分级"分两步**:如果你边发现边判断"这个重要那个不重要",容易边想边漏(注意力分散)。**正确做法是分两步:第一步只管"穷举"——把所有发现的问题全列出来(大到缺对比、小到错别字),不评判、不遗漏;第二步再"分级"(D148晚上的A/B/C)**。先穷举保证不漏,后分级保证抓重点。这和很多任务的"先发散、后收敛"是一个道理。列的时候,**大小问题都记**——别觉得"这个小问题不值得记",小问题攒多了也影响观感,而且分级时你会决定哪些值得现在改、哪些留到最后。列不全时,逐章过一遍(Abstract/Intro/RW/Method/Experiment/Conclusion各挑几个潜在问题),确保每章都审到。每条记一个**具体**问题(不是"实验部分有问题",而是"4.2缺少和X方法的对比"),具体才能据此修改。
**② 手把手带做**
1. 把审稿意见里的问题逐条拆成清单(10–20 条)。
2. 大小问题都记(小到错别字、大到缺对比)。
**③ 合格样例**:问题清单(10–20 条,大小都有)。
**④ 常踩的坑**:只记大问题 → 小问题也记(分级时再排);记得太笼统 → 一条一个具体问题。
**⑤ 卡住自救**:列不全?→ 逐章过(Abstract/Intro/RW/Method/Exp/Conclusion 各挑几个)。
**⑥ 今天(这一步)你同时学会了什么**:你系统列出了论文问题。**做了**(问题清单)、**学了**(穷举不漏)、**会了**(全面列出论文待改点)。

## 晚上段 · 按严重程度分级(A/B/C)

**① 先垫概念**:**A 级**(必须修,不修可能被拒,如 baseline 不够新 / overclaim)/ **B 级**(应该修,如某处表述不清)/ **C 级**(可以改,如个别用词)。先分级,**集中火力先修 A**。
- **为什么要给问题分级(而非按列表顺序改)**:你自审挑出了10-20个问题,如果不分级、按列表顺序一个个改,可能把大量时间花在无关录用的小问题(错别字、用词)上,而真正决定录用的硬伤(缺关键对比、overclaim)却没时间改透。**分级让你集中火力先解决"影响录用"的问题**——A级是会导致拒稿的硬伤,必须优先修复;B级影响阅读体验但不致命;C级是锦上添花。**有限的时间要优先投给A级**,这是修改策略的核心。
- **A/B/C 各是什么(判断标准)**:① **A级=不修可能被拒**——典型如"baseline不够新(审稿人会说你没和最新方法比)""缺关键消融/对比""overclaim(结论夸大,实验不支撑)""方法描述不清导致无法复现"。这些是审稿人拒稿的常见理由。② **B级=应该修但不致命**——如"某段表述不清(加个图/解释就好)""某处逻辑过渡生硬"。影响阅读但不会直接导致拒稿。③ **C级=可以改的细节**——个别用词、错别字、格式小问题。**一句话判断标准:"审稿人会因为这个拒我吗?会→A;不会但影响理解→B;只是小瑕疵→C"**。
- **C级留到最后统一处理(别现在纠结)**:C级问题(错别字、格式、个别用词)虽然也要改,但**不该现在花时间**——它们不影响录用,而且在后续反复修改中还会产生新的、或被连带改掉。**正确做法:C级留到最终proofreading(W24临投稿前)统一扫一遍处理**。现在(W22)的重心是A级(攻坚硬伤)和B级(提升清晰度)。别在自审阶段就抠错别字,那是本末倒置。
**② 手把手带做**
1. 给每个问题标 A/B/C。
2. A 级单独列(优先修)。
3. 判断标准:"审稿人会因为这个拒我吗?会→A"。
**③ 合格样例**:问题清单分级(A/B/C),A 级明确。
**④ 常踩的坑**:全标 A(分不清轻重)→ 区分"影响录用 vs 锦上添花";难判 → 问"会因此被拒吗"。
**⑤ 卡住自救**:拿不准 A 还是 B?→ 涉及实验缺失/夸大结论=A;表述/美化=B/C。
**⑥ 今天(这一步)你同时学会了什么**:你学会**给论文问题分级**。**做了**(问题分级)、**学了**(A/B/C 分级标准)、**会了**(按严重度排修改优先级)。

> **今日交付**:✅ 自审报告 ✅ 问题清单(分级)。

> **技能卡｜问题分级 A/B/C**:**A级**(必须修,不修可能被拒:baseline不够新/缺关键对比/overclaim夸大结论)→ **B级**(应该修:某处表述不清,加图/加解释)→ **C级**(可以改:个别用词/错别字/格式)。判断标准一句话:"审稿人会因为这个拒我吗?会=A"。**集中火力先清A级**,C级留到最终proofreading统一处理。

# D149 周二 · 修改 A 级问题

> 今天集中攻坚 A 级——那些"不改可能被拒"的硬伤。
>
> **预期管理**:今天集中修 A 级问题(不改可能被拒的硬伤)。提醒:A 级常涉及补实验、改方法描述、修表格——先动这些(它们决定录用),需补实验的边改边启动补跑(并行);**overclaim 必须改**(别舍不得"显著超越",改成有数字支撑的客观表述——夸大结论是被拒的常见原因);A 级要先啃硬的,别拖着先改小的。改完局部再通读那一段,避免改一个引入新问题。

## 上午段 · 修改 A 级问题(第一批)

**① 先垫概念**:A 级常涉及**补实验、改方法描述、修表格**。先动这些(它们决定录用)。若需补实验,边改边启动补跑(并行)。
- **A级问题为什么要"边改边并行补跑"**:有些A级问题需要补实验(如审稿人/你自己发现"缺了某个关键对比"),而训练要花时间。**聪明的做法是:一启动补跑,就同时去改其他不需要等实验的A级问题(改表格、改方法描述、改措辞)**——让GPU在后台跑实验,你在前台改别的,并行推进。别干等实验跑完才改别的,那样浪费时间。这是你M5练过的"实验挂机时推进可做工作"的习惯,在改论文时同样适用。
- **overclaim是最常见也最该优先改的A级问题**:overclaim(夸大结论)是审稿人最反感、也最容易导致拒稿的问题之一——比如你写"我们的方法显著超越所有现有方法",但实际只是小幅提升、或只在某些设置下更好。**审稿人一旦发现你overclaim,会对你整篇论文的可信度打折扣**。所以overclaim必须改。
- **怎么把overclaim改成客观表述(具体)**:① **"显著超越"→给数字**——把"significantly outperforms"改成"achieves X mAP, surpassing the previous best by Y"(用数字说话,让读者自己判断);② **绝对化的词→限定**——"我们的方法解决了X问题"改成"我们的方法在X方面取得了改进";③ **删掉无证据的吹捧**——"novel and powerful"这类没数据撑的形容词,删掉或换成有数据支撑的客观陈述。**核心原则:让数据说话,而非用形容词吹**。客观、有数字、有限定的表述,反而比夸大的表述更可信、更经得起审稿。
- **别舍不得"显著超越"(克服心理)**:你可能舍不得把"显著超越SOTA"改成平实的"提升了X点"——觉得后者"不够亮眼"。**但overclaim的风险远大于"听起来不够强"的代价**:夸大被审稿人识破=可信度崩塌=可能被拒;客观表述=可信=审稿人信任你。**宁可平实可信,不要夸大冒险**。而且如果你的提升确实有限,正确的做法是把卖点转到"高效"维度(你单卡的小参数/高FPS),而非在精度上勉强夸大。
**② 手把手带做**
1. 挑 A 级里最关键的几个开修(如 overclaim 措辞、表格错误、缺的对比)。
2. 需补实验的,启动补跑。
3. 记录改了什么。
**③ 合格样例**:第一批 A 级问题已修(或补跑已启动)。
**④ 常踩的坑**:overclaim 不改(舍不得"显著超越")→ 改成有数字支撑的客观表述;A 级拖着先改小的 → 先啃硬的。
**⑤ 卡住自救**:A 级要补大实验来不及?→ 评估能否用已有结果换种说法,或补一个小实验 + 在 Limitation 说明。
**⑥ 今天(这一步)你同时学会了什么**:你开始攻坚 A 级。**做了**(A 级第一批)、**学了**(优先修致命问题、overclaim 改客观)、**会了**(修改影响录用的问题)。

## 中午段 · 修改 A 级问题(续)

**① 先垫概念**:继续修剩余 A 级,直到 A 级清零。**为什么要"A级清零"才算这一步完成**:A级问题是"不修可能被拒"的硬伤——只要还有一个A级没修,论文就还带着一个可能致命的弱点。所以这一步的目标明确:**把所有A级问题修完、清零**,让论文不再有"会导致拒稿"的硬伤。剩余的A级要逐个攻坚,补跑完成的把新结果填进论文。**改A级时要注意:改一个地方可能影响相邻内容**,改完局部后通读那一段,确认没引入新的矛盾或不一致(比如改了某个数字,要检查所有引用这个数字的地方都同步改了)。某个A级实在难搞(如需要大量补实验),标记下来,留作找朋友/导师讨论的重点,或评估能否用已有结果换种说法+在Limitation说明来化解。
**② 手把手带做**
1. 逐个修剩余 A 级。
2. 补跑完成的,把新结果填进论文。
**③ 合格样例**:A 级问题基本修完。
**④ 常踩的坑**:改一个引入新问题 → 改完局部再通读那一段。
**⑤ 卡住自救**:某 A 级实在难?→ 标记,找朋友/导师讨论(也可作为 mock review 重点请教)。
**⑥ 今天(这一步)你同时学会了什么**:你推进了 A 级修改。**做了**(A 级续)、**学了**(持续攻坚)、**会了**(系统清理 A 级)。

## 晚上段 · 修改 B 级问题

## 上午段 · 竞赛数据 EDA(探索性分析)

**① 先垫概念**:**EDA**= 先摸清数据:类别分布、图像大小、标注格式、难点(长尾?小目标?)。摸清才好定策略(如长尾→重采样,小目标→高分辨率)。
- **为什么开赛先做EDA(而非直接训)**:每个竞赛的数据都有自己的特点——类别分布可能长尾(某些类样本极少)、目标可能特别小或特别密集、图像尺寸可能差异大、标注格式可能特殊。**不先摸清这些就直接套用你的方法,可能效果很差(因为你的方法没针对这个数据的特点)**。EDA(探索性数据分析)就是开赛第一步摸清数据,看清它的分布和难点,**然后据此定针对性策略**——这比盲目训练高效得多。
- **EDA具体看什么(可操作)**:① **类别分布**——各类样本数量,是否长尾(决定要不要重采样/类别加权);② **图像尺寸**——大小分布(决定输入分辨率、要不要切图);③ **标注格式**——什么形式的标注(决定怎么用统一数据层适配);④ **目标特点**——目标大小(小目标多→高分辨率)、密集程度(密集→关注NMS/小目标检测);⑤ **难点**——通过看一些样本,发现这个数据的挑战在哪。**统计这些 + 看一批样本图,写成EDA报告(发现+初步策略)**。
- **EDA→策略的对应(把发现变成行动)**:EDA不是为了"了解数据"本身,而是为了**定策略**——发现长尾→用重采样或focal loss;发现小目标多→提高输入分辨率、用多尺度;发现某类特别难→针对性增强或后处理。**EDA报告要落到"我打算怎么做"**,而非只罗列统计数字。这呼应你M1养成的"先看数据再动手"的习惯——竞赛数据也一样,先摸清、再定策略、再训练。
- **复用你的统一数据层适配竞赛数据**:竞赛数据的格式可能和你之前的数据集不同,但你有W11建的统一数据层——加一个解析分支适配竞赛格式即可,上层训练/评估代码不用改。**这又是良好工程设计的复利**:接竞赛数据几乎零成本,你能把精力放在策略和迭代上,而非重写pipeline。
**② 手把手带做**
1. 统计竞赛数据的类别分布 / 图像尺寸 / 标注格式。
2. 写 EDA 报告(发现 + 初步策略)。
3. 复用你的统一数据层适配。
**③ 合格样例**:竞赛 EDA 报告(分布/尺寸/格式 + 初步策略)。
**④ 常踩的坑**:不看数据直接训 → 先 EDA;格式不熟 → 复用统一数据层。
**⑤ 卡住自救**:格式怪?→ 看官方提供的数据读取示例。
**⑥ 今天(这一步)你同时学会了什么**:你做了竞赛 EDA。**做了**(EDA 报告)、**学了**(数据探索、按发现定策略)、**会了**(开赛先摸清数据)。

## 中午段 · 跑竞赛官方 baseline(得首个分数)

**① 先垫概念**:若有官方 baseline,跑通得第一个分数;无则用你的实验框架直接跑竞赛数据。
- **为什么"用你自己的框架"往往比官方baseline更快**:有的竞赛提供官方baseline代码,但配环境、调通它可能很费劲(依赖、版本、文档不全)。而**你经过M1-M5已经有了一套成熟、熟悉的实验框架**(数据层、训练、评估都跑通过),直接用它跑竞赛数据(加个数据解析分支适配)往往比折腾官方baseline更快——你对自己的框架熟,出问题也好排查。**目标是快速拿到第一个分数,用最顺手的工具即可**,不必拘泥于官方baseline。
- **这一步的目标是"快速有个起点"**:中午这一步不追求高分,只追求**快速跑出一个能提交的结果**——用最简单的配置(你框架的默认设置或官方baseline)在竞赛数据上跑一遍,得到一个分数。这个分数就是你的起点基准。**有了它,晚上就能完成首次提交、正式进场**。所以这一步要快,别在这里调优(调优是后面D154开始的事),先有个能交的结果最重要。
**② 手把手带做**
1. 跑官方 baseline(或你的框架)在竞赛数据上。
2. 得到一个本地/线上分数。
**③ 合格样例**:得到一个 baseline 分数(或你的框架跑通)。
**④ 常踩的坑**:官方 baseline 环境复杂卡住 → 直接用你成熟的框架跑;数据没适配 → 复用统一数据层。
**⑤ 卡住自救**:官方 baseline 跑不起?→ 用你自己的框架(更熟),先有个分数。
**⑥ 今天(这一步)你同时学会了什么**:你有了竞赛起点。**做了**(baseline 分数)、**学了**(起点基准)、**会了**(快速得到竞赛 baseline)。

## 晚上段 · 提交第一次结果

**① 先垫概念(首次提交很重要)**:它给你"起点分数",后面每次改进以此为基准。**哪怕排名很低也没关系——关键是"进场"**(很多人卡在不敢交第一次,追求完美反而一直交不出)。
- **为什么"先进场"比"交个好成绩"重要**:很多新手卡在"我想等方案再好一点、分数再高一点再提交"——结果是**追求完美,迟迟交不出第一次**,竞赛都快结束了还在本地调。**这是大忌**。正确的做法是:**先用最简单的方案(官方baseline或你的现成框架)跑出一个分数、提交、进场**——哪怕排名垫底。为什么?因为① 你需要确认整个流程跑通(数据读取、提交格式都对);② 你需要一个"起点基准",后面每个改进才有参照(知道改进了多少);③ 进场后心理上你就"在这个游戏里了",会持续迭代。**"进场拿到基准分"本身就是胜利**。
- **首次提交的核心价值是"打通流程+建立基准"**:第一次提交,你验证了从"竞赛数据"到"合格提交文件"的全流程没问题(这本身就排除了很多坑:数据格式、提交格式、编码等);同时拿到了起点分数,成为你后续所有改进的"尺子"——改进1提了多少、改进2提了多少,都和这个基准比。**没有基准,你不知道自己的改进有没有用**。所以首次提交不追求分数,追求的是"流程通了+有基准了"。
- **提交格式必须对照官方 sample submission**:第一次提交最容易栽在格式上——列名不对、文件名不对、编码不对、行数不对,导致提交失败或得0分。**解法:严格对照官方提供的sample submission(样例提交文件)**,逐列、逐字段对齐你的输出格式。官方sample就是"正确格式的标准答案",照着它生成你的提交文件,就不会错。用补充包的格式自检脚本核对一遍再提交,避免白跑。
- **别被"排名低"打击**:第一次提交排名垫底是完全正常的(你用的是最简单方案,别人可能已经迭代很多轮了)。**这不代表你不行,只代表你刚进场**。竞赛是个迭代过程——重要的是你进场了、有基准了,接下来每个改进(D154开始)都会往上爬。心态上把第一次提交当"起跑线"而非"成绩单"。
**② 手把手带做**
1. 按提交格式生成结果文件(用补充包的格式自检)。
2. 提交。
3. 记下起点分数和排名(竞赛日志)。
**③ 合格样例**:**竞赛首次提交**完成,有起点分数 / 排名。
**④ 常踩的坑**:**追求完美迟迟不交** → 先交后迭代;**提交格式错** → 对照官方 sample submission。
**⑤ 卡住自救**:提交格式报错?→ 逐列对照官方 sample;编码/文件名不符 → 按要求改。
**⑥ 今天(这一步)你同时学会了什么**:你完成了首次提交(进场)。**做了**(首次提交)、**学了**("先进场"心态、以基准衡量)、**会了**(按格式提交并记基准)。

> **技能卡｜竞赛进场**:第一次提交=拿"基准分",哪怕垫底也是赢;之后每个 Trick 都用它当尺子。别为完美耽误进场。

> **今日交付**:✅ 竞赛 EDA 报告 ✅ **竞赛首次提交**。

# D153 周六(集中日)· 处理 mock review + 写 rebuttal 练习

> 朋友的意见回来了。今天学会"分两类处理 + 写 rebuttal"——这正是真实审稿要做的事。
>
> **预期管理**:今天处理 mock review(分两类)+ 写 rebuttal 练习。提醒:把意见分"有道理(要改)"和"不同意(要反驳)"两类,对每条都认真对待、**对事不对人不情绪化**(审稿措辞可能尖锐,但出发点是帮你);不同意的要给有理有据的反驳——反驳三角度:①用已有数据反驳 ②澄清审稿人误解 ③补一个小实验;别对不同意的避而不谈,每条都要回应。这是真实 rebuttal 的预演。

## 上午段 · 收 mock review 反馈 → 整理 → 分两类

**① 先垫概念**:把朋友的意见逐条整理,分"**有道理**(要改)"和"**不同意**(要反驳)"两类。这是真实审稿的预演——**对每条都要认真对待,不情绪化**(审稿措辞可能尖锐,但出发点是帮你)。
- **为什么要把意见分"有道理/不同意"两类**:收到一堆审稿意见,不能一股脑全改、也不能一概不理——要**分类处理**:有道理的(指出了真问题)就改;不同意的(你认为审稿人误解了或不成立)就准备反驳。**这个分类是处理审稿意见的第一步**,它让你对每条意见有明确的应对策略,而非混乱地一条条纠结。这正是真实投稿收到审稿意见后要做的事,现在用mock review练。
- **怎么判断一条意见"有道理"还是"该反驳"**:① **有道理**——审稿人指出的确实是你论文的真问题(表述不清、缺对比、逻辑漏洞),即使你一开始不爱听,冷静想确实如此;② **该反驳**——审稿人的意见基于误解(误读了你的方法/设置)、或要求不合理(超出论文范围)、或你已有证据反驳。**判断技巧:别凭"爱不爱听"判断,凭"审稿人说的对不对"判断**。一个有用的自问:"审稿人为什么这么说?"——多数情况下,即使审稿人误解了,也说明你那里**表述不够清楚**(否则他不会误解),所以哪怕你要反驳,也往往要顺便改进表述。
- **"对事不对人、不情绪化"是关键修养**:mock review(以及真实审稿)的意见可能措辞尖锐——"这个实验设计有缺陷""写作混乱"——让你下意识想辩护或生气。**但你要训练自己对事不对人、不情绪化**:审稿人(哪怕措辞尖锐)的出发点是帮你把工作做得更好,他指出的问题(哪怕表述刺耳)往往有价值。**把注意力放在"他指出的问题是什么、我该怎么应对",而非"他的态度让我不爽"**。这种专业心态,是你做研究、写rebuttal、将来自己审别人论文都需要的。现在用mock review练起来。**为什么现在练rebuttal特别值**:真实投稿时,从收到审稿意见到提交rebuttal往往只有有限时间(几天到两周),临时学怎么写rebuttal会手忙脚乱。现在借mock review先把"分类→方案→反驳"的流程和句式练熟,等真投稿时收到意见,你就能从容应对——这是把"未来的紧急任务"提前在不紧急时演练,投资回报很高。
**② 手把手带做**
1. 整理 mock review 每条意见。
2. 标"有道理 / 不同意"。
3. 心态:对事不对人。
**③ 合格样例**:mock review 意见整理(分两类)。
**④ 常踩的坑**:情绪化对待尖锐意见 → 对事不对人;看不懂意见 → 找朋友确认本意。
**⑤ 卡住自救**:某条不知该不该接受?→ 想"审稿人为什么这么说",多半指向一个真实弱点。
**⑥ 今天(这一步)你同时学会了什么**:你学会整理审稿意见。**做了**(意见整理)、**学了**(分两类、对事不对人)、**会了**(把反馈分成可行动两类)。

## 中午段 · 对"有道理"的逐条定修改方案

**① 先垫概念**:对每条"有道理"的意见,写**具体修改方案**(改哪、怎么改)。**为什么要写"具体方案"而非笼统说"会改"**:收到一条有道理的意见(如"4.2缺少和最新方法的对比"),如果只在心里记"嗯,会改",很容易后面忘了、或改得不到位。**正确做法是对每条有道理的意见写出具体的修改方案**:改论文的哪个位置、具体怎么改(补哪个对比实验/加哪句解释/改哪个表)。这样把"意见"转成了"可执行的行动项",改起来不会漏、不会跑偏。方案多的时候,也按A/B/C(影响录用程度)排优先级,先做最关键的。**意见→具体方案→执行**,是处理审稿反馈的标准流程,这也是真实rebuttal阶段你要做的——审稿人看你的修改,看的就是你有没有针对每条意见做出实际的、到位的修改。把每条方案标到论文的具体位置(改第几节第几段),执行时就不会找不到、不会漏。
**② 手把手带做**
1. 对每条有道理的意见写方案。
2. 标到论文具体位置。
**③ 合格样例**:修改方案清单(每条:针对哪条意见、怎么改)。
**④ 常踩的坑**:笼统说"会改" → 写具体怎么改。
**⑤ 卡住自救**:方案多?→ 也按 A/B/C 排优先级。
**⑥ 今天(这一步)你同时学会了什么**:你把意见转成了行动。**做了**(修改方案)、**学了**(意见→方案)、**会了**(把审稿意见落成修改计划)。

## 晚上段 · 对"不同意"的写 rebuttal(反驳)

**① 先垫概念(处理审稿意见原则)**:① 每条都认真回应 ② 同意就改 ③ **不同意要给有理有据的反驳**(用数据 / 已有实验 / 澄清误解,不情绪化)。这是为真实 rebuttal 练手。
- **为什么 rebuttal 是必备技能**:论文投稿后,审稿人会给意见,你需要写 rebuttal(答辩/回复)来回应——同意的改、不同意的有理有据地反驳。**rebuttal 写得好,能把"borderline(边缘)"的论文救成"accept"**;写得差(情绪化、答非所问、回避问题),可能把本来有机会的论文搞砸。所以现在用 mock review 练 rebuttal,是为真实投稿的关键环节做准备。这是每个研究者都要掌握的硬技能。
- **rebuttal 三原则(铁律)**:① **每条意见都要认真回应**——哪怕是你不同意的,也不能避而不谈(审稿人会觉得你心虚或不尊重);② **同意的就大方改**——审稿人指出的真问题,承认并说明你怎么改(这显得你虚心、有则改之);③ **不同意的要有理有据地反驳**——不是简单说"我不同意",而是用证据说明为什么审稿人的担心不成立。**三条的核心是"认真、诚恳、有据"**。
- **反驳的三个角度(不同意时这样驳)**:① **用已有数据反驳**——"审稿人担心X,但如Table Y所示,我们的实验已经表明…"(你的实验里可能已经有反驳的证据);② **澄清审稿人的误解**——有时审稿人是误解了你的方法/设置,礼貌地澄清"我们想说明的是…,可能表述不够清楚,已在修订版改进";③ **补一个小实验**——如果审稿人的质疑确实需要新证据,补一个针对性的小实验来回应。**这三个角度覆盖了大部分"不同意"的情况**:要么你已有证据、要么是误解、要么补证据。
- **永远"对事不对人、不情绪化"(rebuttal 的态度)**:审稿意见有时措辞尖锐、甚至让你觉得"审稿人没认真读"——但**写 rebuttal 时必须保持礼貌、客观、专业,绝不情绪化**。用"We thank the reviewer for the comment. The reviewer is concerned that X. However, as shown in…, Thus…"这样的礼貌句式。**情绪化的反驳(哪怕你有理)会让审稿人反感,反而害了你的论文**。记住:审稿人的出发点是帮你把工作做得更好(即使措辞尖锐),你的回应也要体现这种专业态度。对事不对人,是 rebuttal 的基本修养。
**② 手把手带做**
1. 对"不同意"的意见写 rebuttal(礼貌 + 证据反驳)。
2. 套句式:"We thank the reviewer. The reviewer is concerned that X. However, as shown in Table Y, …. Thus …"
**③ 合格样例**:rebuttal 练习(有理有据、礼貌)。
**④ 常踩的坑**:情绪化反驳 → 客观礼貌;对不同意的避而不谈 → 每条都回应。
**⑤ 卡住自救**:不知怎么驳?→ 用三角度:① 已有数据反驳 ② 澄清审稿人误解 ③ 补一个小实验。
**⑥ 今天(这一步)你同时学会了什么**:你学会**写 rebuttal**。**做了**(rebuttal 练习)、**学了**(回应审稿三原则、反驳三角度)、**会了**(有理有据回应每条意见)。

> **技能卡｜处理审稿意见**:每条都回应;同意→改;不同意→用"数据/澄清误解/补实验"礼貌反驳。永远对事不对人。

> **今日交付**:✅ mock review 整理 ✅ 修改方案 ✅ rebuttal 练习。

# D154 周日(复盘日)· W22 复盘 + 竞赛改进 1

> 本周收尾:复盘 + 竞赛迈出第一个提分改进。
>

## 中午段 · 竞赛改进 1(换更强 backbone / 增大分辨率)

**① 先垫概念**:竞赛提分常从"**换更强 backbone / 增大输入分辨率**"这类稳妥改进起步(见效快、风险低)。**一次只改一处**,才知道哪个有用。
- **为什么从"换backbone/增大分辨率"起步**:竞赛提分有很多招数(换backbone、调分辨率、数据增强、模型集成、后处理、TTA等),其中**"换更强backbone"和"增大输入分辨率"是最稳妥的起步招**——它们见效快(往往直接涨点)、风险低(不容易搞坏)、实现简单(改个配置)。**先用这些稳妥招把分数往上推一截,建立信心、积累对这个竞赛的感觉**,再尝试更复杂的招数(集成、特殊trick)。这是竞赛迭代的常见路径:先摘低垂的果子。
- **"一次只改一处"是竞赛迭代的铁律(和消融同理)**:如果你一次同时换backbone、改分辨率、加增强,分数涨了——**你不知道是哪个改动起的作用**(可能backbone有用、分辨率没用甚至有害,但被backbone的提升掩盖了)。**一次只改一处,提交看分数变化,你才能确定这一处改动的真实效果**(涨了=有用保留,没涨=无用换下一招)。这和你W19做消融"每次只改一个变量"是完全一样的逻辑——竞赛迭代本质也是一连串的"控制变量实验"。
- **每个改进记入"竞赛Trick日志"**:就像实验矩阵管理几十组实验,竞赛也要用一个**Trick日志**记录每次尝试:改了什么、Δ分(提升多少)、是否保留。**这样你能清晰地看到"哪些招有用、哪些没用、当前最优组合是什么"**,避免重复尝试、避免忘记。竞赛到后期会试很多招,没有日志会乱成一团。一次一处改 + Trick日志记录,是有条理地爬榜的关键。
- **OOM是换大backbone/高分辨率的常见障碍**:换更强(更大)的backbone或增大输入分辨率,会增加显存占用,你单张4090(24GB)可能OOM。**解法:降batch size + 梯度累积(用累积保持等效batch)、混合精度训练(amp,省显存)**。这些都是你前面练过的单卡省显存技巧,在竞赛里继续用。实在跑不动超大配置,就在你显存能承受的范围内选最强的backbone/最高的分辨率。
**② 手把手带做**
1. 做竞赛改进 1(换更强 backbone 或增大分辨率,二选一)。
2. 训练。
3. 记入竞赛 Trick 日志。
**③ 合格样例**:竞赛改进 1 训练完成。
**④ 常踩的坑**:大 backbone/高分辨率 OOM → 降 batch + 梯度累积;一次改多处 → 一次一处。
**⑤ 卡住自救**:OOM?→ 降 batch、梯度累积、混合精度;没提升?→ 记录换下一招(W23 有 Trick 清单)。
**⑥ 今天(这一步)你同时学会了什么**:你开始竞赛迭代。**做了**(竞赛改进 1)、**学了**(稳妥提分起步、一次一处)、**会了**(用更强 backbone/分辨率提分)。

## 晚上段 · 提交竞赛改进版 → 看排名变化

**① 先垫概念**:提交改进 1 的结果,看排名/分数变化,以基准衡量改进。
- **为什么"以基准衡量"是竞赛迭代的核心方法**:你有了首次提交的基准分数,现在每做一个改进,就提交、看分数相对基准变化了多少——**这个"Δ分"告诉你这个改进到底有没有用、有多大用**。涨了=有用(保留这个改进,作为新基准);没涨甚至跌了=没用(放弃,换下一招)。**整个竞赛迭代就是"改进→提交→看Δ→决定保留还是放弃"的循环**,每一步都以当前最优为基准衡量。没有基准、不看Δ,你就是在盲目试,不知道自己在进步还是退步。
- **Trick日志记三样**:每次提交后,在Trick日志里记**①改了什么 ②Δ分(相对上次/基准) ③是否保留**。例如"换Swin-B backbone: +1.2,保留";"加TTA: +0.3,保留";"某增强: -0.5,放弃"。**这个日志是你竞赛进展的完整账本**——它让你清楚当前用了哪些有效trick、当前最优是什么、还有哪些招没试。竞赛后期试的招多了,没日志会乱、会重复试、会忘记。
- **"线上没涨但本地涨"要警惕(过拟合本地划分)**:有时你的改进在本地验证集上涨了,但提交到线上排行榜没涨甚至跌了——**这往往是过拟合了你的本地验证划分**(你的改进恰好迎合了本地验证集的特点,但不泛化到线上测试集)。**遇到这种情况,以线上为准**(线上测试集才是真正的评判)。这提醒你:本地验证集要和线上分布尽量一致,别过度依赖本地分数。线上分数是最终的真相。
- **没提升就换下一招,别放弃整个方向**:某个改进(如某种增强)提交后没涨,**只说明这一招对这个竞赛没用,不代表你的整体方向不行**——记录下来(日志里标"放弃"),换下一招试(W23会有更系统的Trick清单)。竞赛是个不断试错的过程,大部分招可能没用,但只要持续试、保留有用的,分数就会稳步往上爬。别因一两招没用就气馁或放弃。**竞赛的本质是"持续试错 + 保留有效"**——接受大部分尝试可能无效,但只要有日志记录、一次一处改、保留有用的,分数就会螺旋上升,这也是做研究的常态心态。
**② 手把手带做**
1. 生成提交、提交。
2. 看排名变化,记入 Trick 日志(改了什么 / Δ分 / 是否保留)。
**③ 合格样例**:**竞赛第 2 次提交**,排名变化记录。
**④ 常踩的坑**:没提升就放弃这个方向 → 记录,试下一招;提升就保留。
**⑤ 卡住自救**:线上没涨但本地涨?→ 可能过拟合本地划分,看线上为准。
**⑥ 今天(这一步)你同时学会了什么**:你完成第二次提交并学会以基准衡量。**做了**(竞赛第 2 次提交)、**学了**(以基准衡量、Trick 日志)、**会了**(迭代并跟踪排名)。

## 二、实用工具 — 竞赛 EDA + 提交格式自检
```python
import os, glob, collections
from PIL import Image
# ① 竞赛 EDA:类别分布 + 图像尺寸
def eda(ann_labels, img_dir):
    print("类别分布:", dict(collections.Counter(ann_labels).most_common()))   # 看长尾
    sizes = collections.Counter()
    for f in glob.glob(os.path.join(img_dir, "*"))[:500]:
        try: sizes[Image.open(f).size] += 1
        except: pass
    print("常见图像尺寸:", sizes.most_common(5))                              # 定输入分辨率
# ② 提交文件自检(对照官方 sample 的列)
def check_submission(sub_path, required_cols):
    import csv
    with open(sub_path) as f: header = next(csv.reader(f))
    print("提交缺列:", set(required_cols) - set(header) or "无", "| 实际列:", header)
if __name__ == "__main__":
    print("用法:开赛先 EDA;提交前自检格式")
```
**预期**:① 打印类别分布(看长尾)+ 常见尺寸(定分辨率);② 检查提交文件列是否符合官方要求。**用法**:开赛先跑 EDA 摸清数据(据发现定策略:长尾→重采样/类别加权,小目标→提高分辨率);每次提交前用 check_submission 对照官方 sample 的列核对一遍,避免因格式不符白跑或得 0 分。这两个小工具配合 Trick 日志,让你的竞赛迭代既不踩格式坑、又能有条理地爬榜。
