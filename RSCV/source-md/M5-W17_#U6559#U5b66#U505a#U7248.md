## 上午段 · 设计完整实验矩阵文档

**① 先垫概念(假设你从没管理过大规模实验)**
- **实验矩阵**:把所有要跑的实验列成**一张表**(每行一组实验,带编号 / 配置 / 状态),它就是你的**"作战地图"**。规模哪来的?`3 个数据集 ×(6 个 baseline + 你的方法 = 7 个方法)× 3 个 seed = 63 组`。
- **为什么非管不可**:想象你两天后看到日志里一个 `mAP=0.783`——没有矩阵,你根本说不出它是"数据集 2 上 baseline 4 的 seed 1",还是"数据集 1 上你的方法 seed 3"。**矩阵给每组一个唯一 ID,让任何一个数字都能反查到它的来历**;每完成一组就在表里打勾,进度一眼可见。这跟 M3 时你凭记忆管几组实验是两个世界——规模一上来,记忆就崩,必须靠"表"。
- **和通用 CV 的关系**:这不是遥感特有的,是所有做实证研究(CV/NLP/RL)的人都要会的工程素养。你现在练的是可迁移到任何领域的"实验工程"能力。
- **为什么"混乱"是大规模实验的头号杀手(本周反复强调)**:90% 的人不是输在方法不好,而是输在"管理跟不上"——跑了几十组,结果和配置对不上、checkpoint 互相覆盖、忘了某次的超参,最后对着一堆数字无法复盘、无法写论文。**算法再好,如果结果不可追溯,就等于没做**。所以本周的及格线不是"跑了多少组",而是"每一组都能被追溯到它的来历"。这是一种纪律,一旦养成,你后面每个研究项目都受益。
- **矩阵 + 独立 config + 独立输出目录,三位一体**:光有矩阵还不够——每组实验要有**独立的 config 文件**(文件名=实验 ID,跑哪组指哪个文件,杜绝"改了 config 忘了改回来"的串味)和**独立的输出目录**(以 ID 命名,杜绝 checkpoint/日志互相覆盖)。三者配套,几十组实验才真正可控、可复现、可追溯。这套"工程脚手架"看着繁琐,但它是大规模实验不崩盘的地基。

**② 手把手带做**
1. 在 `experiments/experiment_matrix.md` 建一张表,至少这些列:
   ```markdown

   |--------|--------|------|------|-----------|------|--------|------|
   | D1-base1-s0 | D1 | baseline1 | 0 | cfg/d1_base1.yaml | 待跑 |  |  |
   ```
2. **ID 命名要可读**:`{数据集}-{方法}-s{seed}`(如 `D1-ours-s2`),一眼知道是谁——别用 `exp1/exp2` 这种过两天就忘的名字。
3. 用 W8 的 **SOTA 性能榜**确定那 6 个 baseline:挑"**开源 + 被论文反复当基准对比**"的(这才是"公认 baseline",审稿人才认)。
4. 把 63 组**全部列出来**(哪怕暂时只跑得动一部分),状态先全填"待跑"。

**③ 合格样例**:一张 63 行的实验矩阵——每组有唯一可读 ID、对应一个 config 文件、有状态列;那 6 个 baseline 是你方向公认的(能说出每个为什么选它)。

**④ 常踩的坑**
- **不建矩阵直接乱跑**:跑得很爽,但一周后结果和配置对不上,根本无法复盘、无法写论文。**先有地图再行军**。
- **baseline 选得随意**(顺手挑几个不知名的)→ 审稿人会说"你没和主流方法比",直接质疑你的对比有效性。回 SOTA 榜挑公认的。
- **ID 无规律**(`run_final_v2_real`)→ 几十组里你自己都分不清,务必含"数据集+方法+seed"。

**⑤ 卡住自救(决策树)**

- config 太多管不过来?→ **一组一个 config 文件,文件名就等于实验 ID**,以后跑哪组就指哪个文件。

**⑥ 今天(这一步)你同时学会了什么**:你学会了**用实验矩阵管理大规模实验**——这是从"学生式跑实验"迈向"研究者式做实验"的分水岭。**做了**(63 组实验矩阵)、**学了**(矩阵=作战地图、为何必须管理、ID 可读命名、公认 baseline 的选取)、**会了**(把几十组实验组织成一张可追溯、可打勾的表)。

> **技能卡｜大规模实验管理三件套**:① **矩阵**(每组唯一 ID + 状态)→ ② **每组独立 config**(文件名=ID)→ ③ **每组独立输出目录**(以 ID 命名)。三者齐全,几十组实验才不会互相覆盖、才追溯得回去。

## 中午段 · 配置 wandb(给实验装"自动飞行记录仪")

**① 先垫概念**
- **wandb(Weights & Biases)**:一个实验追踪工具。把它想成**飞机的"黑匣子/自动飞行记录仪"**——你训练时它**自动**记下这一架次的全部数据:超参、loss 曲线、各项指标、运行时长、用了哪台机器。事后还能在网页里把**多架次并排对比**。
- **它解决你什么痛**:63 组实验,手记超参必然出错、必然漏。wandb 让你**再也不会"忘了那次的学习率是多少"**,也能一眼看出"哪组配置的曲线最好"。
- **为什么"自动记录"比"手动记"可靠太多**:手动记超参/结果,在 63 组规模下必然出错——你会忘记记某次、会记错某个数、会漏掉某个细节。而 wandb 在你训练时**自动**抓取并上传全部信息(超参、每个 epoch 的 loss/指标、运行时长、硬件、甚至代码版本),一条不漏、一字不错。**把"记录"这件易错的体力活交给工具,你只管分析**——这是大规模实验不出错的关键。**尤其要把 git commit hash 也记上**:日后想精确复现"那次"的结果,你需要知道当时用的是哪个版本的代码,光有超参不够。
- **wandb 最强的是"横向对比"**:你有 63 条实验,wandb 网页能把它们**并排画在一张图上**(如所有方法的 val 曲线叠在一起),你一眼就能看出"哪条最高、哪条最稳、哪条崩了"。还能按超参分组、排序、筛选(如"只看 lr=0.01 的"),快速定位规律。**这种多实验的可视化对比,是手动记录和 print 完全做不到的**,也正是你 63 组实验最需要的。
- **和 TensorBoard 的区别**:TensorBoard 在本地、看**单次**曲线很方便;wandb 在云端、**多实验横向对比**更强(你正好有 63 组要横向比)。**二选一即可**——重隐私/不方便联网就用 TensorBoard,否则推荐 wandb。今天别纠结,选一个 5 分钟配好。

**② 手把手带做**
1. 装并登录:
   ```bash
   pip install wandb
   wandb login        # 粘贴官网给你的 API key
   ```
2. 在 `train.py` 里接入(开头初始化、训练中 log):
   ```python
   import wandb
   wandb.init(project="rs-main-exp",
              name=f"{cfg['dataset']}-{cfg['method']}-s{cfg['seed']}",  # name 用实验 ID!
              config=cfg)                       # 把超参字典传进去,网页才看得到
   for epoch in range(cfg["epochs"]):
       # ... 训练 + 验证,得到 loss / val_metric ...
       wandb.log({"epoch": epoch, "loss": loss, "val_metric": val_metric})
   wandb.finish()
   ```
3. **先跑一个最小实验**(几个 iter)验证能上报,再正式开跑——别等大实验跑完才发现没记上。

**③ 合格样例**:wandb 里建好了 `rs-main-exp` 这个 project;跑完那个最小实验后,网页上能看到这次的 **loss 曲线** + **超参表**(lr / batch / epoch 等都在 config 里显示出来了)。

**④ 常踩的坑**
- **只 `print` 不接 wandb**:终端一关日志就丢了,63 组根本记不住。
- **接了 wandb 但没把超参传进 `config`**:网页上看得到曲线、却不知道这条是什么配置——**务必把超参字典传给 `config`**。
- **每次 `name` 都一样**:网页里几十条线分不清谁是谁。**name 用实验 ID**(数据集-方法-seed)。

**⑤ 卡住自救(决策树)**
- 不方便联网 / 重隐私?→ 改用 **TensorBoard 本地**(`from torch.utils.tensorboard import SummaryWriter`),记一样的东西。
- wandb 接入报错?→ 先单独跑官方最小示例确认环境/登录没问题,再把它接进你的 `train.py`。
- 网页上看不到指标?→ 检查是不是漏了 `wandb.log(...)`,或 key 名写错。

**⑥ 今天(这一步)你同时学会了什么**:你给实验装上了"自动记录仪",从此超参/曲线/指标**自动留痕、可横向对比**。**做了**(wandb 配置 + 最小验证)、**学了**(实验追踪工具是什么、wandb vs TensorBoard、为何必须自动记录)、**会了**(让每组实验自动记录并可在网页对比)。

> **技能卡｜每个实验必记五样**:超参(config)、loss 曲线、验证指标、运行时间、**当前 git commit hash**(把代码版本也记上,日后才能精确复现"那次"的结果)。

## 晚上段 · 数据集 1 启动 baseline 1–3

**① 先垫概念**
- **对比实验的铁律**:要让"我的方法比 baseline 好"这句话成立,必须**控制所有其它变量都相同**(同数据、同评测协议、同 seed、同训练轮数),**只改"方法"这一项**。否则别人会说"你是不是只是训得更久/分辨率更大才赢的?"——对比就废了。
- **为什么"公平对比"是论文可信度的根基**:审稿人评判一个方法,核心问的是"你的提升真的来自你的方法,还是来自别的因素(训得久、数据多、调参好)?"。**如果你跑自己方法时顺手改了 lr、用了更大分辨率、训了更多 epoch,那你的提升就说不清是方法的功劳还是这些改动的功劳**——对比失去意义,审稿人直接质疑。所以铁律是:你的方法 vs baseline,**除了"方法"本身,数据/评测协议/seed/训练轮数/增强全部相同**。这个纪律要贯彻到每一组实验的每一个细节。
- **这条纪律为什么对你尤其重要**:你是单人单卡,没有大组的资源去"暴力调参刷点"。**你的论文要靠"方法本身的有效性"说话,而严格的公平对比正是证明这一点的唯一方式**。一旦对比不公平,你那点来之不易的提升就不可信了。所以与其花心思在各种"小动作"上刷点,不如把对比做得干干净净——只换方法、其余全同——这样你的提升才站得住、才发表得了。
- **为什么先跑 baseline**:先把"标杆线"立起来。你的方法出结果时,得有个参照才知道自己是"刚过线"还是"遥遥领先"。
- **seed 是什么**:随机种子,决定权重初始化、数据打乱顺序等"随机起手"。**固定 seed = 让随机过程可复现**;不同 seed 多跑几次 = 看结果稳不稳(下周三起做多 seed)。

2. 每启动一个,矩阵对应行状态改成"**进行中**"。
3. 打开 wandb 盯三条 loss 曲线。

**③ 合格样例**:baseline 1–3 已在跑,wandb 里三条 loss 正常下降;矩阵里这三行状态已是"进行中"。

**④ 常踩的坑**

## 上午段 · 监控 baseline 1–3 训练

**① 先垫概念(怎么判断训练正不正常)**
- **loss 应稳步下降**——注意是"稳步",**有上下波动是正常的**,不必单调下降。
- **两种典型异常**:① loss 一直不降(几乎水平)→ 学习率可能太小,或数据加载有问题(模型没真正在学);② loss 突然变成 **NaN**(爆炸)→ 学习率太大,或数据里有脏值/坐标越界的标注。
- **关键经验**:**前几个 epoch 的下降速度,基本决定整体走势**。所以要早看——发现不对,几分钟内就能止损,而不是等它白跑一晚上。

**② 手把手带做**
1. 打开 wandb,看 baseline 1–3 的 **loss 曲线**和 **val 指标曲线**。
2. 对照"稳步下降"判断:健康的让它继续;异常的**立即停掉**排查。
3. 把观察(谁正常、谁异常、怎么处理的)记一句到实验日志。

**③ 合格样例**:三条 loss 都在稳步下降(或你已识别出异常那条、并定位到原因开始修)。

**④ 常踩的坑**
- **启动后不管、跑完才看**:白白浪费几小时 GPU——大规模实验,GPU 时间就是命。
- **看到波动就以为坏了**:波动正常,看**总体趋势**。
- **NaN 了还傻等**:NaN 不会自愈,**立即停**,降 lr / 查数据。

**⑤ 卡住自救(决策树)**

## 晚上段 · 启动你的方法 seed 2

**① 先垫概念(为什么要多 seed)**:单次实验有随机波动(初始化、数据打乱都随机)。**跑 3 个不同 seed 取平均 ± 标准差**,才能区分"是真有效"还是"这次 seed 运气好"。这是学术规范,也是审稿人必查的——只报单 seed 的结果会被认为不可信。
- **为什么单次结果可能骗人**:深度学习训练有很多随机性(权重随机初始化、数据每轮随机打乱、某些操作的随机性)。同一个方法、同样的设置,换个随机种子,结果可能差零点几甚至一两个点。**所以你单跑一次得到"+1.5",很可能只是这次 seed 运气好——换个 seed 可能就只剩 +0.3 甚至持平**。靠单次结果下"我的方法更好"的结论,是不可靠的,审稿人也不会信。
- **3 个 seed + mean±std 怎么解读**:跑 3 个不同 seed,得到 3 个结果,算**平均值(mean)±标准差(std)**。mean 是你方法的"真实平均水平"(消除了单次运气);std 反映"稳定性"(std 小=每次都差不多、稳定;std 大=时好时坏、不稳定)。**报"78.1±0.3"远比报"78.4"可信**——前者说明你跑了多次、结果稳定可复现。
- **"提升要超过 std 才算赢"这条铁律**:如果你的方法比 baseline 高 0.2,但两者的 std 都有 0.5——那这 0.2 完全在随机噪声范围内,**不能算"显著提升"**(可能只是这几次 seed 的运气)。只有当"你的 mean − baseline 的 mean"明显大于它们的 std(如高 1.5 而 std 只有 0.3),才能理直气壮说"显著更好"。**这是判断"真赢"还是"噪声内"的硬标准**,别拿噪声内的微弱优势 overclaim。
- **公平的关键:baseline 和你的方法同等对待**:多 seed 的纪律必须对所有方法一视同仁——不能只给自己的方法跑 3 个 seed 取最好的,而 baseline 只跑 1 个。**那是作弊式的不公平**。要么都跑多 seed 取 mean±std,要么都单 seed(但单 seed 不可信)。审稿人会查这个。这也呼应本周反复强调的"公平对比"——对照纪律体现在每一个细节。
- **GPU 不够时的取舍**:3 个 seed 是学术下限。如果算力实在紧张,优先保证**主数据集**的 3 seed(那是你的核心结果),次要数据集可以少跑一些(但要在论文里注明)。错峰跑(白天一个 seed、晚上一个)能在单卡上凑齐多 seed。

**② 手把手带做**
1. 换一个随机 seed(如 `--seed 1`),重跑你的方法,**其余设置不变**:
   ```bash

   ```
2. 矩阵更新。
3. 错峰避免显存冲突。

**③ 合格样例**:seed 2 已启动(**只换了 seed**,config 没动)。

**④ 常踩的坑**:**多 seed 时改了别的变量** → 不可比(多 seed 的全部意义就是"只有 seed 不同");**只跑 1 个 seed 就写进论文** → 不可信。

## 中午段 · 分析"在哪好、在哪差"

**① 先垫概念(为什么花专门时间做这个)**:这是论文 **Discussion 的核心**。一句"在小目标上显著提升(+5.3 AP),在大目标上提升有限(+0.8),原因可能是我们的多尺度模块对小尺度更友好"——**有数字、有原因的分析,远比单报一个总分有价值**,它直接体现你的学术深度。
- **为什么"总分"远不如"细分+原因"值钱**:总分(如"+1.8 mAP")只告诉读者"你的方法好一点",但不解释"好在哪、为什么好"——这是流水账式的结果汇报,学术价值低。而"在小目标上 +5.3、在大目标上 +0.8,因为我的多尺度模块对小尺度更友好"**讲清了你的方法到底在解决什么问题、机理是什么**——这是洞察,是审稿人判断你"是否真懂自己方法"的关键。**一篇论文的深度,很大程度体现在 Discussion 的细分分析上**。
- **"细分分析"怎么做(可操作)**:① 拿到 per-class 结果,找出你的方法相对 baseline **提升最大的几类**和**几乎没提升甚至下降的几类**;② 对每一类,问"这类样本有什么特点(小/密集/某种场景)";③ 把"该类特点"和"你的方法设计(你的组件治什么)"对起来——**差异往往就出在这个对应关系里**(你的组件正好治了某类的痛点,所以那类提升大;某类的痛点你没碰,所以没提升)。这个"数据特性×方法设计"的对应,就是你 Discussion 的逻辑骨架。
- **细分分析还能反过来指导你改进方法(M4 会用到)**:你发现"大目标上几乎没提升",这不只是 Discussion 素材,更是改进方向——下一轮迭代(M4)你可以针对"大目标"加强,或在论文里把这写成 Future Work。**结果分析不是终点,而是下一轮研究的起点**。养成"每出一份结果就深挖在哪好在哪差"的习惯,你的研究会持续进步、论文会持续变厚。
- **原因要"有据"而非"牵强"**:最忌讳的是给个泛泛的原因("因为我们的方法更好""因为更鲁棒")——这等于没说。原因必须具体到机理(你的哪个组件、怎么作用、为什么对这类有效),且最好能用可视化或额外小实验佐证。**说不清机理的"提升",审稿人会怀疑是调参/运气而非方法真有效**。

**② 手把手带做**
