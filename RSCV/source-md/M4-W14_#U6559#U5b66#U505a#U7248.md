# D92 周一 · 基于 v2 问题设计 v3 + 启动

> **预期管理**:今天把 v2 的遗留弱点(密集相邻目标粘连)变成 v3 的一个针对性改动,并启动训练。提醒:v3 不是"再堆一个新模块",而是"把上一版没收口的那个问题收口"——改动要小、要准、单卡可做。结果明后天看。

## 上午段 · 设计 v3 改进（针对 v2 暴露的问题）

**① 先垫概念(v3 的改动从哪来、迭代的"收敛感")**
- **v3 的改进来自 v2 仍没解决好的问题**(从 v2 的 per-class/定性/跨数据集结果看最弱的一环)。继续"针对问题改"的原则。本例:v2 在密集相邻小目标上仍有"框粘连"(标准 NMS 把挨得近的两个目标当成一个),所以 v3 针对粘连改后处理。
- **和通用 CV 一样、但你要有"收敛意识"**:方法迭代不是无限加模块,而是"发现问题→针对改→验证→还有没有大问题"的收敛过程。到 v3,你应该感觉"主要弱点已经一个个被收口",而不是越改越复杂。**对单卡选手尤其重要**:每多一个模块都增加显存/耗时,要的是"少而精的有效改动",不是堆砌。
- **本例 v3 的两小改(都针对粘连)**:① 把标准旋转 NMS 换成旋转 **Soft-NMS**(不直接删相邻框,而是按重叠度衰减其得分,密集场景少漏);② 检测头最高分辨率层微调(让相邻小目标特征更可分)。

**② 手把手带做**:分析 v2 的弱点(从 v2 的 per-class/定性/跨数据集结果看),在 `docs/v3设计.md` 写 v3 核心改动(针对哪个弱点、怎么改、预期);基于 v2 的 config 派生 v3 config。设计骨架:
```markdown
# v3 设计（针对 v2 遗留弱点，单卡可做）
v2 最弱处：密集相邻小目标"框粘连"（标准 NMS 误并）；HRSC 舰船密集排列上尤明显。
改动：① 旋转 Soft-NMS（衰减而非删除相邻框）② 检测头最高分辨率层 +1 级。
预期：密集/相邻场景召回↑、粘连↓；总 mAP 小幅↑；参数几乎不增（Soft-NMS 是后处理）。
单卡可行：✅ Soft-NMS 仅后处理无训练开销；检测头微调显存可控。
```
**③ 这一步合格的样子**:v3 改动定义清晰,对应 v2 的一个明确弱点(粘连),单卡可做,`diff` 出相对 v2 只改这两处。

**⑤ 卡住怎么自救(决策树)**:想不出 v3 改动? → 从"v2 三类定性负面案例的最大公约数"切入(本例都是密集相邻)→ 针对它找最轻的改法(能后处理就不动训练);改动一上来就很大? → 拆成"先改后处理看效果,有必要再动结构"。
**⑥ 今天(这一步)你同时学会了什么**:你延续了"针对问题迭代"并加了"收敛意识"。**做了**(v3 设计)、**学了**(从弱点设计下一版、迭代要收敛而非堆砌、能后处理就别动结构)、**会了**(基于上版不足规划单卡可做的 v3)。

## 中午段 · 实现 v3 核心改动（最小改动）

**① 先垫概念**:在 v2 基础上实现 v3 的核心改动(最小改动),跑通形状。本例两改动都很轻:Soft-NMS 是后处理(替换 NMS 调用)、检测头微调是改一处配置。**"最小改动"为什么是迭代的黄金法则**:① 改得越少,出 bug 的面越小,定位越快(v3 出问题你只需查这两处);② 改得越少,归因越干净(性能变了能确定是这两处带来的);③ 改得越少,越能复用已验证的 v2 代码(站在巨人肩膀上)。**很多人迭代时的误区**是"既然要出新版,不如多改几处一步到位"——结果一旦掉点,根本说不清是哪处的锅,只能推倒重来。正确姿势永远是"小步快跑、一次一处、跑通即提交"。本例两改动一个是纯后处理(零训练成本)、一个是单点配置改动,正是"最小改动"的典范。
**② 手把手带做**:实现 v3 改动(只动这两处),dummy 跑通。旋转 Soft-NMS 核心:
```python
# 旋转 Soft-NMS：不直接删相邻框，按旋转 IoU 衰减其得分（密集场景少漏）
import torch
def rotated_soft_nms(boxes, scores, sigma=0.5, score_thr=0.05):
    boxes, scores = boxes.clone(), scores.clone()
    keep = []
    idx = scores.argsort(descending=True)
    while idx.numel() > 0:
        i = idx[0]; keep.append(i.item())
        if idx.numel() == 1: break
        rest = idx[1:]
        ious = rotated_iou(boxes[i:i+1], boxes[rest]).squeeze(0)   # 与最高分框的旋转IoU
        decay = torch.exp(-(ious ** 2) / sigma)                    # 高斯衰减（重叠越大衰减越多）
        scores[rest] = scores[rest] * decay                        # 衰减而非删除
        rest = rest[scores[rest] > score_thr]                      # 衰减后过低才丢
        idx = rest[scores[rest].argsort(descending=True)]
    return torch.tensor(keep)
```
**③ 合格样例**:v3 实现、`forward`/后处理跑通形状正确(与 v2 同接口),dummy 输入不报错。
**④ 坑**:① 一次改多处 → 只动这两处;② Soft-NMS 衰减太狠(sigma 太小)→ 把高分相邻框也压没了,反而掉点。
**⑤ 自救**:粘连没改善 → 调 sigma(大一点衰减更温和);实现拿不准 → 先在几张密集图上单独跑 Soft-NMS 看框,确认"相邻框被保留而非误并"。
**⑥ 今天(这一步)你同时学会了什么**:你实现了 v3 的轻量针对性改动。**做了**(v3 实现)、**学了**(后处理级改动、Soft-NMS 原理)、**会了**(在 v2 上做最小改动实现 v3)。

## 晚上段 · 启动 v3 训练（可比设置）

**① 先垫概念**:用 v3 config 启动训练(固定 seed,设置和 v2 可比,只差 v3 改动);监控。检测头微调要重训,Soft-NMS 只在推理生效。**为什么要区分"训练改动"和"推理改动"**:v3 的两个改动性质不同——检测头微调改了网络结构,必须重新训练才能让新参数学到东西;而 Soft-NMS 只是后处理(把模型输出的框做非极大值抑制时换个策略),不涉及训练,同一份权重换 NMS 策略重新推理即可。理解这个区分能帮你省大量算力:推理改动可以"训练一次、推理时反复试不同 NMS 超参",而训练改动每改一次都要重训几小时。**所以启动时**:config 里只让检测头微调进入训练流程,Soft-NMS 的超参(sigma)留到推理/评估时再扫。

**⑤ 自救**:OOM → batch 减半;loss 异常 → 先确认检测头改动接进了前向(权重置零验证)。

## 上午段 · v3 结果分析 + 改进

**① 先垫概念**:v3 训完,分析 vs v2(是否提升、哪类提升——尤其密集/相邻);若有小问题(如某 sigma 下仍有粘连),微调改进。延续"看针对场景 + 看总指标"两层判断。**这"两层判断"是评估针对性改进的核心方法**:① 第一层看**总指标**(整体有没有变好/变差,守住底线——针对性改进至少不能把总指标拖下去);② 第二层看**针对场景**(它瞄准的那部分——密集/相邻——有没有明显改善,这才是它的价值所在)。一个理想的针对性改进是"总指标持平或微涨 + 针对场景明显改善",说明它精准地补了短板而没伤其他。**为什么不能只看一层**:只看总指标会埋没"总指标小涨但密集场景大涨"的好改进;只看针对场景会漏掉"密集场景涨了但把其他场景搞坏了"的副作用。两层一起看,才能对一个改进下公允的结论。

```python
# 推理超参（Soft-NMS）无需重训，对同一份权重快速扫几组 sigma
for sigma in [0.3, 0.5, 0.7]:
```

## 中午段 · 调参（v3 训练超参的适度调优）

## 中午段 · 消融结果

**① 先垫概念**:评估消融,看最终版本每个新组件的贡献(Δ vs 完整 + 显著性),延续 W12 的解读方法。**消融结果有三种典型情形,对应三种处理**:① 组件贡献大且显著(如多尺度 -1.7)→ 这是方法的核心,论文重点讲;② 组件贡献小但在"针对场景"显著(如 Soft-NMS 总指标 -0.5 但密集场景明显)→ 保留并注明适用场景,别因总指标小就删;③ 组件贡献在噪声内(如检测头微调 -0.4,std≈0.3,临界)→ 认真考虑删掉,因为"删了性能基本不变"意味着它没必要存在,而更简洁的方法更优雅、更快、更契合你的高效卖点。**这里有个反直觉但重要的点**:发现自己加的某个组件没用、果断删掉,不是失败,而是成熟——审稿人欣赏"方法简洁、每个组件都有据"的论文,讨厌"堆了一堆说不清作用的模块"的论文。**消融的终极目的**就是帮你判断"哪些该留、哪些该删",留下一个干净、每块都有用的最终方法。

## 三、版本决策矩阵 + 参数/FPS 测量 + 实验进度看板（完整代码）
```python
import numpy as np, torch, time

# ① 版本决策矩阵：用 3 数据集均值 + 效率 + 复杂度，量化"主推 v3 还是回退 v2"
def decide_version(table, params, fps):
    """table={方法:{数据集:[seeds]}}, params/fps={方法:数值}。综合打分给建议。"""
    methods = list(table.keys())
    avg = {m: np.mean([np.mean(v) for v in table[m].values()]) for m in methods}  # 跨数据集均值
    print(f"{'方法':<8}{'3数据集均值':<12}{'参数(M)':<10}{'FPS':<8}")
    for m in methods:
        print(f"{m:<8}{avg[m]:<12.2f}{params[m]:<10}{fps[m]:<8}")
    best_acc = max(methods, key=lambda m: avg[m])
    # 决策规则：若 v3 均值 >= v2 且效率不差太多 → v3；若 v3 仅微优(<0.2)却更慢 → 回退 v2
    if "v3" in avg and "v2" in avg:
        gain = avg["v3"] - avg["v2"]
        slower = fps["v2"] - fps.get("v3", fps["v2"])
        if gain >= 0.2: print(f"→ 建议主推 v3（均值 +{gain:.2f}）")
        elif gain > 0 and slower > 2: print(f"→ v3 仅 +{gain:.2f} 却慢 {slower} FPS，建议回退 v2（简洁高效）")
        else: print(f"→ 主推综合最优：{best_acc}")
    return avg

# ② 参数量 + FPS 测量（复用 W11，主表"效率列"的数据来源）
def count_params(model): return sum(p.numel() for p in model.parameters())/1e6
@torch.no_grad()
def measure_fps(model, size=1024, warmup=10, runs=50):
    model.eval().cuda(); x=torch.randn(1,3,size,size).cuda()
    for _ in range(warmup): model(x)
    torch.cuda.synchronize(); t0=time.time()
    for _ in range(runs): model(x)
    torch.cuda.synchronize(); return runs/(time.time()-t0)

if __name__ == "__main__":
    decide_version(
        {"v2":{"A":[77.2],"B":[69.1],"C":[71.8]}, "v3":{"A":[78.1],"B":[69.4],"C":[72.6]}},
        params={"v2":38,"v3":38}, fps={"v2":22,"v3":22})
```
**用法**:① 大表数据齐了,`decide_version` 把"主推哪版"从拍脑袋变成有规则的量化建议;② `count_params/measure_fps` 产出主表的效率列(固定尺寸、预热后测,保证可比)。
