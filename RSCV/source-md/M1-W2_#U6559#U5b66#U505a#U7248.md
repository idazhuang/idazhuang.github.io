## 上午段 · 精读 Oriented R-CNN(Xie et al. 2021, ICCV)
**① 先垫概念**:
- **方法论文**:核心是"**它提出了什么新东西、为什么比前人好**"。读它你要能回答:它解决了旋转检测里的哪个具体痛点?用什么招?
- **两阶段检测器(two-stage)**:先"**生成候选框(proposal)**"(可能有目标的区域),再"**对候选框做精细分类+回归**"。Oriented R-CNN 属于这一类,它的创新在于**高效地生成"旋转候选框"**。
- **一阶段 vs 两阶段(这个范式对比要刻进脑子)**:**一阶段**(如 YOLO 系)直接在特征图上预测框,**快但通常精度略低**;**两阶段**先选候选区再精修,**准但通常慢一些**。遥感旋转检测里两类都有人做。理解这个权衡,你看任何检测论文都能先归位它属于哪类、为什么这么选。
- **RoI(Region of Interest)**:候选框框出的那块特征区域。旋转检测里是 **Rotated RoI**(旋转的候选区)。把候选框对应的特征"抠"出来送进第二阶段精修——这个"抠特征"的操作(RoI Align/旋转 RoI Align)是两阶段检测的关键零件。
- **为什么从 Oriented R-CNN 开篇**:它是空天院孙显组的代表作、社区复现成熟、在 DOTA 上是强 baseline——既是你第一个要跑通的实验,也是你后续改进(M3–M4 加自己的组件)的基座。读懂它,等于读懂了"两阶段旋转检测器"这一整类。
**② 带做**:精读 3 遍(综述/方法/应用对应 5/3/2 遍,这是方法论文→3 遍)。第 1 遍 标题+摘要+Fig1+Tab1;第 2 遍 Intro+Conclusion;第 3 遍 Section 3 Method,**死磕一件事:它的"旋转 RoI/旋转 proposal"是怎么生成的**。笔记第 2 段用**一句话+一个手画 pipeline** 说清它的招数。
**③ 合格样例**:`2021_Xie_OrientedRCNN.md`,第 2 段能讲清"它怎么又快又准地产生旋转候选框",并标注"它比前人(如 RoI Transformer)省在哪"。
**④ 坑**:陷入数学公式细节出不来——第一遍抓"**思想/流程**"就行,公式 D9 对比时再深究。
**⑤ 卡住**:看不懂 Method → 去看它的 Fig 2/3(方法流程图),遥感/CV 方法论文的图就是"方法的说明书",看图顺序跟着箭头走。
**⑥ 同时学会了什么**:你学会了**读方法论文的姿势**(抓核心创新+画出 pipeline+对比前人),并理解了"两阶段检测+RoI"这个 CV 基础范式。

## 中午段 · 打开 MMRotate 源码,逐行读 Oriented R-CNN 的 config
**① 先垫概念**:
- **config(配置文件)**:MM 系列把"用什么模型、什么数据、怎么训"全写在一个 `.py` 配置里。**读懂 config = 读懂整个实验设置**,这是复现的核心技能。
- config 的五大块(对应你昨天读论文学的概念):**backbone**(主干,提特征,如 ResNet-50)、**neck**(脖子,多尺度特征融合,如 FPN)、**head**(头,做最终的检测预测)、**loss**(损失函数,告诉模型"错多少")、**schedule**(训练计划:学习率、训多少轮)。
**② 带做**:打开 `configs/oriented_rcnn/` 下的配置文件,**逐行读注释**。对照上面五大块,在 `20-代码实验/config注释_OrientedRCNN.md` 里写下:这个实验用的 backbone / neck / head / loss / 学习率 / batch_size / 训练轮数分别是什么。读 config 时对照这张"五大块地图":
```python
# Oriented R-CNN config 的五大块（简化示意，真实 config 会用 _base_ 继承拆开）
model = dict(
    type='OrientedRCNN',
    backbone=dict(type='ResNet', depth=50, ...),        # ① 主干：提特征
    neck=dict(type='FPN', in_channels=[256,512,1024,2048], ...),  # ② 脖子：多尺度融合
    rpn_head=dict(type='OrientedRPNHead', ...),          # ③ 头(第一阶段)：产生旋转proposal
    roi_head=dict(type='OrientedStandardRoIHead', ...),  # ③ 头(第二阶段)：精分类+回归
    train_cfg=..., test_cfg=...)                          # 训练/测试的匹配、NMS 等
# 数据块
dataset_type='DOTADataset'
data_root='/abs/path/to/split_dota/'                     # ← 改成你切好图的绝对路径
data=dict(samples_per_gpu=2, ...)                        # ← samples_per_gpu 就是 batch_size
# schedule 块
optimizer=dict(type='SGD', lr=0.0025, momentum=0.9, weight_decay=1e-4)  # ④ 学习率/优化器
runner=dict(type='EpochBasedRunner', max_epochs=12)      # ⑤ 训多少轮(1×=12)
```
对照这个,把真实 config 里对应的值抄进你的注释文档(注意真实值可能分散在 `_base_` 继承的多个文件里)。
**③ 合格样例**:一份注释文档,能指着 config 说出"它用 ResNet-50 + FPN,SGD,lr=0.005,12 epochs"这种级别的信息。
**④ 坑**:被 `_base_ = [...]`(继承的基类配置)绕晕——MM 的 config 会**继承**其他文件。顺着 `_base_` 进去看被继承的部分,它们合起来才是完整配置。
**⑤ 卡住**:某参数不知含义 → 先记进文档标"待查",大部分参数 D9–D11 跑起来后你会自然懂;关键的(backbone/lr/epoch)务必搞清。
**⑥ 同时学会了什么**:你掌握了**"读 config 反推实验设置"**这把万能钥匙——以后复现任何 MM 系列代码,第一步都是读它的 config。

## 晚上段 · 准备训练 config + 改 batch_size 适配 4090 + dry-run
**① 先垫概念**:
- **dry-run(试运行)**:正式开跑前,**先只跑 1 个 epoch / 几十个 iteration**,确认"能正常训练、不报错",再投入几小时正式训练。这是避免"跑了 3 小时才发现路径写错"的保命操作。
- **batch_size(批大小)**:一次喂给模型几张图。**越大越稳但越吃显存**。你是 **4090(24GB)**,Oriented R-CNN + ResNet-50 通常能开 `batch_size=2`(甚至更高),比 12GB 卡宽裕得多——这是你硬件的优势。
- **dry-run 是一种"先排雷再投入"的科研习惯**:训练动辄几小时,如果路径、显存、标签有问题,等几小时崩了再发现,时间全浪费。先用 1 epoch/几十 iter 快速验证"链路通不通",通了再正式投入——这个习惯能帮你省下大量"白等"的时间,以后每个新实验都该先 dry-run。
- **把单卡 4090 写成你的"卖点"而非"短板"**:你只有一张卡,看似不如实验室的多卡集群,但**这恰恰是你论文的差异化定位**——"在单张消费级 GPU 上实现 X"本身就是高效性的证明。从第一个实验起就记录"我用单张 4090、batch_size=2、训练耗时 X 小时",这些数字以后会变成你论文里 Params/FPS/单卡可复现的卖点。**资源受限不是借口,是你的特色。**
**② 带做**:复制一份 config 改成你的:① 改数据路径指向你下载/切好的 DOTA;② `batch_size` 先设 2(4090 够);③ 跑一次 dry-run(把 epoch 临时设 1,或只跑几十 iter)看能否正常前进。
```bash
# ① 复制一份你自己的 config（别改官方原文件）
cp configs/oriented_rcnn/oriented_rcnn_r50_fpn_1x_dota_le90.py configs/my_orcnn_r50.py
# ② 在 my_orcnn_r50.py 里改两处：data_root 指向切好图的绝对路径；samples_per_gpu=2
# ③ dry-run：单卡、训练（先把 max_epochs 临时设 1 或 Ctrl+C 看前几十 iter 是否正常）
python tools/train.py configs/my_orcnn_r50.py
# 观察终端：应持续打印 loss（有限数、在变化），无报错 → 数据通了、模型能训
nvidia-smi          # 另开一个终端，确认 4090 显存被占用、GPU 利用率不为 0
```
**③ 合格样例**:dry-run 时终端持续打印 loss(且是有限数、在变化),无报错——截图存证。这说明数据通了、模型能训。
**④ 坑**:① 直接开正式训练不 dry-run → 几小时后才暴雷;② batch_size 设太大爆显存(`CUDA out of memory`);③ 数据路径用了相对路径在后台跑时找不到。
**⑤ 卡住自救(决策树)**:
- `CUDA out of memory` → 把 batch_size 降到 1;仍不行→减小输入分辨率或开混合精度(fp16)。
- loss 打印出 `nan` → 学习率太大,先按"batch_size 减半则 lr 减半"的线性原则调小 lr。
- 报"找不到标注/图片" → 路径错,用**绝对路径**,并确认 DOTA 已按需要切过图(明天 D9 做)。
**⑥ 今天(这一步)你同时学会了什么**:你学会了**"改 config 适配自己硬件 + 用 dry-run 排雷"**——这是复现别人代码时最实用的两招,能帮你省下大量"跑半天才发现错"的时间。**做了**(可训练的 config + dry-run 通过)、**学了**(config 五大块、batch_size 与显存关系、dry-run 的意义)、**会了**(改路径/batch_size、读懂 OOM/nan 报错并对症)。

> **技能卡｜复现一份 MM 代码的开局四步**:① 读 config(反推实验设置)→ ② 改数据路径 + batch_size 适配你的 GPU → ③ dry-run 1 epoch 排雷 → ④ 确认 loss 正常再正式开训。

> **今日交付物**:✅ Oriented R-CNN 笔记 ✅ config 注释文档 ✅ dry-run 成功截图。

## 中午段 · 运行 DOTA 切图工具(理解"为什么切"+ overlap 的作用)
**① 先垫概念**:
- **为什么切图(image split)**:DOTA 原图常 2000×4000+,**整张塞进 GPU 既爆显存又让小目标更小**。所以把大图切成 1024×1024 的小块(patch)再训练。这是遥感检测**特有的工程步骤**,通用 CV(图本就小)不需要。
- **overlap(重叠)**:切块时让相邻块**重叠一部分**(如 200 像素),避免一个目标正好被切在边界上、两块都只看到半个。
- **为什么这是遥感"特有"的坑**:通用 CV 数据集(COCO)的图本来就几百像素、目标占比也合适,直接喂就行;遥感是"超大图 + 超小目标"的极端组合,不切图根本训不了。**这个差异是你理解"遥感 CV 难在哪"的一个具体切口**——很多遥感特有的设计都源于"图太大、目标太小、还任意朝向"。
- **切图带来的新问题(也是你未来可做的点)**:切块会**割裂大目标**(一座桥被切到两块),也会让模型**看不到全局上下文**;推理时还要把各块的预测**拼回原图**并去重。这些都是遥感检测的工程难点,记下来——它们既是你现在要正确处理的,也可能是未来论文里可以改进的地方(如何更好地处理跨块目标)。
**② 带做**:运行 MMRotate 的切图脚本 `tools/data/dota/split/img_split.py`(参数照官方文档),把 train/val 切成 1024×1024、overlap 200 的 patch。切完看一眼输出目录的图和标注。
```bash

    --base-json tools/data/dota/split/split_configs/ss_trainval.json
# ss = single-scale 单尺度切图；配置 json 里指定了 patch 尺寸(1024)、gap(200=overlap)、
#      输入 DOTA 目录、输出目录。改 json 里的路径指向你的 DOTA。
# 切完：输出目录是一堆 1024×1024 小图 + 切好的标注；用 D6 的 vis_dota.py 抽查一张确认框还对
```
**③ 合格样例**:得到一堆 1024×1024 的小图 + 对应切好的标注;随手用你 D6 的 `vis_dota.py` 可视化一张切块,框仍然对。
**④ 坑**:① 忘了切图直接拿原图训→OOM 或效果差;② overlap 设 0→边界目标被切碎,掉点;③ 切完没更新 config 里的数据路径(要指向切后的目录)。
**⑤ 卡住**:切图脚本报错 → 多半是输入/输出路径或 DOTA 目录结构不符脚本预期,对照官方文档的目录结构摆好。
**⑥ 同时学会了什么**:你理解了**遥感大图必须切块训练**这一关键工程常识,以及 overlap 的设计动机——这在你后面所有遥感检测/分割实验里都会用到。

# D10 周三 · 读 ReDet + 学会"看训练健不健康"(TensorBoard / loss 曲线)

> 你的训练昨晚在跑。今天的核心新技能是:**怎么判断"训练是健康的还是出问题了"**——看 loss 曲线、学习率曲线、mAP 曲线。这是每个炼丹师的基本功。

> **预期管理**:今天学"看曲线诊断训练健康度",这是会跟随你整个博士生涯的基本功。提醒:loss 会上下抖动是正常的(看趋势不看单点);如果发现 loss 不降或变 nan,别慌——那说明你学会了"诊断",下面的决策树会带你定位是 lr、数据还是标签的问题。

## 上午段 · 精读 ReDet(Han et al. 2021, CVPR)——旋转等变网络
**① 概念**:**旋转等变(rotation-equivariant)**——直觉:遥感目标朝向随机,如果网络"图转了多少度、特征也跟着转多少度",就天然对朝向鲁棒。ReDet 把这种"等变性"设计进网络。理解"**为什么旋转等变对遥感重要**"即可。
**② 带做**:精读 3 遍,笔记第 2 段答:它靠什么实现旋转等变?这相比"靠数据增强见过各种角度"好在哪?
**③ 合格样例**:能用一句话向外行解释"旋转等变"是什么、对遥感为什么有用。
**④ 坑**:陷进群卷积(group conv)的数学——抓"等变=输入转则特征同步转"的直觉即可。
**⑤ 卡住**:概念太抽象 → 类比:CNN 对"平移"天然等变(物体挪个位置照样认),ReDet 想让它对"旋转"也这样。
**⑥ 同时学会了什么**:你接触到"**把先验(目标会旋转)设计进网络结构**"这种思路——这是一类高级 idea 的来源,后面你想自己的方法时用得上。

## 中午段 · 监控训练:TensorBoard + 看懂三条曲线
**① 先垫概念**:
- **TensorBoard**:可视化训练过程的工具,能画出 loss、学习率、mAP 随训练步数的曲线。
- 三条曲线的"健康长相":**loss** 应**总体平稳下降**(可以抖,但趋势向下);**学习率** 按 schedule 变化(常见先 warmup 上升再阶梯下降);**mAP**(若每隔几 epoch 验证一次)应**逐步上升**。
- **为什么看曲线比看终端数字强**:终端滚动的数字你只能看到"此刻这一个值",看不出趋势;曲线把整个训练过程画出来,一眼就能判断"在降/在升/卡住/发散"。**这是诊断训练的核心手段**,以后每次训练都要做这个"体检"。
- **不健康的几种长相**(看到就要排查):loss **不降反升**或**长期持平**(lr 太大/数据标签有 bug);loss **突然飙到 nan/inf**(lr 太大或脏数据);loss 降但 **mAP 一直是 0**(标签/类别映射/评测路径错)。**记住这几种"病征"对应的"病因"**,下面决策树会用到。
- **学习率曲线为什么要看**:它能确认 schedule 真的按预期在跑(warmup 有没有生效、阶梯下降在第几 epoch),若 loss 在某个点突然变化,对照 lr 曲线常能解释(比如 lr 阶梯下降时 loss 跟着下一个台阶)。
**② 带做**:`tensorboard --logdir work_dirs/` 打开,浏览器看曲线。在实验日志里记下:① loss 有没有在降?② 当前到第几 epoch?③ 有没有验证 mAP、是多少?

```bash
tensorboard --logdir work_dirs/orcnn_r50 --port 6006
# 浏览器开 http://localhost:6006（远程服务器需 ssh -L 6006:localhost:6006 做端口转发）
# 没开 TensorBoard hook 也没关系：MM 的 .log.json 里有逐 iter 的 loss，可用补充包 plot_loss 画

```
**③ 合格样例**:你能指着曲线说"loss 从 X 降到 Y,在平稳下降,训练健康"。
**④ 常踩的坑**:① 只看终端数字不看曲线——**曲线一眼看出趋势,数字看不出**;② loss 抖一下就以为崩了——**正常会抖**,看趋势不看单点。
**⑤ 卡住自救(决策树)**:

**⑥ 今天(这一步)你同时学会了什么**:你学会了**"用 TensorBoard 三条曲线判断训练健康度"**——这是你以后每次训练都要做的体检。能看懂曲线,你就从"盲跑"升级成"会诊断"。**做了**(监控并记录了训练状态)、**学了**(loss/lr/mAP 曲线的健康长相)、**会了**(从曲线异常反推问题:lr/数据/标签)。

## 上午段 · 精读 Gliding Vertex(Xu et al. 2021, TPAMI)
**① 概念**:**滑动顶点(gliding vertex)**——一种"巧妙表示旋转框"的方式:在水平框的四条边上各滑出一个顶点来逼近旋转框,**避免角度回归的不连续问题**(角度从 359°→0° 会突变,让网络难学)。
**② 带做**:精读 3 遍,笔记答:它用什么方式回避了"角度回归不连续"这个坑?
**③ 合格样例**:能说清"角度突变问题"是什么、滑动顶点怎么绕开它。
**④/⑤**:不懂"角度周期性"→记住"0° 和 360° 其实是同一个朝向,但数值上差很大,直接回归角度会让网络困惑"。
**⑥ 同时学会了什么**:你接触到旋转检测里一个经典痛点(角度表示)及其多种解法——这类"表示方式"的小创新,正是"小而硬"题目的富矿。

## 中午段 · 跑评估脚本,记录 mAP
**① 先垫概念**:
- **测试/评估**:用训好的权重(`work_dirs/.../latest.pth`)在验证/测试集上跑,算出指标。
- **mAP**:所有类别 AP 的平均,检测的总分。DOTA-v1.0 上 **Oriented R-CNN + ResNet-50** 复现到 **mAP ≈ 75–76** 算正常。
- **mAP 到底在量什么**:AP(平均精度)综合衡量一个类别"查得全(召回)又查得准(精度)"的程度;一个检测算正确,要求预测框和 GT 框的 IoU 超过阈值(如 0.5)且类别对。mAP 就是把所有类别的 AP 平均。**它一个数概括了检测器的综合水平**,所以是检测的"总分"。
- **关键坑:评测协议要对齐(07 vs 12 metric)**:同一份预测,用 VOC2007 的 11 点插值还是 VOC2012 的连续积分算 AP,数值会差一两个点。**复现对比时必须用和论文/社区同一种协议**,否则"我比它低 2 个点"可能只是协议不同,不是方法差。DOTA 社区常用 07 metric。

## 晚上段 · 分析 per-class AP + 写《DOTA baseline 复现报告》
**① 先垫概念**:
- **per-class AP**:mAP 是平均分,但**不同类别难度天差地别**。看每个类别各自的 AP,能告诉你"**问题出在哪**"。比如大目标(篮球场)AP 很高、小目标(small-vehicle)AP 很低 → **小目标检测就是一个可做的研究问题**。这就是"**从数据中发现研究问题**"。
- **为什么这一步是科研最迷人的起点**:很多人以为选题靠灵感,其实更多是靠"看数据看出来的"。per-class AP 就是一面镜子,照出你的方法在哪类目标上栽跟头;那个最弱的类,往往就藏着一个具体、可做、有意义的研究问题。**你 M3 要找的 Gap,源头就在这种"看 per-class 找弱项"的训练里**。
- **怎么从弱类提炼问题**:看最弱的几类有什么**共性**——是不是都"小"(small-vehicle)?都"密集"(ship)?都"样本少"(swimming-pool)?共性指向原因,原因指向解法。比如"最弱的几类都是小而密集的目标"→ 推测"切块后小目标特征丢失"→ 解法方向"高分辨率特征/专门的小目标检测头"。
- **记录 vs 科研的分水岭**:看到 small-vehicle 弱,只写"它 AP 低"是**记录**(工程);追问"为什么低、能不能做文章"才是**科研**。今天你要练的是后者——这是研究者和调包工的核心区别。

## 晚上段 · 第一个消融:ResNet-50 → ResNet-101,重启训练
**① 先垫概念**:
- **消融实验(ablation)**:**只改一个变量、其余完全不变**,看这个变量对结果的贡献。它是科研中最基础、审稿人最看重的实验方法。**换 backbone 是最安全的入门消融**。
- **控制变量**:除了 backbone,lr/bs/epoch/数据全保持和 D9 那次**完全一致**,这样 mAP 的差异才能**干净地归因到 backbone**。
- **为什么消融是科研的硬通货**:任何"我加了 X 让性能变好"的论断,都必须用消融证明——去掉 X、其他不变,性能确实掉了,才说明 X 真有用。否则审稿人会问"你怎么知道是 X 起的作用,而不是顺便调的别的?"。**控制变量是消融的灵魂**:多改一个东西,归因就被污染,整个实验白做。
- **换 backbone 为什么最适合入门**:① 改动极小(config 里 depth 50→101 + 换预训练权重);② 因果清晰(backbone 容量变了→看 mAP 怎么变);③ 不涉及你还没设计的新模块。**这套"只改一处→干净归因"的纪律,和你 M3–M4 给自己方法的每个组件做消融,是一模一样的方法论**——现在用最简单的 backbone 练熟它。

## 晚上段 · 把 `vis_dota.py` 升级为 `vis_results.py`(画预测框 vs GT 框 + 算 IoU)
**① 先垫概念**:
- **定性分析(qualitative analysis)**:不只看数字,**看图**判断模型好坏。标准做法:同一张图上画**预测框(绿)**和**真值 GT 框(红)**,一眼看出对/错/漏。
- **GT(ground truth)**:人工标注的"标准答案"框。
- **IoU(Intersection over Union)**:预测框与 GT 框的"重叠程度"= 交集面积 / 并集面积,**0~1,越接近 1 越准**。它是判断"这个预测框算不算检测正确"的核心度量。
**② 手把手带做**:基于 D6 的脚本扩写 `20-代码实验/utils/vis_results.py`:① 读模型推理结果(MMRotate 可输出预测,存成 pkl/json);② 在图上画预测框(绿)和 GT 框(红);③ 选做:对一对框算 IoU 并标在框上。
```python
import cv2, numpy as np
# 把旋转框 (cx,cy,w,h,θ) 转成 4 个角点用于画框
def obb_to_corners(box):
    cx, cy, w, h, ang = box
    c, s = np.cos(ang), np.sin(ang)
    dx, dy = w/2, h/2
    pts = [(-dx,-dy),(dx,-dy),(dx,dy),(-dx,dy)]
    return np.array([[cx+x*c-y*s, cy+x*s+y*c] for x,y in pts], np.int32)

def draw_pred_vs_gt(img, preds, gts, out):
    for g in gts:   cv2.polylines(img,[obb_to_corners(g)],True,(0,0,255),2)   # GT 红
    for p in preds: cv2.polylines(img,[obb_to_corners(p)],True,(0,255,0),2)   # 预测 绿
    cv2.imwrite(out, img)
    # 看图：只有红没绿=漏检；只有绿没红=误检；红绿重合=检对
# 拿预测结果：tools/test.py ... --out result.pkl，再读 pkl 取每张图的框
```
**③ 合格样例**:输出图上绿框=预测、红框=GT;能直观看到"哪些目标被准确框中、哪些漏检(只有红没绿)、哪些误检(只有绿没红)"。
**④ 坑**:① 预测结果的坐标格式和 GT 不一致(都要转成 8 点角点再画);② 颜色不区分,看不出对错(务必预测/GT 不同色)。
**⑤ 卡住**:拿不到模型预测结果 → 用 `tools/test.py` 加 `--out result.pkl` 把预测存下来再读;IoU 算旋转框较复杂 → 第一次可先只画框、不算 IoU,把"对错漏"看清就达标。
**⑥ 今天(这一步)你同时学会了什么**:你做出了**第一个"定性分析"工具**,从此能"看图诊断"而不只是"看数字"。漏检/误检的可视化,正是论文里展示方法优势、也是你发现"模型在哪类目标上栽跟头"的利器。**做了**(`vis_results.py`)、**学了**(定性分析、GT、IoU)、**会了**(把预测与真值叠加可视化、用"对/错/漏"读图)。

## 二、完整可运行代码 — ① 画训练 loss 曲线 ② per-class AP 柱状图

> 配合 D10(看训练健不健康)和 D11(评估)。存 `20-代码实验/utils/plot_curves.py`:

```python
import json, matplotlib.pyplot as plt

# ① 从 MM 框架的 log（.log.json，每行一个 json）画 loss 曲线
def plot_loss(log_json_path, out="loss.png"):
    iters, losses = [], []
    with open(log_json_path) as f:
        for line in f:
            try:
                d = json.loads(line)
            except Exception:
                continue
            if d.get("mode") == "train" and "loss" in d:
                iters.append(d.get("iter", len(iters)))
                losses.append(d["loss"])
    plt.figure(); plt.plot(iters, losses)
    plt.xlabel("iter"); plt.ylabel("loss"); plt.title("Training Loss")
    plt.savefig(out, dpi=150); print("saved", out)

# ② per-class AP 柱状图（手动把评估打印的 per-class AP 填进 dict 即可）
def plot_perclass_ap(ap_dict, out="perclass_ap.png"):
    names = list(ap_dict.keys()); vals = list(ap_dict.values())
    plt.figure(figsize=(10,4)); plt.bar(names, vals)
    plt.xticks(rotation=60, ha="right"); plt.ylabel("AP"); plt.title("Per-class AP")
    plt.tight_layout(); plt.savefig(out, dpi=150); print("saved", out)

if __name__ == "__main__":
    # plot_loss("work_dirs/oriented_rcnn_r50/20240101_000000.log.json")
    plot_perclass_ap({"plane":89.1, "small-vehicle":58.4, "ship":72.0, "swimming-pool":51.2})
```
**预期**:`loss.png` 是一条总体下降(有波动正常)的曲线;`perclass_ap.png` 一眼看出哪类最低(就是你要攻的弱类)。

## 五、本周报错速查表

| 现象 | 根因 | 解法 |
|---|---|---|
| 训练 OOM(显存爆) | batch_size/分辨率过大 | 降 bs(4090 旋检常用 bs=2)、关部分增强、或用梯度累积 |
| 训练 loss=NaN | lr 太大 / 数据有脏标注 | 降 lr;检查切图后有无空标注/越界框 |
| 评估 mAP=0 或极低 | 评估标注路径/类别名配错 | 核对 config 里 data root 与类别列表;确认评测协议(07/12 metric) |
| dry-run 就报错 | config 路径/版本不匹配 | 先跑通官方 demo,再在其 config 上最小改动 |
| 切图后目标被切碎 | overlap 太小 | 增大 overlap(如 200),保留跨边界目标 |
| 训练极慢 | num_workers 太小/没用 GPU | 调大 num_workers;确认模型 `.cuda()`、`nvidia-smi` 有占用 |
