# D134 周一 · Method 章定稿（基于最终方法）

> 今天把 Method 据"删/调之后的最终方法"对齐——确保论文里写的方法,和你代码里跑的方法,**一个字都不差**。
>
> **预期管理**:M5 收官周开始,本周把实验成果写成论文两大主干章。今天先让 Method 与最终代码严格对齐。提醒:写作的第一关不是英语,是"让没见过你工作的人读完能复现你的方法、能信你的结论";Method 要"既说是什么、更说为什么"(只有公式没有直觉=读者看不懂);以**最终 config/代码为事实来源**,代码里没有的组件论文里也不能有(否则审稿人对照代码会抓不一致)。

## 上午段 · 更新 Method 章骨架(基于最终方法)

**① 先垫概念**:阶段一(M4-W15)写的 Method 骨架基于的是**早期方法**;经过 M5 的迭代和消融,你的方法**变了**(删了无效组件、可能换了 loss/结构)。所以要**据最终方法逐节更新**——把"代码里已经没有的组件"从 Method 删掉,把"新增/保留的组件"写准。**类比**:这就像产品发布前最后核对说明书——说明书必须描述**实际发货的那台机器**,不能还写着已砍掉的功能。
- **为什么"文码不一致"是必须清除的隐患**:你的方法从M4到M5经历了大改(W19删了无效组件、可能调了loss)——如果Method还停留在早期版本(描述着已删的组件),就出现了"论文说的方法"和"代码跑的方法"不一致。**审稿人(尤其会复现的)对照你的代码/补充材料,一眼就能发现"论文写了组件C但代码里没有"——这是硬伤,直接质疑你论文的可信度**(连自己的方法都没描述对?)。所以M5收官第一件事,就是让Method和最终代码字字对应。
- **"config是事实来源"这个原则(操作铁律)**:更新Method时,**以最终方法的config/代码为唯一的"事实来源(single source of truth)"**——config里有的组件,才写进Method;Method里写了但config里没有的,删掉。不要凭记忆或凭"我当初是这么设计的"来写,因为方法经过消融已经变了。**打开最终config,逐个组件对照Method,核对每一项**:config有这个组件吗?Method写对了吗?超参一致吗?这种"以代码为准、逐项核对"是保证文码一致最可靠的方法。
- **"产品说明书"类比为什么贴切**:产品发布前,说明书必须描述**实际发货的那台机器**——如果工程上砍掉了某个功能,说明书也必须删掉对应描述,否则用户照着说明书操作会发现"咦,没有这个功能?"。你的Method就是方法的"说明书",必须描述**最终实际跑的那个方法**。消融砍掉了某组件,Method也要砍掉对应描述。读者(用户)照着Method复现,得到的应该就是你最终方法的结果。**说明书与实物一致,是基本的诚信和严谨**。
**② 手把手带做**
1. 打开最终方法的代码,逐个组件对照 Method 骨架。
2. 标出要改的:删掉已删组件的描述、补上新组件、修正公式/步骤。
3. 列一个"Method↔代码 对照清单"(每个组件:代码里有吗?Method 里写对了吗?)。
**③ 合格样例**:Method 骨架与最终方法一致——没有"代码里不存在的组件",也没有"代码里有但 Method 漏写的"。
**④ 常踩的坑**
- **Method 还描述着已删组件** → 审稿人对照代码会发现不一致,直接质疑。**逐个核对删掉**。
- **新组件没写进 Method** → 读者无法复现。
- **改了方法没同步公式** → 公式和文字打架。
**⑤ 卡住自救(决策树)**:不确定哪些要改?→ 拿最终 config 当"事实来源",config 里有的组件才写进 Method;Method 写了 config 没有的 → 删。
**⑥ 今天(这一步)你同时学会了什么**:你学会**让 Method 与最终代码严格对齐**。**做了**(Method 骨架更新 + 对照清单)、**学了**(文与码一致、config 是事实来源)、**会了**(据最终方法更新论文描述)。

> **技能卡｜文码一致**:以"最终 config / 代码"为事实来源——Method 里写的每个组件、每个超参,都要能在代码里找到对应;代码里没有的,论文里也不能有。

## 晚上段 · 写 Method 章最终版(过检查清单)

**① 先垫概念(Method 检查清单——背下来)**:① 所有符号在**首次出现时定义**;② 公式与文字描述一致;③ 架构图与文字一致;④ 伪代码与实际代码逻辑一致;⑤ **每个设计都有"为什么这么做"的直觉解释**(不只是"是什么")。第⑤条是最常缺、也最致命的——只有公式没有直觉,读者看不出你的洞察。
- **为什么"只有公式没有直觉"是 Method 章最致命的毛病**:很多新手写 Method 就是堆公式和模块描述——"我们用了一个注意力模块,公式如下…我们又加了一个融合层,公式如下…"。读者读完只知道"你做了什么操作",但**完全不知道"你为什么这么做、它解决了什么问题、你的洞察是什么"**。这样的 Method 读起来像一份操作手册,显不出研究价值。审稿人会想"这就是随便堆了些模块吧?"。**真正好的 Method,每个设计都先讲直觉("现有方法在密集小目标上漏检,是因为下采样丢了小目标特征,所以我们设计了一个保留高分辨率特征的分支"),再给公式(严谨化)**——直觉让读者理解你的洞察,公式让方法可复现。两者缺一不可,而新手最常缺直觉。
- **"直觉+公式+图里位置"三件套(每个组件都要齐)**:写每个组件时,确保三样都有——① **直觉**(为什么需要它、它治什么问题,用大白话讲清);② **公式**(精确的数学表达,让人能实现);③ **在架构图里的位置**(读者能在 Figure 2 里找到它)。三者配合:直觉给理解、公式给严谨、图给定位。检查 Method 时,逐个组件问"这三样齐了吗?"——尤其别漏了直觉。
- **"符号首次出现就定义"为什么重要**:读者读到一个符号(如 F、α、L_aux)却不知道它是什么,就读不下去、也无法复现。**每个符号第一次出现时就要定义**(如"记输入特征为 F∈ℝ^{C×H×W},其中 C/H/W 分别为通道数/高/宽")。这是数学写作的基本规范,缺了它论文就不严谨、不可复现。检查时过一遍所有符号,确保每个都在首次出现处有定义。
- **检验 Method 的终极标准:"陌生读者能复现吗"**:写完/检查 Method 时,假装自己是"一个懂 CV 但完全没见过你这个工作的人"在读——**他能照着你的 Method 把方法实现出来吗?**能,说明 Method 写得清楚完整;如果他会卡在某处(某个细节没说清、某个符号没定义、某个设计不知道为什么),那里就是要补的。这个"陌生读者复现"标准,贯穿你以后写的所有方法描述。
**② 手把手带做**
1. 通读/打磨 Method 最终版,**逐条**过上面 5 项检查。
2. 每个组件确保有"直觉(为什么)+ 公式(严谨)+ 在图里的位置"。
3. 符号第一次出现就定义(如 "记输入特征为 F∈ℝ^{C×H×W}")。
**③ 合格样例**:Method 章最终稿,5 项检查全过——尤其每个组件都说清了"为什么用它"。
**④ 常踩的坑**
- **只写"是什么"不写"为什么"** → 读者看不出洞察,显得像堆模块。**每个组件补一句"它解决了 XX 问题"**。
- **符号没定义就用** → 无法复现。
- **公式和文字不一致** → 审稿人扣分。
**⑤ 卡住自救**:某处吃不准?→ 假装"一个懂 CV 但不懂你工作的人"在读,他能照着实现吗?不能就补细节。直觉说不清?→ 回到"这个组件治哪个 Gap/哪类失败案例"。
**⑥ 今天(这一步)你同时学会了什么**:你**定稿了 Method 章并过了检查清单**。**做了**(Method 最终稿)、**学了**(Method 5 项检查清单、直觉+公式+图三件套)、**会了**(把一章打磨到"读者能复现")。

> **技能卡｜Method 检查清单**:①符号首次定义 ②公式↔文字一致 ③图↔文字一致 ④伪代码↔代码一致 ⑤每个设计有"为什么"。逐条过,缺一补一。

## 上午段 · 写 Algorithm 1 伪代码最终版

**① 先垫概念**:**Algorithm 1**(伪代码)把训练/推理流程**精确而简洁**地写出来(≤20 行),让读者快速理解整体流程、也极大帮助复现。**类比**:它是方法的"菜谱步骤"——食材(输入)、步骤(各步)、成品(输出),照着能做出来。要和实际代码逻辑一致。
- **为什么伪代码对复现极有帮助**:正文的文字描述方法,容易分散在各处、读者拼不出完整流程;而Algorithm 1把"输入→各步骤→输出"的**完整流程浓缩在一个框里**,读者一眼看清"先做什么、再做什么、怎么算loss、怎么更新"。**对想复现你工作的人,伪代码是最直接的指南**——他照着伪代码的步骤,配合正文的细节,就能实现。所以好的论文几乎都有Algorithm 1,它是Method的"流程图"。
- **"菜谱步骤"类比为什么贴切**:菜谱不会把每个动作的细节都写(如"手腕以45度角翻炒"),而是写**关键步骤**:"① 热油 ② 下葱姜爆香 ③ 下主料翻炒 ④ 加调料 ⑤ 收汁出锅"——照着能做出菜。伪代码也一样:写**主流程的关键步骤**(前向→算loss→反向→更新),而非把每个张量操作都写进去。读者照着伪代码的步骤,就能实现你的方法,就像照菜谱能做出菜。
- **"≤20行、抓主流程"的分寸(易踩坑)**:伪代码最常见的毛病是**太长太细**——把代码几乎抄了一遍(每个层、每个操作都写)。这就失去了伪代码"简洁概览"的意义,读者反而被淹没在细节里。**正确的粒度是"懂CV的人看着能实现"**:写主流程骨架(数据→前向→loss→反向→更新),把繁琐的细节(具体的张量维度变换、辅助操作)留给正文文字或代码。控制在≤20行,逼自己只留主干。如果发现写不下,就是塞了太多细节,该把细节移到正文。
- **伪代码要和代码逻辑一致(别对不上)**:Algorithm 1描述的流程必须和你实际代码的逻辑一致——写完伪代码,对照代码的训练循环核对:步骤顺序对吗?算loss的方式对吗?有没有漏掉关键步骤或多写了不存在的步骤?**伪代码和代码不一致,会误导复现者**。这也是M5收官"文码一致"的一部分:不只Method文字、伪代码也要和最终代码对齐。
**② 手把手带做**
1. 写 Algorithm 1:Input(数据/超参)→ 各步(前向/算 loss/反向/更新)→ Output(训练好的模型)。
2. 控制在 ≤20 行,抓主流程(别把每个细节都塞进去)。
3. 对照代码核对逻辑一致。
```latex
% Algorithm 1 骨架（LaTeX algorithm2e/algorithmic 包），抓主流程、≤20行
\begin{algorithm}
\caption{Training of Our Method}
\KwIn{训练集 $\mathcal{D}$, 学习率 $\eta$, 轮数 $E$}
\KwOut{训练好的模型参数 $\theta$}
初始化 $\theta$（backbone 用预训练权重）\;
\For{$e = 1$ \KwTo $E$}{
  \ForEach{batch $(x, y) \in \mathcal{D}$}{
    $F \leftarrow \text{Backbone}(x)$\;          % 提特征
    $F' \leftarrow \text{OurModule}(F)$\;          % 你的创新组件（标红/重点）
    $\hat{y} \leftarrow \text{Head}(F')$\;
    $\mathcal{L} \leftarrow \mathcal{L}_{\text{our}}(\hat{y}, y)$\;  % 你的损失
    $\theta \leftarrow \theta - \eta \nabla_\theta \mathcal{L}$\;    % 反向+更新
  }
}
\Return $\theta$\;
\end{algorithm}
% 要点：只留主流程（前向→loss→反向→更新），细节移到正文文字；与代码 forward 一致
```
**③ 合格样例**:Algorithm 1(≤20 行,输入/步骤/输出清晰,与代码一致)。
**④ 常踩的坑**:伪代码太长太细(像把代码抄一遍)→ 抓主流程;和代码逻辑不符 → 对齐。
**⑤ 卡住自救**:不知写多细?→ 写到"懂 CV 的人看着能实现"的粒度;太长?→ 把细节移到正文文字,伪代码只留骨架。
**⑥ 今天(这一步)你同时学会了什么**:你写了最终伪代码。**做了**(Algorithm 1)、**学了**(简洁伪代码=菜谱步骤、≤20 行)、**会了**(用伪代码精确表达流程)。

## 中午段 · 找朋友互审 Method 章

**① 先垫概念**:Method 互审的**灵魂问题**只有一个——"**读完你能实现我的方法吗?**" 能→Method 合格;不能→他卡在哪、哪里缺细节,那就是你要补的地方。**外部视角**能发现你"太熟而脑补"的盲点。
- **为什么"自己读不出问题、别人一读就卡"**:你对自己的方法太熟了,读Method时会**不自觉地脑补缺失的细节**——某个步骤你没写清,但你心里知道怎么做,读的时候自动补上了,所以觉得"写得挺清楚"。**但陌生读者没有你脑子里的背景,你没写的他就不知道,立刻卡住**。这就是"当局者迷"——你是最不适合检验自己Method清晰度的人。所以必须找外部视角(朋友/同行)来读,他卡住的地方,就是你"以为写了其实没写清"的盲点。
- **"能否实现"是检验Method的唯一标准**:Method写得好不好,不看辞藻、不看长短,只看**一个懂CV但没见过你工作的人,读完能不能照着实现**。能,说明信息完整、表述清楚;不能(他在某处卡住、不知道怎么做),那里就缺了关键信息。所以互审时,明确请朋友以"我要照着实现"的心态读,并问他"哪里看不懂、哪里缺细节、能实现吗"——他的卡点就是你的待补清单。
**② 手把手带做**
1. 把 Method 章 + Algorithm 1 发给朋友(同领域更佳)。
2. 明确问:"能照着实现吗?哪里看不懂/缺细节?"

## 二、实用工具 — 大表转 LaTeX + 两章一致性自检
```python
import numpy as np, re
# ① 整合大表 → LaTeX tabular(最优自动加粗)
def to_latex(data, datasets):    # data={"method":{"D1":mean,...}}
    best = {d: max(data[m][d] for m in data) for d in datasets}
    print("\\begin{tabular}{l|" + "c"*len(datasets) + "}\n\\toprule")
    print("Method & " + " & ".join(datasets) + " \\\\ \\midrule")
    for m, dd in data.items():
        cells = []
        for d in datasets:
            v = f"{dd[d]:.1f}"
            if abs(dd[d]-best[d]) < 1e-6: v = "\\textbf{"+v+"}"
            cells.append(v)
        print(f"{m} & " + " & ".join(cells) + " \\\\")
    print("\\bottomrule\n\\end{tabular}")

# ② 两章一致性:抽取关键设置词供人工比对
def extract_terms(md_path):
    t = open(md_path, encoding="utf-8").read()
    return set(re.findall(r'(lr=\S+|bs=\d+|\d+\s*epochs?|[A-Z][A-Za-z]*Loss)', t))
if __name__ == "__main__":
    to_latex({"baseline1":{"D1":75.0,"D2":67.0,"D3":70.0},"Ours":{"D1":78.1,"D2":69.4,"D3":72.6}}, ["D1","D2","D3"])
```
**预期**:① 输出可直接编译的 LaTeX 主表(最优加粗);② 抽取两章关键设置词供比对一致性。

## 四、本周写作坑速查表
| 现象 | 根因 | 解法 |
|---|---|---|
| Method 写了代码没有的组件 | 没据最终方法更新 | 以最终 config 为事实来源,删/补 |
| 别人无法复现实验 | 实现细节缺失 | 写全数据集/超参/硬件(正文或 supp) |
| 结果只报数字 | 没解读 | 用"提升+原因"句式 |
| 回避 Limitation | 怕暴露不足 | 主动写(诚实=加分),具体到场景 |
| Method 与 Experiment 矛盾 | 各写各的 | 一致性检查,数字以最终实验为准 |
| 把天智杯当联系空天院敲门砖 | 误判主办方 | 天智杯非空天院主办;练手可以,破冰靠你的工作 |

| 自己读Method觉得清楚、别人读不懂 | 太熟而脑补缺失细节 | 找外部视角互审,以"读完能否实现"为标准 |

| LaTeX表手写语法错 | 手敲易漏&/\\ | 用脚本从数据自动生成(还自动加粗最优) |
