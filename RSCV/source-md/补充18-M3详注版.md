# 第一部分 · W9 找 Gap

## ★ 从 Limitation 挖 Gap：三个层次（原文只说"挖 ≥10 条"）

不是所有 Limitation 都能变成好 Gap。**按可做性分三层**：

| 层次 | 长什么样 | 例子 | 对你 |
|---|---|---|---|
| **L1 · 作者明说的** | Conclusion 里的 "Future Work" | "我们的方法在小目标上仍有不足" | ✅ 最容易找，但**别人也都看得到，竞争最激烈** |
| **L2 · 实验暴露的** | 论文表格里某一列明显低，作者没解释 | per-class AP 里 bridge 特别低 | ✅ **最适合你**——要读表才能发现，多数人不读表 |
| **L3 · 默认假设** | 全领域都默认成立、但可能不成立的前提 | 都假设训练和测试同分布；都假设有充足算力 | ⚠️ 最有价值，也最难，**但一旦成立就是大文章** |

**★ 你的优势在 L2。** 因为你 W2 亲手跑过 baseline、看过 per-class AP、做过消融——**你有别人没有的"自己的实验观察"**。

**具体动作**：打开你 W2-D11 的 per-class AP 表和 `待做idea.md`，**把里面每一条实验观察，去 A 级论文里找对应的讨论**。找不到讨论的，就是 L2 型 Gap。

## D58 查重：三个必查的地方（原文说了工具，没说查什么）

**★ 查重不是"搜一下有没有同名论文"，而是回答三个问题**：

```text
① 这个「问题」有没有人提过？
   → Scholar 搜问题的描述（不是你的方法名）
   → 例："SAR ship detection azimuth robustness"

② 这个「解法」有没有人用过？（哪怕在别的任务上）
   → 搜解法的通用名 + 任意领域

③ 这个「问题+解法」的组合有没有人做过？
   → 两个关键词一起搜
   → 只有这一项撞了才是真撞车
```

**★ 大多数新手的错误是只做第 ③ 步**，结果要么把已有工作当创新，要么把"通用 CV 已有、遥感没有"误判成撞车而放弃。

**Connected Papers 怎么用**（原文提到但没说）：在 `connectedpapers.com` 输入一篇核心论文，它会画出这篇周围的引用网络图。**看图上有没有和你想法接近的节点**——比逐个搜关键词高效得多。

## D61–D62 · ★ 什么叫"最小可行实验"（toy）

原文说"评估候选 1 的最小可行实验（toy）"，**但没定义"最小"**。

### toy 实验的三条设计原则

```text
① 时间上限 2 小时 —— 超过就不叫 toy 了，拆得更小
② 只验证一件事 —— 你的核心假设成立不成立，其余全部固定
③ 必须有对照组 —— 没有对照的 toy 什么都证明不了
```

### 怎么把一个完整实验"缩"成 toy

| 缩什么 | 完整实验 | toy |
|---|---|---|
| **数据量** | 全部 2 万张切块 | **随机抽 1000–2000 张** |
| **epoch** | 12 | **2–3** |
| **模型** | ResNet-50 + FPN | 同一个（**不要换，换了就不可比**） |
| **评测** | 完整 val | 固定的小 val 子集 |
| **seed** | 3 个 | **1 个**（toy 阶段只看方向，不下结论） |

**★ 关键原则**：**只缩"规模"，不缩"结构"。** 数据少、轮次少可以，但**模型、流程、评测方式必须和完整实验一致**——否则 toy 的结论迁移不到完整实验上。

### toy 结果怎么读（★ 这是原文完全没有的部分）

toy 实验**不能证明你的方法有效**，它只能给三种信号：

| 信号 | 长什么样 | 该怎么办 |
|---|---|---|
| **正信号** | 你的方法在 toy 上明显好于对照（比如 +2 以上） | ✅ 值得投入完整实验 |
| **中性信号** | 差不多，或涨跌在 ±1 以内 | ⚠️ **不代表方法没用**——toy 规模太小，噪声大。**看趋势和 loss 曲线，而不是最终数字** |
| **负信号** | 明显更差，或训不起来 | ❌ 先查是不是实现有 bug（用 tiny-batch 过拟合检查）；确认没 bug 再考虑放弃 |

> **★ 最重要的一条**：**toy 出中性信号是最常见的情况，不要因此就毙掉 idea。** toy 的作用是**排除"明显不行"和发现"明显有戏"**，中间地带需要完整实验才知道。
>
> **原文 D65 说"含中/负信号怎么如实写"——就是这个意思。诚实记录中性信号，不要美化成正信号。**

# 第三部分 · W11 实验框架

## ★ 补上 `set_seed()`（原文给了 `--seed` 参数，没给函数本体）

**只传一个 seed 参数是不够的**——如果你不在代码里把所有随机源固定住，**同样的 seed 跑两次结果还是不一样**。

新建 `utils/seed_tools.py`：

```python
"""seed_tools.py —— 固定随机性 + 多 seed 结果的显著性判断。"""
import os
import random
import numpy as np


def set_seed(seed: int, deterministic: bool = True):
    """把所有随机源固定住。★ 缺任何一行都会导致复现不了。"""
    random.seed(seed)                       # Python 自带随机
    np.random.seed(seed)                    # numpy
    os.environ['PYTHONHASHSEED'] = str(seed)
    try:
        import torch
        torch.manual_seed(seed)             # CPU
        torch.cuda.manual_seed_all(seed)    # 所有 GPU
        if deterministic:
            torch.backends.cudnn.deterministic = True
            torch.backends.cudnn.benchmark = False   # ★ 关掉才可复现，代价是慢一些
    except ImportError:
        pass
```

**★ `cudnn.benchmark` 这一行要特别说**：

| 设置 | 效果 |
|---|---|
| `benchmark = True`（**PyTorch 常见默认写法**） | cuDNN 自动挑最快的卷积算法 → **快，但每次挑的可能不同 → 结果不可复现** |
| `benchmark = False` + `deterministic = True` | **可复现**，但慢 10–20% |

**建议**：**做对比实验时开 deterministic**（结果可信最重要）；**跑大规模训练赶时间时可以关掉**，但要在实验记录里注明。

**另外一个坑**：`DataLoader` 的多进程也有随机性，要传 `worker_init_fn` 和 `generator` 才能完全固定。**如果你发现同 seed 两次结果仍有微小差异，多半是这里。**

## ★★ W12-D79 的核心：+0.4 到底算不算提升

原文说"A1 结果分析（并判断显著性）"，**但全书没有一处说怎么判断**。这是 M3 最重要的一个技能，因为**判断错了，你后面所有工作都建立在幻觉上**。

### 完整判定工具（接在上面的 `seed_tools.py` 后面）

```python
def summarize(vals):
    v = np.asarray(vals, float)
    return dict(mean=v.mean(), std=v.std(ddof=1) if len(v) > 1 else 0.0, n=len(v))


def compare(base, ours, seed_paired=True):
    """判断 ours 相对 base 的提升是否可信。"""
    b, o = np.asarray(base, float), np.asarray(ours, float)
    sb, so = summarize(b), summarize(o)
    delta = so['mean'] - sb['mean']
    pooled = np.sqrt((sb['std']**2 + so['std']**2) / 2) if len(b) > 1 else 0.0
    out = dict(base=f"{sb['mean']:.2f}±{sb['std']:.2f}",
               ours=f"{so['mean']:.2f}±{so['std']:.2f}",
               delta=round(delta, 3),
               cohen_d=round(delta / pooled, 2) if pooled > 0 else None)
    if seed_paired and len(b) == len(o):
        d = o - b
        out['每个seed都赢'] = bool((d > 0).all())
        out['配对差均值'] = (f"{d.mean():.2f}±{d.std(ddof=1):.2f}"
                          if len(d) > 1 else f"{d.mean():.2f}")

    # ---- 判定规则 ----
    if len(b) < 3 or len(o) < 3:
        out['结论'] = '❌ seed 不足（<3），不能下任何结论'
        return out

    # ★ 配对判定优先：同 seed 逐对相减，能消掉 seed 本身带来的共同波动
    if seed_paired and len(b) == len(o):
        d = o - b
        if d.mean() <= 0:
            out['结论'] = '无提升'
        elif (d > 0).all() and d.mean() > 2 * d.std(ddof=1):
            out['结论'] = '✅ 配对判定：每个 seed 都赢且差值稳定 —— 可信'
        elif (d > 0).all():
            out['结论'] = '⚠ 每个 seed 都赢，但差值本身波动大 —— 加 seed 再看'
        else:
            out['结论'] = '★ 有的 seed 输了 —— 不可信'
        return out

    noise = max(sb['std'], so['std'])          # 无配对时退化为边际比较（更保守）
    if delta <= 0:            out['结论'] = '无提升'
    elif delta < noise:       out['结论'] = '★ 提升小于噪声，不可信'
    elif delta < 2 * noise:   out['结论'] = '⚠ 弱信号'
    else:                     out['结论'] = '✅ 提升明显大于噪声'
    return out
```

### ★ 实测四种情形（我跑过，结论会让你意外）

**情形 1：mAP 涨了 0.4，但两组各自的标准差是 0.6**

```text
base: 73.03±0.60    ours: 73.43±0.50    delta: 0.4
每个seed都赢: True   配对差均值: 0.40±0.10
结论: ✅ 配对判定：每个 seed 都赢且差值稳定 —— 可信
```

**★ 这个结果和直觉相反。** 只看"提升 0.4 < 标准差 0.6"会判定为不可信——**但这是错的**。

**原因**：两组的标准差主要来自 **seed 本身造成的共同波动**（同一个 seed 下 baseline 和你的方法会一起高、一起低）。**同 seed 逐对相减，这部分共同波动被消掉了**，剩下的 0.40±0.10 才是真正的效应。

> **这就是"配对比较"比"边际比较"更有力的原因。** 学术界报 mean±std 是惯例，**但判断有效性时一定要看配对差**。**很多人在这里误杀了自己真正有效的方法。**

**情形 2：涨了 0.73，但配对差波动大**

```text
配对差均值: 0.73±0.61
结论: ⚠ 每个 seed 都赢，但差值本身波动大 —— 加 seed 再看
```

**情形 3：有一个 seed 输了**

```text
每个seed都赢: False   配对差均值: 0.27±0.40
结论: ★ 有的 seed 输了 —— 不可信
```

**情形 4：只跑了 1 个 seed**

```text
结论: ❌ seed 不足（<3），不能下任何结论
```

**★ 情形 4 是新手最常犯的错。** 跑一次涨了 0.9 就以为成功了——**单次实验的波动本身就可能超过 0.9**。

### ★ 三条判定纪律

1. **少于 3 个 seed 不下任何结论。** 这是底线。
2. **看配对差，不要只看 mean±std。** 边际比较会误杀真正有效的方法。
3. **每个 seed 都赢，比"平均涨得多"更有说服力。** 前者说明稳定，后者可能是某一次运气。

### 现实方案（学术界通行做法）

```text

    ↓ 目的是"排出优先级"，不是"下结论"
第二轮（确认）：只对最关键的 1–2 组补到 3 seed → 3–6 次训练，2 天
    ↓ 只有这一轮的结果能写进论文正文
```

**★ 必须在报告和论文里写清**："消融实验的筛选阶段使用单一随机种子，最终报告的关键配置使用 3 个种子的平均值。" **不写清楚就是学术不端的灰色地带。**

## 5 组消融怎么设计（原文列了 A1–A5，这里补设计原理）

| 编号 | 消融什么 | 回答的问题 | ★ 注意 |
|---|---|---|---|
| **A1** | 去掉你的核心组件 | **它到底有没有用** | 这是最重要的一组，其余都可以砍，这组不能 |
| **A2** | 核心组件换成简单版 | **复杂设计值不值** | ★ 如果简单版效果一样，**你的贡献就要重新表述** |
| **A3** | 换 loss | loss 的贡献 | |
| **A4** | 换 backbone | 方法是否 backbone-agnostic | ★ 审稿人常问"换个 backbone 还成立吗" |
| **A5** | 换数据增强 | 提升是不是来自增强而非方法 | ★ **这一组最容易暴露"其实是增强在起作用"** |

> **★ A2 和 A5 是最诚实、也最容易被跳过的两组。**
> - A2 问的是"你的复杂设计有没有必要"——如果简单版一样好，**诚实的做法是把方法简化，而不是藏起这个结果**。
> - A5 问的是"提升是不是来自别处"——**很多"有效方法"经不起这一问**。

## D84 · ★ go/no-go 的判定标准（原文只问"能继续吗"，没给标准）

### 三个信号灯

| 灯 | 条件 | 决策 |
|---|---|---|
| 🟢 **GO** | ① 3-seed 配对判定为"可信"（见上）**且** ② A1 消融显示去掉核心组件确实掉点 **且** ③ 提升不是来自数据增强（A5 排除） | **继续，进入 M4 方法 v2** |
| 🟡 **PIVOT** | 有提升但很弱（配对差波动大），或提升主要来自某个非核心因素 | **不换课题，但要换切入角度**：把重点从"提性能"转向"分析为什么难"，或者把方法简化后重新定位 |
| 🔴 **NO-GO** | 排查过实现 bug 之后，3-seed 仍无提升甚至更差 | **认真考虑转 Plan B**（Proposal 第 7 节写的那个） |

### ★ 判 🔴 之前必须先排除的三件事

**不要在没做这三件事之前宣布失败**：

```text
① 实现有 bug 吗？
   → tiny-batch 过拟合检查（拿 32 张图，你的方法应该能训到 100%）
   → 如果背不下来，是 bug，不是方法无效

② 超参没调吗？
   → 你的方法可能需要和 baseline 不同的 lr
   → ★ 但注意：如果你给自己的方法调了参而 baseline 没调，对比就不公平
   → 正确做法：两边都在小范围内搜一下，各取最优

③ 对比设置公平吗？
   → 参数量差多少？如果你的方法多了 30% 参数，
     那对照组应该是"参数量相当的更大 baseline"，而不是原始 baseline
```

> **★ 第 ③ 条最容易被忽略。** 如果你的提升只是因为模型更大，那不叫方法有效。**审稿人一定会问这个。**

### 🟡 PIVOT 不是失败（这一段原文完全没有）

**M3 结束时拿到黄灯是很常见的**，而且**黄灯往往是好事**——它说明你发现了一个真实存在但比想象中难的问题。

**黄灯时的三种转法**：

| 转法 | 具体做什么 | 产出还能是什么 |
|---|---|---|
| **从"提性能"转"做分析"** | 系统研究"为什么这个问题难"、"现有方法在什么条件下失效" | 分析类论文，**GRSL 这类 Letters 很欢迎** |
| **从"通用改进"转"特定条件"** | 你的方法可能只在某个子集上有效——**那就把范围收窄，把那个子集讲透** | 更聚焦的贡献 |
| **从"新方法"转"新基准"** | 把你搭的实验框架和公平对比做成一个基准 | 基准类工作，引用往往不低 |

**★ 关键认知**：**研究的产出不只是"性能提升"。** 一个诚实的负结果 + 扎实的分析，价值高于一个可疑的 +0.3。
