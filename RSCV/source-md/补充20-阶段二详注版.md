# 第一部分 · ★ M5 主实验：先算 GPU 的账

## 原文的矩阵，单卡跑不完

W17–W18 要求：**3 个数据集 × 6 个 baseline + 你的方法 3 个 seed**。

**算一下**（按你 W2 实测的 DOTA 训练耗时 8–14 小时）：

```text
每个数据集：6 个 baseline × 1 seed + 你的方法 × 3 seed = 9 次训练
三个数据集：                                          = 27 次训练
27 × 8~14 小时 = 216 ~ 378 GPU 小时 = 9 ~ 16 天连续满负荷
```

**而 W17 + W18 一共 14 天**，还要留时间给分析、可视化、写作、以及**必然会发生的失败重跑**。

> **★ 结论：按原文照做，W18 一定崩。** 这不是你效率低，是矩阵本身没按单卡设计。

## ★ 学术界的标准做法：baseline 数字可以引用，不必都自己训

**这是能救你两周的一条知识，原文完全没提。**

**规则**：

| 情况 | 该怎么办 | 表格里怎么标 |
|---|---|---|
| **baseline 在这个数据集上有已发表结果，且评测协议和你一致** | ✅ **直接引用原论文数字** | 数字后加引用 `[12]`，或标注 `†` 并在表注说明"引自原文" |
| **协议不一致**（切图方式/mAP 算法/单尺度多尺度不同） | ❌ **必须自己重训** | 标 `‡` 说明"我们在统一协议下重跑" |
| **该 baseline 没在这个数据集上报过** | ❌ 必须自己训 | 同上 |
| **你的方法** | ❌ **永远自己训，且必须 3 seed** | 报 mean±std |

**★ 这不是偷懒，是通行做法。** 你去看任何一篇 TGRS 的对比大表，里面绝大多数 baseline 数字都是引用的——**因为让每个作者都重训所有 baseline 是不现实的，也不环保**。

**但有一条底线**：**表格里必须让读者分得清哪些是引用的、哪些是你跑的。** 藏起来才是问题。

## 现实版的实验矩阵（把 27 次砍到 15 次）

```text
每个数据集：
  ├─ 4 个 baseline：引用原论文数字（标注来源）           0 次训练
  ├─ 1~2 个关键 baseline：自己重训（协议对齐，1 seed）    2 次
  └─ 你的方法：3 seed                                    3 次
                                                    ── 5 次 / 数据集
三个数据集 = 15 次训练 ≈ 120 ~ 210 GPU 小时 ≈ 5 ~ 9 天
```

**★ "关键 baseline"选哪个**：选**你直接改进的那个**（比如你在 Oriented R-CNN 上做的改进，就必须自己重训 Oriented R-CNN）。**因为你的提升是相对它算的，这个数字必须是同一环境下跑出来的。**

## 实验矩阵文档模板（D113 让你写，没给格式）

```markdown
# 实验矩阵 v1

## 命名规范（★ 先定死，否则几十个实验会乱）
格式：{数据集}_{方法}_{关键变体}_s{seed}
例：  dota_ours_v3_s0 / dota_orcnn_r50_s0 / dior_ours_v3_s1

## 主结果矩阵
| ID | 数据集 | 方法 | 来源 | seeds | 状态 | mAP | 备注 |
|----|--------|------|------|-------|------|-----|------|
| E01 | DOTA | RoI Transformer | 引用[Ding2019] | — | ✅ | 75.0 | 协议一致 |
| E02 | DOTA | Oriented R-CNN | **自训** | 0 | ⏳ | | 我的直接对照 |
| E03 | DOTA | Ours v3 | 自训 | 0,1,2 | ⏳ | | |
| ... |

## 消融矩阵（W19 用）
| ID | 配置 | 去掉了什么 | seeds | 状态 | mAP |

## ★ GPU 排期（按天）
| 日期 | 白天跑 | 夜间跑 | 预计完成 |

```

> **★ 命名规范这一条现在就要定死。** 你 W19 要做 8 类消融，加上主实验，**总实验数会超过 50 个**。到那时候再改命名，你会分不清哪个是哪个。

## wandb 的组织方式（M3 接上了，这里说怎么用好）

```python
wandb.init(
    project='rscv-paper1',                    # 一篇论文一个 project
    group=f"{dataset}_{method}",              # ★ 同一组的多个 seed 归到一起
    name=f"{dataset}_{method}_s{seed}",       # 单次运行的名字
    tags=[dataset, method, 'main' if is_main else 'ablation'],   # ★ 便于筛选
    config=cfg,
)
```

**★ `group` 这个参数很关键**：wandb 会把同 group 的多个 seed **自动聚合成均值±std 曲线**——这正是你论文里要画的图（见 [M4 的绘图规范](m4-full.html)）。

# 第二部分 · M6 Mock Review 与 Rebuttal

## ★ D148 的"5 个维度"是哪 5 个（原文没说）

**审稿人实际会打分的五个维度**（IEEE 系期刊和 CV 会议大同小异）：

| # | 维度 | 审稿人在问什么 | 你自审时问自己 |
|---|---|---|---|
| **1** | **Novelty / 原创性** | 这个想法之前有人做过吗？ | **我能一句话说清和最接近的工作的区别吗？** |
| **2** | **Technical soundness / 技术正确性** | 方法有没有逻辑漏洞？公式对吗？ | 每个设计选择我都解释了"为什么是这样"吗？ |
| **3** | **Experimental validation / 实验充分性** | 实验能支撑结论吗？消融够吗？对比公平吗？ | ★ **我的提升会不会只是因为参数更多？我做了 A5（排除数据增强）那组消融吗？** |
| **4** | **Clarity / 表述清晰度** | 读得懂吗？图表清楚吗？ | **一个陌生人只读 Method 章能实现我的方法吗？** |
| **5** | **Significance / 重要性** | 这个问题值得解决吗？影响多大？ | 我的贡献能被一句话概括吗？ |

**★ 自审时的打分纪律**：**每个维度打 1–5 分，并且必须写出"扣分理由"。** 全打 4-5 分说明你没在认真审——**你自己都找不出问题，审稿人会替你找**。

## ★ 审稿人最常提的 8 个问题（提前准备）

这些问题**大概率会出现在你的真实审稿意见里**，D148 自审时就该逐条检查：

| # | 常见质疑 | 你该提前准备什么 |
|---|---|---|
| 1 | "提升是不是来自更多参数？" | **参数量/FLOPs 对比表**，或和参数量相当的更大 baseline 比 |
| 2 | "只在一个数据集上有效？" | 三数据集大表（你 M4 已经有了） |
| 3 | "为什么不和 XXX 比？" | Related Work 里说明为什么某些方法不可比（协议不同/代码未开源） |
| 4 | "结果的方差多大？" | **3-seed mean±std**（你 M3 学的） |
| 5 | "消融不完整，组件 B 的作用没证明" | 每个组件都有独立的消融行 |
| 6 | "超参是怎么选的？是不是在测试集上调的？" | ★ **明确写"超参在 val 上选定，test 只跑一次"** |
| 7 | "方法太复杂，实际能用吗？" | FPS / 推理耗时 / 单卡可训 |
| 8 | "和 baseline 的差距在统计上显著吗？" | 用 [M3 的配对判定](m3-full.html)，报每个 seed 的结果 |

> **★ 第 6 条最容易翻车。** 如果你在调参时反复看 test 集的结果，那叫 **test set leakage**，是实打实的方法论错误。**从现在起：超参只在 val 上选，test 集在论文定稿前只跑一次。**

## ★ Rebuttal 怎么写（D153 说"写反驳"，没给范式）

### 三条原则

```text
① 先感谢，再回应 —— 不是客套，是让审稿人愿意读下去
② 每条意见单独编号回应，不要合并 —— 审稿人要能对上他提的每一条
③ 能改就改，不能改就解释；★ 绝不要争辩"你没看懂"
```

### 三种情况的标准写法

**情况 A：审稿人说得对，你改了**

```markdown
**R1.3** 审稿人指出消融实验缺少组件 B 的独立验证。

感谢指出。我们补充了组件 B 的独立消融（新增 Table 5 第 3 行）：
在 DOTA 上，去掉组件 B 后 mAP 从 75.7 降至 74.2（3 seeds，−1.5）。
相关讨论见修改稿 Section 4.3，第 8 页第 2 段（蓝色标注）。
```

**★ 要点**：说清**改在哪（章节+页码）**、**改了什么（具体数字）**。审稿人时间有限，**让他能一眼验证**。

**情况 B：审稿人误解了，你需要澄清**

```markdown
**R2.1** 审稿人认为我们的方法需要额外的标注信息。

感谢这一疑问，这可能是我们表述不清导致的误解。我们的方法**不需要**
任何额外标注，仅使用与 baseline 完全相同的标注（原文 Section 3.2）。
为避免歧义，我们在修改稿 Section 3.2 开头增加了一句明确说明，
并在 Table 1 中增加了"额外标注需求"一列。
```

**★ 关键**：**把误解归因于"我们表述不清"，而不是"审稿人没读懂"。** 而且**真的去改表述**——既然一个专家会误解，其他读者也会。

**情况 C：你不同意，需要反驳**

```markdown
**R3.2** 审稿人建议与方法 X 对比。

我们理解审稿人希望看到更全面的对比。但方法 X 使用多尺度训练与测试
（原文 Section 5.1），而本文所有实验均为单尺度协议；在不同协议下直接
对比数值会产生误导。

为回应这一关切，我们采取了两个措施：
(1) 在 Table 2 中新增方法 X 的原文数值，并明确标注其协议差异；
(2) 在 Section 5.4 增加一段讨论，说明多尺度带来的增益与本文贡献正交。

如果审稿人认为仍有必要在统一协议下重跑方法 X，我们愿意在下一轮补充。
```

**★ 反驳的结构**：**理解对方关切 → 给出技术理由 → 提供折中方案 → 留一个台阶**。**永远不要只说"我们不同意"。**

# 第三部分 · ★ M7 投稿（全书最薄的一段）

## 3.1 选哪本刊（全书零指导，但这个决定影响整篇论文的写法）

| 期刊 | 定位 | **页数** | 适合什么 | 你的第一篇 |
|---|---|---|---|---|
| **IEEE GRSL** | Letters，短文，快 | **最多 5 页**（超过就不能在 GRSL 发） | 一个清晰的小创新点 | ✅ **最推荐** |
| **IEEE TGRS** | GRSS 旗舰，覆盖面最广 | 长文 | 完整的方法 + 充分实验 | ⚠️ 门槛更高，第二篇再考虑 |
| **IEEE JSTARS** | 偏应用 | 长文 | 应用导向的工作 | 备选 |
| **ISPRS J. P&RS** | 影响因子高，偏方法与摄影测量 | 长文 | 方法扎实 + 写作好 | 暂不 |
| **CVPR / ICCV / ECCV** | CV 顶会 | 8 页正文 | 方法创新强 | 门槛最高 |

### ★ GRSL 的两个硬约束（实测查证）

1. **最多 5 页。** 超过 5 页的稿件**不会在 GRSL 发表**，但可以转投 TGRS 或 JSTARS。
2. **版面费**：前 3 页无强制费用；**第 4、5 页对非 GRSS 会员是 $230/页**，GRSS 会员为 $0。**如果你打算写满 5 页，加入 GRSS 会员通常更划算。**

**每篇至少 2 个审稿人。投稿时在 manuscript type 下拉菜单里选 "Letters"。**

> **★ 5 页这个约束必须在写之前就知道。** 如果你按 TGRS 长文的规模写完了十几页，再往 GRSL 塞是灾难性的返工。**W15 开始写之前，先定目标期刊，再按它的模板和页数写。**

### 怎么决定投哪本

```text
① 你的贡献能不能在 5 页内讲清楚？
   → 能 → GRSL（快、门槛适中，第一篇的最佳选择）
   → 不能，需要三数据集大表 + 8 类消融 + 大量讨论 → TGRS

② 你的工作是"方法创新"还是"应用落地"？
   → 方法 → GRSL / TGRS
   → 应用 → JSTARS

③ ★ 诚实评估：你的提升幅度和实验充分性
   → 提升明显 + 实验扎实 → 可以冲 TGRS
   → 提升不大但角度新颖 → GRSL 更合适
```

## 3.2 ★ Cover Letter 怎么写（D177 让你"核对"，全书没教过怎么写）

**Cover Letter 是写给主编看的**，目的是让他决定"送不送审、送给谁审"。**不是论文摘要的复制。**

### 模板（直接可用）

```text
Dear Editor-in-Chief,

We are pleased to submit our manuscript entitled "<论文标题>" for
consideration as a Letter in IEEE Geoscience and Remote Sensing Letters.

【第1段：这篇解决什么问题，为什么重要 —— 3-4 句】
Object detection in remote sensing images faces <具体挑战>. Existing
methods <现状>, but <你的 Gap>. This gap is particularly critical for
<应用场景>.

【第2段：你做了什么，关键结果是什么 —— 3-4 句，★ 要有数字】
In this work, we propose <方法名>, which <一句话核心思想>. Experiments
on three benchmark datasets (DOTA, DIOR-R, HRSC2016) show that our method
improves mAP by <X.X> points over the baseline while adding only <Y>%
parameters. All results are averaged over three random seeds.

【第3段：为什么适合这本刊 —— 2 句】
We believe this work fits the scope of GRSL as it presents a concise and
novel contribution to <方向> within the 5-page format.

【第4段：必需的声明 —— 不要漏】
We confirm that this manuscript is original, has not been published
elsewhere, and is not under consideration by another journal. All authors
have approved the manuscript and agree with its submission.

We have no conflicts of interest to declare.
【如果有推荐/回避审稿人，在这里列】

Thank you for your consideration.

Sincerely,
<你的名字>
<单位、邮箱>
```

**★ 三个常见错误**：
1. **写成摘要的复制** —— 主编已经能看到摘要，Cover Letter 要讲的是"为什么适合你这本刊"
2. **漏掉原创性声明** —— 这是必需的，漏了会被退回
3. **太长** —— 一页以内，主编只花 1 分钟看

## 3.3 投稿文件清单（D178 让你"列清单"）

```text
□ 主稿 PDF（按期刊模板排版，行号打开——多数期刊要求）
□ 源文件（.tex + .bib + 所有图的源文件）——★ 有些期刊接收时才要，先备好
□ Cover Letter（单独 PDF 或在系统里粘贴）
□ Supplementary Material（超参表、更多可视化、更多消融）
□ 作者信息（★ 姓名拼写、单位全称、ORCID、通讯作者标记）
□ 摘要（250 词以内，系统里单独填）
□ 关键词（3-5 个，★ 用期刊的标准关键词表里的词，便于匹配审稿人）
□ 推荐审稿人 / 回避审稿人（可选）
□ 版权与原创性声明（系统里勾选）
```

**★ 关于行号**：IEEE 模板通常有 `\usepackage{lineno}` 选项。**投稿版打开行号，审稿人才能说"第 137 行有问题"**——这直接影响审稿体验。

## 3.4 arXiv 上传（D183 说"可选但推荐"，没说怎么做）

**为什么推荐**：① 抢时间戳（防止被人抢先）② 提前被引用 ③ 求职时有东西可给。

**怎么做**：

```text
① 注册 arxiv.org 账号
② ★ 新用户需要 endorsement（背书）—— 找一位在同类别发过 arXiv 的同行帮你背书
   （导师、师兄师姐、或你 M7 冷邮件联系过的人）
③ 分类选 cs.CV（主）+ eess.IV（副）
④ 上传 .tex 源码包（arXiv 会自己编译），不要只传 PDF
⑤ License 选 arXiv 默认的即可（不要选 CC BY-NC，某些期刊有限制）
```

**★ 时机**：**投稿之后再传 arXiv**，不要之前。理由：有些期刊对预印本有政策要求，先确认目标期刊允许（IEEE 通常允许），而且投稿后传能对上版本。

## 3.5 ★ 投稿后的时间线预期（原文写了"心态管理"，但没给具体预期）

| 阶段 | GRSL 大致时间 | 你该做什么 |
|---|---|---|
| 提交 → 主编初筛 | 几天到两三周 | **什么都别做，去干竞赛/第二课题** |
| 送审 → 收到审稿意见 | **通常一到三个月**（会变） | 同上 |
| 收到 Major/Minor Revision | — | 认真改，别拖 |
| 修改 → 二审 | 一到两个月 | |

**★ 三条心态纪律**（原文提了"心态管理"，这里具体化）：

1. **不要每天刷投稿系统的状态。** 状态从 "Under Review" 变成别的，通常要一个月以上。**每周看一次足够。**
2. **Major Revision 是好消息。** 第一篇论文能拿到 Major Revision 而不是 Reject，**已经说明工作站得住**。
3. **被拒不代表工作差。** 转投是常态。**收到拒稿后先看审稿意见有没有可用的建议，改完转投下一本**——很多论文都是第二三次投中的。

> **★ 最重要的一条**：**投出去之后，把注意力真正转移走。** 原文安排 D184 起立刻转竞赛，是对的——**这不是"分散注意力"，这是让你在等待期继续产出**。等待期有一到三个月，如果你在这段时间只是焦虑，那就是纯损失。
