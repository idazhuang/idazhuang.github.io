# D99 周一 · 列论文 outline + 收集图表素材 + Intro 段 1–2

> **预期管理**:今天进入写作模式——先搭整篇 outline(避免写到一半结构乱),把所有图表素材归齐(写到哪引到哪),再起步写 Intro 的前两段。提醒:写作和做实验是两种肌肉,第一天可能不适应,这很正常;记住"论文是把已有结果讲清楚,不是创造新东西",你手上素材都齐。

## 上午段 · 列论文 outline（8 节,每节 3–5 个 bullet）

**① 先垫概念(outline 为什么必须先列)**
- **outline(提纲)**= 先把整篇论文的骨架列出来(8 个 section,每节 3–5 个 bullet),**让整篇一目了然再动笔**——避免写到一半发现结构乱、推倒重来。参考 A 级论文的标准结构:Abstract / Introduction / Related Work / Method / Experiments / Ablation / Conclusion / References。
- **和写代码先设计架构一个道理**:你不会不画模块图就开始写一个大系统;论文也一样,先有骨架,每段才知道"自己该承担什么、和前后怎么衔接"。**对第一次写论文的你尤其重要**:没有 outline,很容易写成"想到哪写到哪"的散文,逻辑链断裂,审稿人读着累。
- **outline 不是照抄某篇论文目录**:章节名可以仿 A 级论文,但每节的 bullet 要填**你自己的故事线**(你的 Gap、你的方法、你的结果)。

**② 手把手带做**:在 `paper/outline.md` 列 8 个 section,每节写 3–5 个 bullet(这节要讲什么)。参照你读过的 A 级论文结构 + 你的 Proposal v2 内容。骨架:
```markdown
# 论文 outline（8 节，每节 3–5 bullet）
1 Abstract：问题一句 + 方法一句 + 主结果一句（最后写）
2 Introduction：① 背景 ② 挑战/Gap ③ 方法概述 ④ 贡献列表（4 段）
3 Related Work：子节1 旋转检测方法 / 子节2 通用检测 / 子节3 借鉴的通用 CV 技巧
4 Method：Overview / 多尺度融合 / 遮挡感知分配 / Soft-NMS+检测头 / Algorithm 1
5 Experiments：数据集与设置 / 主表（3 数据集，含参数FPS）/ 与 SOTA 对比
6 Ablation：消融表（各组件）/ 定性可视化 / 推理超参分析
7 Conclusion：总结 + 局限 + 未来
8 References
```
**③ 这一步合格的样子**:8 节 outline,每节 3–5 个 bullet,整篇逻辑能一眼看懂(从 Gap 到方法到验证一条线)。
**④ 最常踩的坑**:① 不列 outline 直接写正文 → 结构散、反复返工;② outline 照抄某篇论文目录 → 要按你的故事线组织(你的组件、你的数据集);③ bullet 写太笼统("讲方法")→ 写具体("讲多尺度融合怎么解决小目标")。
**⑤ 卡住怎么自救(决策树)**:不知每节写啥? → 仿 A 级论文的章节标题 + 用你 Proposal v2 的对应内容填;某节 bullet 想不全? → 回看你的实验产出(主表→Experiments、消融→Ablation、方法报告→Method),素材都在;纠结章节顺序? → 用最通用的 8 节标准结构,别自创。
**⑥ 今天(这一步)你同时学会了什么**:你学会**先搭 outline 再写论文**。**做了**(论文 outline)、**学了**(论文标准结构、先骨架后血肉、按自己故事线组织)、**会了**(为一篇论文规划章节骨架)。

> **技能卡｜先 outline 后正文**:动笔前先列 8 节 outline(每节 3–5 bullet),让整篇逻辑一眼可见再填内容。章节仿 A 级论文,bullet 填你自己的故事线(Gap→方法→结果)。这一步省下大量"写到一半推倒重来"的时间——和写代码先设计架构同理。

## 晚上段 · 写 Introduction 段 1（背景）+ 段 2（挑战/Gap）

**① 先垫概念(Introduction 4 段结构)**:经典 Intro = **段1 背景(这个领域为什么重要,3–4 句)→ 段2 挑战(现有方法有什么问题=你的 Gap,4–5 句)→ 段3 方法概述(你做了什么,一段)→ 段4 贡献列表(bullet 列 3–4 条)**。今晚写段 1、2。**为什么 Intro 这么重要**:它是审稿人读完摘要后第一个细看的部分,决定第一印象;一个好的 Intro 让审稿人在读方法前就认同"这个问题值得解决、这个思路有道理"。**4 段结构是久经考验的套路**——先讲清楚"问题重要",再讲清楚"现状不足"(你的机会),自然引出"你的方法",最后用贡献列表让审稿人一眼看到价值。
**② 手把手带做**:写段 1(你方向的重要性,3–4 句,快速收敛)+ 段 2(现有方法的局限=你的 Gap,4–5 句,引出你要解决的问题)。填空骨架 + 范例:
```markdown
# 段1 背景（3-4 句，快速收敛到你的问题）
骨架：{方向}在{应用}中很重要 → 遥感图像有{独特性质} → 使{你的任务}既重要又困难。
范例：遥感图像中的目标检测在国防、测绘、灾害监测中至关重要。与通用图像不同，
遥感目标常呈任意朝向、尺度小、排列密集，因此旋转目标检测成为关键且具挑战的问题。

# 段2 挑战/Gap（4-5 句，点出现有方法缺什么 + 根因）
骨架：现有方法（引 2-3）多采用{做法}；它们在{某方面}有效，但在{你的 Gap}不足；
      根因是{本质原因}；这在{你关注的场景}尤其突出。
范例：现有旋转检测方法多依赖更强的骨干网络或更大的预训练（如 RingMo 等），
在通用基准上表现优异，但往往算力开销大、难以在单卡部署，且在密集相邻小目标
场景下仍受"框粘连"困扰。其根因在于：多数工作聚焦表示增强，较少针对遥感特有的
小目标、遮挡与密集排列做轻量而专门的设计。
```
**③ 合格样例**:Intro 段 1–2 成稿,段 1 三四句收敛到问题,段 2 清晰点出"现有方法缺什么 + 根因"。
**④ 最常踩的坑**:① 段 1 背景写太长(整段泛泛讲遥感发展史)→ 3–4 句即收敛到你的问题;② 段 2 只说"现有方法不够好"不说**具体缺什么、为什么**→ 要点到 Gap 和根因(你的方法正是冲着这个根因去的)。
**⑤ 卡住怎么自救**:写不出 → 用你 M3 Proposal 的 Motivation 段改写(已经写过类似的);段 2 的 Gap 提炼不出 → 回看你方法解决的核心问题(密集粘连/单卡高效),Gap 就是"现有方法在这上面不行";背景收不住 → 强制自己 3 句话内必须出现"你的任务"。
**⑥ 今天(这一步)你同时学会了什么**:你开始写 Intro(背景+挑战)。**做了**(Intro 段 1–2)、**学了**(Intro 4 段结构、背景快速收敛、段 2 点 Gap 与根因)、**会了**(写背景并收敛到 Gap)。

## 上午段 · 写 Intro 段 3（方法概述）+ 段 4（贡献列表）

**① 先垫概念(方法概述 + 贡献列表)**:段 3 = 一段话说清"你做了什么"(方法概述,3–4 句,承接段 2 的 Gap);段 4 = **贡献列表**(bullet 列 3–4 条,每条"我们提出了 X,它带来 Y")——这是审稿人快速判断你工作价值的地方。**贡献列表是 Intro 的"广告位"**:很多审稿人会直接看贡献列表来判断"这篇够不够分量"。所以每条贡献要**具体 + 可验证**:不是"我们提出一个有效的模块",而是"我们提出 X 模块,在密集场景提升 Y,且几乎不增参数"。
**② 手把手带做**:写段 3(方法概述,承接 Gap)+ 段 4(3–4 条贡献,用真实结果支撑)。填空骨架 + 范例:
```markdown
# 段3 方法概述（3-4 句，承接段2 Gap）
骨架：为此我们提出{方法名}，针对{Gap}设计了{组件1/2/3}；
      借鉴{通用CV技巧}并适配遥感；在单卡预算下实现{效果}。
范例：为此，我们提出一种面向单卡预算的高效旋转检测方法。它包含多尺度融合（增强
小目标）、遮挡感知标签分配（提升密集遮挡召回）与旋转 Soft-NMS（缓解框粘连），
将通用检测中的若干轻量技巧适配到遥感场景，在不显著增加参数的前提下提升精度。

# 段4 贡献列表（3-4 条，每条用真实数字）
• 我们针对遥感小目标/遮挡/密集排列，设计了三个轻量且专门的组件，可即插于
  Oriented R-CNN 等检测器。
• 我们的方法在 DOTA/DIOR-R/HRSC 三个数据集上平均提升 X mAP，且参数仅 +2M、
  推理 22 FPS，契合单卡部署。
• 我们提供完整消融与跨数据集验证，证明每个组件有效且方法泛化。
```
**③ 合格样例**:Intro 段 3–4 成稿,段 3 承接 Gap、段 4 贡献条具体可验证(带真实数字)。
**④ 最常踩的坑**:① 贡献写空("我们提出一个有效方法")→ 要具体(提出什么、解决什么、提升多少);② 贡献和实验对不上 → 用真实数字;③ 贡献列了五六条 → 3–4 条最有力的即可,贪多反而稀释。
**⑤ 卡住怎么自救**:贡献提炼不出 → 从主表/消融里挑最硬的 2–3 条数字,每条数字配一句"我们做了什么";方法概述太长 → 只讲"做了什么+为什么",细节留给 Method;不确定哪些算贡献 → 问"审稿人凭什么觉得这篇有价值",答案就是你的贡献。
**⑥ 今天(这一步)你同时学会了什么**:你写完了 Intro 的方法概述与贡献。**做了**(Intro 段 3–4)、**学了**(方法概述承接 Gap、贡献列表写法、用真实数字)、**会了**(用真实结果写贡献)。

> **技能卡｜贡献列表写法（用真实数字）**:Intro 段 4 是审稿人判断分量的"广告位"。每条贡献 = "我们做了 X(具体) + 它带来 Y(真实数字)",3–4 条最硬的即可。忌空话("有效的方法")、忌贪多(稀释)、忌与实验对不上。数字从你的主表/消融里挑。

## 中午段 · 修改润色 Introduction

**① 先垫概念**:通读 Intro 4 段,润色——确保"背景→挑战→方法→贡献"一条线连贯、删冗余、术语一致。**润色是写作的必要环节**:初稿往往段落间有跳跃、有重复、术语前后不一(一会儿"目标"一会儿"物体");润色就是把这些磨平,让读者顺畅读下来。**重点检查过渡**:段与段之间要有逻辑衔接(段 2 末点出 Gap → 段 3 首"为此我们…"自然承接)。**一个高效的润色顺序**:① 先读一遍只看"逻辑流"——四段是不是"重要→不足→我的解法→价值"一条线,有没有哪段突兀;② 再读一遍只看"重复"——同一个意思是不是在两段都说了(背景和挑战常重复),删掉冗余;③ 最后读一遍只看"术语"——同一概念有没有用了不同的词,统一。分三遍各盯一个维度,比一遍想抓全部高效得多。**润色不是改得花哨,而是让逻辑更顺、表达更准**——学术写作崇尚清晰,不崇尚辞藻。
**② 手把手带做**:通读 Intro 4 段,润色(逻辑连贯、删冗余、术语一致、加过渡句);确保一条线贯穿。
**③ 合格样例**:Introduction 完成稿(4 段连贯,术语统一,过渡自然)。
**④ 最常踩的坑**:① 段落跳跃(段 2 讲完 Gap 段 3 突然讲方法没过渡)→ 加"为此/To this end"类过渡;② 术语不统一(目标/物体/object 混用)→ 建术语表统一;③ 背景太长 → 精简。
**⑤ 卡住怎么自救**:看不出问题 → 假装第一次读的人通读一遍;术语乱 → 列一张术语对照表全文替换;不确定连不连贯 → 检查每段第一句是否承接上段最后一句。
**⑥ 今天(这一步)你同时学会了什么**:你完成并润色了 Introduction。**做了**(Intro 完成稿)、**学了**(润色与逻辑连贯、过渡句、术语统一)、**会了**(打磨一段学术写作)。

## 晚上段 · 开始写 Related Work 子节 1

# D102 周四 · 写 Method（Overview + 组件 1 + 组件 2）

> **预期管理**:今天开始写 Method——全篇最需要"严谨可复现"的一章。提醒:Method 的金标准是"让不认识你的人读完也能实现";用总分结构(先 Overview 再逐组件),每个组件用"直觉+公式+图"三件套,别只堆公式不讲为什么。

## 上午段 · 写 Method Overview（全局 + 架构图引用）

**① 先垫概念(Method 写法:总分结构)**:核心原则——**让不认识你的人读完也能实现**。用"**总分**"结构:先 Overview(全局,数据怎么从输入流到输出、你的组件在哪,引用架构图),再逐个讲组件。**为什么先 Overview**:读者需要先有"全局地图"才能理解每个组件的位置和作用;上来就讲某个组件的公式,读者不知道它在整个流程的哪一环,会迷失。**Overview 要点**:一段话讲清"输入→backbone→neck(含你的组件)→head→输出"的数据流,并"如 Figure 2 所示"引出架构图。
- **"让陌生人读完也能实现"为什么是 Method 不可妥协的金标准**:Method 章和论文其他部分有个本质区别——Intro 是讲故事、RW 是摆背景,而 **Method 是一份"技术契约":它向读者(和审稿人)承诺"按我写的,你能复现出我的方法和结果"**。可复现性是科学的基石,一个无法被复现的方法,在学术上是没有价值的(别人没法验证、没法在此基础上推进)。所以 Method 写作的标准不是"我自己看得懂"(你当然懂,是你做的),而是"**一个有相关背景、但完全不了解你工作的人,只读这一章,能不能把你的方法实现出来**"——这又是知识的诅咒在作祟:你脑子里有所有实现细节,容易把关键的设定(超参、维度、连接方式、训练细节)当成"显然"而省略,但对复现者那些恰恰是卡点。**所以写每个组件时,要问自己:别人照这段能写出代码吗?有没有哪个数字、哪个连接、哪个细节我没交代清楚?** 这种"为复现者负责"的严谨,既是学术规范,也直接关系到审稿——审稿人如果觉得"这方法描述不清、没法复现",是会据此拒稿的。把 Method 写到"陌生人能实现"的程度,是你这篇论文能不能立住的关键一章,值得你在这一章上多花心思、反复确认每个细节(超参、维度、连接、训练设定)是否齐全、是否可被复现。
**② 手把手带做**:写 Method Overview 段(全局描述 + "如 Figure 2 所示"引用架构图)。范例:
```markdown
# Method Overview 范例
图 2 展示了我们方法的整体架构。给定一张遥感图像，骨干网络提取多层特征，随后
我们的多尺度融合模块（第 X 节）增强小目标表达；在检测头的标签分配阶段，遮挡感知
分配（第 Y 节）提升密集遮挡目标的召回；推理阶段，旋转 Soft-NMS（第 Z 节）缓解
相邻框粘连。整个框架以 Oriented R-CNN 为基线，所有组件均轻量、可即插。
```
**③ 合格样例**:Method Overview 成稿,读者能建立全局观(数据流清晰、组件位置明确、引了架构图)。
**④ 坑**:Overview 写太细(把某组件公式都搬进来)→ 只讲全局,细节留给组件小节;没引架构图 → 必须"如 Figure 2 所示"。
**⑤ 自救**:Overview 写不出 → 照着你的架构图,用文字把"输入怎么一步步流到输出、你的组件在哪一环介入"描述一遍即可;太长 → 控制在一段,细节后置给组件小节;不知道详略 → Overview 只回答"整体怎么走、我加了哪几块",具体每块怎么实现一律留到对应组件小节,这样读者先有地图再看细节,不会迷路。
**⑥ 今天(这一步)你同时学会了什么**:你写了 Method 的全局总览。**做了**(Method Overview)、**学了**(总分结构、先全局给地图、引架构图)、**会了**(写方法的全局描述)。

## 中午段 · 写 Method 组件 1（直觉 + 公式 + 图示）

**① 先垫概念(组件三件套)**:每个核心组件要有 **① 直觉(为什么用它、治哪个问题)② 公式(严谨定义、符号说清)③ 图示(在架构图里的位置/内部结构)**。三件套齐全,组件才"既懂又能复现"。**为什么三件套缺一不可**:只有直觉→读者懂思想但没法实现;只有公式→读者能实现但不懂为什么这么设计(也看不出创新点);加图示→直观。**直觉写在最前面**:先用一两句话讲"这个组件治什么问题、为什么这么设计",再给公式——读者带着"为什么"去看公式,理解快得多。
**② 手把手带做**:写组件 1 小节(多尺度融合):直觉 + 公式 + 图示。范例:
```markdown
# 组件1（多尺度融合）三件套范例
【直觉】遥感小目标在深层特征上易丢失细节。我们融合多个尺度的特征以保留小目标的
   细粒度信息（治"小目标漏检"）。
【公式】设第 l 层特征为 F_l，融合特征 F* = Conv( Σ_l Up(W_l · F_l) )，其中 Up(·)
   表示上采样到最高分辨率，W_l 为 1×1 卷积对齐通道。（所有符号在此定义）
【图示】见图 2 左侧"多尺度融合"分支：三层特征经对齐、上采样、相加、卷积后输出。
```
**③ 合格样例**:组件 1 小节三件套齐全,懂 CV 的人能照着复现。
**④ 坑**:① 只写公式不写直觉 → 读者看不出"为什么";② 符号没定义(F_l 是什么没说)→ 无法复现;③ 没引图 → 加"见图 2"。
**⑤ 自救**:公式写不出 → 先用文字 + 伪代码精确描述,公式后补;直觉说不清 → 回"它治哪个 Gap";符号乱 → 列符号表统一。
**⑥ 今天(这一步)你同时学会了什么**:你学会用**组件三件套**写 Method。**做了**(组件 1)、**学了**(直觉+公式+图、直觉先行、符号定义)、**会了**(把一个组件写到可复现)。

> **技能卡｜Method 组件三件套**:每个核心组件写"直觉(治哪个 Gap、为什么这么设计)+ 公式(严谨定义所有符号)+ 图示(架构图位置/内部结构)"。直觉写最前,读者带着"为什么"看公式理解更快。三件套齐 = 既懂又能复现,也让创新点可见。缺直觉=不懂为什么,缺公式=没法实现。

## 晚上段 · 写 Method 组件 2（遮挡感知分配）

**① 先垫概念**:组件 2(遮挡感知标签分配)同样用三件套。**它属于"训练策略"类组件**:不改网络结构,而改训练时正样本怎么分配——对遮挡严重的目标放宽匹配,让它得到更多正样本、提升召回。直觉、公式(分配规则)、图示(可画一个分配示意)都要有。**训练策略类组件对你尤其划算**:它**不增加任何推理开销**(只影响训练时怎么算 loss、分正负样本,推理时网络结构和速度完全不变),却能提升性能——这正契合你"单卡高效"的定位。论文里把这点讲出来是加分项:"我们的遮挡感知分配仅作用于训练,推理零额外开销"。**写这类组件的注意点**:要讲清"改了什么分配规则、为什么这样改能帮到目标类别",而不是泛泛说"我们改进了标签分配";公式要把"遮挡程度怎么量化、阈值怎么随它变化"写明白。
**② 手把手带做**:写组件 2 小节(三件套),注意和组件 1 的衔接(组件 1 是结构、组件 2 是训练策略,逻辑上互补)。范例:
```markdown
# 组件2（遮挡感知分配）三件套范例
【直觉】密集遮挡目标常因 IoU 匹配过严而正样本不足、召回低。我们对遮挡严重的目标
   放宽匹配阈值，给它更多正样本（治"遮挡漏检"）。
【公式】对 gt 框 g，设其遮挡程度 o(g)∈[0,1]，匹配阈值 τ(g)=τ0 − α·o(g)；
   anchor a 与 g 的旋转 IoU 超过 τ(g) 即为正样本。（o, τ0, α 在此定义）
【图示】见图 2 检测头分支：遮挡重的目标匹配范围更宽（示意为更大的接收区域）。
```

## 二、实用工具 — 统计各章字数（盯 ≥6000）+ 图表引用完整性检查
```python
import re
# ① 统计各 section 字数（中文按字符计；盯 Intro+RW+Method ≥6000）
def count_words_by_section(md_path):
    text = open(md_path, encoding="utf-8").read()
    parts = re.split(r'^#{1,3}\s+(.*)$', text, flags=re.M)
    total = 0
    for i in range(1, len(parts), 2):
        title, body = parts[i], parts[i+1]
        n = len(re.sub(r'\s', '', body))
        total += n
        print(f"{title[:30]:<32} {n} 字")
    print(f"--- 合计 {total} 字 ---")

# ② 检查正文引用的图表是否都存在（避免"如图3"但没有图3）
def check_figure_refs(md_path, figure_ids):   # figure_ids = {"Figure 1","Figure 2","Table 1",...}
    text = open(md_path, encoding="utf-8").read()
    refs = set(re.findall(r'(?:Figure|Table|图|表)\s*\d+', text))
    missing = refs - figure_ids
    print("引用但可能缺失的图表:", missing or "无")

if __name__ == "__main__":
    print("用法：统计各章字数确认 Intro+RW+Method≥6000；检查图表引用完整性")
```

## 四、Method 单组件"四件联动"完整范例（直觉/公式/图示/伪代码一致）
> 把一个组件写到"图、文、公式、伪代码四者说同一件事"——这是 Method 可复现的关键。以旋转 Soft-NMS 为例完整演示一遍。

```markdown
### 正文（直觉 + 公式 + 图示，三件套）
【直觉】密集相邻目标经标准 NMS 易被误并（"框粘连"）。我们用旋转 Soft-NMS：不直接
删除与最高分框重叠的相邻框，而是按其旋转 IoU 衰减得分，从而在密集场景保留更多
正确框（治"密集粘连"）。
【公式】设当前最高分框为 b_i、其余框 b_j，得分 s_j 更新为
        s_j ← s_j · exp( − RIoU(b_i, b_j)² / σ )，
其中 RIoU 为旋转框 IoU，σ 为衰减系数；衰减后 s_j < t 的框被丢弃。
【图示】见图 2 推理分支"Rotated Soft-NMS"模块：相邻框得分被衰减而非删除。

### 伪代码（Algorithm 1 节选，与上面公式同一逻辑）
while S 非空:
    i ← argmax(S); D ← D ∪ {B_i}
    for j ≠ i: S_j ← S_j · exp(−RIoU(B_i,B_j)²/σ)   # ← 与正文公式完全一致
    去掉 S_j < t 的框

### 一致性自检（四者对同一件事）
[✓] 直觉里的"衰减而非删除" = 公式的乘 exp 衰减 = 伪代码第3行 = 图里"得分衰减"标注
[✓] 符号 σ, t, RIoU 在正文公式处定义，伪代码沿用同名
[✓] 图 2 有"Rotated Soft-NMS"模块且位置在推理分支（与 Overview 描述一致）
```
**这套"四件联动 + 一致性自检"用在每个组件上**:写完一个组件,就对一遍"直觉/公式/图示/伪代码是不是在说同一件事、符号是否同名同义"。四者一致的 Method,审稿人挑不出"图文不符"的硬伤,复现者照着就能实现。

## 五、中文骨架 → 英文初稿 的衔接贴士（英文吃力时的稳妥路径）
> 你不必一上来用英文流畅写作。稳妥路径:先用中文把逻辑骨架写顺,再逐段译英,最后润色。

```markdown
1. 先中文搭骨架：用本包的填空骨架，把每段逻辑、每个组件三件套用中文写顺、写全。
   （这一步解决"想清楚"，不被英文卡住思路）
2. 逐段译英：一段一段译，别整篇硬翻；保留你已理顺的逻辑结构。
3. 句式套模板：学术英文有固定句式，套用即可——
   - 引出 Gap: "However, existing methods ... still suffer from ..."
   - 提出方法: "To this end, we propose ..."
   - 贡献: "We ... ; Extensive experiments show that ..."
   - 组件直觉: "Motivated by ..., we introduce ... to address ..."
4. 润色：用工具检查语法，统一术语（建术语对照表：目标=object、旋转框=oriented box…）。
5. 别追求一步到位的"母语级"英文——逻辑清晰 + 术语准确 + 句式规范，就是合格的论文英文。
```
**心态**:论文英文不是文学创作,是"用规范句式把清晰逻辑表达出来"。你逻辑理顺了(中文骨架),英文只是换一套规范句式装上去。M5 写完整论文时这套流程还会反复用。

## 七、本周写作坑速查表（现象 → 根因 → 解法）
| 现象 | 根因 | 解法 |
|---|---|---|
| Intro 背景写一大段 | 没快速收敛到 Gap | 背景 3-4 句即收敛到你的问题 |
| 段2 只说"不够好"不说缺啥 | 没点 Gap 和根因 | 写具体缺什么+为什么(你方法正冲它去) |
| 贡献写成"提出有效方法" | 太空 | 具体:提出什么/解决什么/提升多少(真实数字) |
| 贡献列了五六条 | 贪多稀释 | 留 3-4 条最硬的 |
| RW 像流水账 | 没分类、没点不足 | 分 2-3 子类,每类"共性→代表→不足" |
| 三章内容重复 | 各章定位不清 | RW 讲别人、Method 讲自己,各司其职 |
| Method 别人无法复现 | 只公式无直觉/符号没定义/无图 | 组件三件套:直觉+公式(定义符号)+图;加伪代码 |
| 图/文/伪代码不一致 | 各写各的 | 统一架构图、Method 文字、Algorithm 三者 |
| 字数不够去凑字 | 误解"详细" | 补该有内容(直觉/不足/衔接),非灌水 |
| 自己看不出问题 | 太熟脑补 | 切读者视角/隔天再读/找外部读者/TTS 朗读 |
