# 1. 看到「把 X 数据集下下来」

**出现 56 处**，从 W1 的 DOTA 一直到 M18。原文几乎从不给地址。

## 三步法

**第一步：找官方页面（2 分钟）**

搜索 `<数据集名> dataset official` 或 `<数据集名> download`。**优先级**：

1. **论文里的链接** —— 数据集论文的 Abstract 末尾或 Introduction 脚注，几乎必有。这是最权威的。
2. **作者/实验室主页** —— 遥感数据集大量挂在这里（如 DOTA 在 `captain-whu.github.io`）。
3. **GitHub 仓库** —— 搜 `<数据集名> github`，README 里给网盘链接。
4. **Papers with Code 的 Datasets 页** —— 搜数据集名，它会聚合所有已知下载入口。

**国内特别注意**：遥感数据集大量只放百度网盘。找不到 Google Drive 的直链时，去中文社区搜 `<数据集名> 百度网盘`，多半有人转存过。

**第二步：确认目录结构要求（★ 最容易漏，也最容易卡死）**

**下载前先去看框架文档要什么结构。** 位置固定：

```text
<框架仓库>/docs/en/  或  docs/zh_cn/  →  找 dataset_prepare / useful_tools / 数据集准备
```

或者直接在仓库里搜：

```bash
grep -rn "data_root" configs/_base_/datasets/ | head
```

配置文件里写死的路径**就是框架期望的结构**。照着摆，一个字母都别改。

**第三步：先下最小的那个 split**

**永远先下 val 或 test（几百 MB 到 2 GB），把整条流程跑通，再让 train 在后台慢慢下。**

这一招能救你两天。原手册从没说过，但它是所有有经验的人的默认动作。

## 下完必做的四项体检

```bash
# ① 数量对不对（和论文里报的数字比）
ls <split>/images | wc -l
# ② 图和标注一一对应
ls <split>/images | wc -l ; ls <split>/labelTxt | wc -l
# ③ 标注长什么样（★ 一定要 head 一下，别信想象）
head -3 <split>/labelTxt/$(ls <split>/labelTxt | head -1)
# ④ 磁盘够不够（切图/解压常常再翻一倍）
df -h .
```

> **一条纪律**：**数据集永远放在项目目录之外，用软链接指进来。**
> ```bash
> mkdir -p data && ln -s /mnt/bigdisk/DOTA data/DOTA
> ```
> 否则你迟早会把几十 GB 提交进 git，或者换项目时重复下载。

# 2. 看到「参考官方文档 / 自己查一下最新」

**出现 33 处。** 这是最气人的一类——把最难的一步推给你。但**这一招学会之后，你反而比拿到写死的版本号更强**，因为写死的数字半年就过期。

## 三分钟读穿任何 GitHub 仓库

进到仓库主页后，**按这个顺序看，每处不超过 30 秒**：

| 顺序 | 看哪 | 找什么 |
|---|---|---|
| 1 | **README 顶部的徽章** | 最新版本号、支持的 Python/PyTorch 范围 |
| 2 | **`docs/en/faq.md`** 或 README 的 Installation 段 | **版本兼容表**（哪个版本配哪个依赖）—— 这是最值钱的一张表 |
| 3 | **`docs/en/get_started.md` / `install.md`** | 完整安装命令 + 验证 demo |
| 4 | **`configs/<方法名>/README.md`** | **模型库表格**：每行是一个模型，末尾有 config 链接和权重（model）下载链接 |
| 5 | **Releases 页** | 这个仓库最后一次更新是什么时候（**判断它是不是已经没人维护了**） |
| 6 | **Issues 搜索** | 把你的报错原文粘进去。**记得删掉 `is:open` 过滤器**，很多答案在已关闭的 issue 里 |

## 版本兼容表怎么用

看到这样一张表：

```text
| MMRotate | MMCV                     | MMDetection             |
| main     | mmcv-full>=1.5.3, <1.8.0 | mmdet >= 2.25.1, <3.0.0 |
```

**读法**：取**上界减一个小版本**通常最稳（`<1.8.0` 就选 1.7.x），因为那是这个版本发布时实际测过的组合；取下界容易缺特性，取最新容易踩没测过的坑。

## 一个通用判断：这个项目还活着吗

```text
最后一次 commit 在半年内 + Issues 有人回  →  正常，跟着最新文档走
最后一次 commit 超过一年 + Issues 堆积     →  ★ 老项目，必须按"考古模式"装：
                                              把 numpy / setuptools / 格式化工具
                                              按回当年的版本（见《MMRotate 实操》§4.3）
```

**"考古模式"是复现两年前代码的标准姿势**，你后面会用很多次。

# 3. 看到「用你改好的 config」「把参数调好」

## 读改验三步

**读**：先搞清这个配置从哪继承、最终展开成什么样。

```bash
# MM 系框架通用
python tools/misc/print_config.py <你的config.py>
# 其他框架：找 --print-config / --dump-config 之类的参数，或直接 python 打印配置对象
```

**改**：**永远新建自己的文件去继承，绝不直接编辑官方配置。**

```python
_base_ = ['../官方/基线配置.py']
# 下面只写你要改的几行
```

理由有三个，每个都很实际：① 说得清自己的实验和基线差在哪；② `git pull` 更新不冲突；③ 三个月后你还知道自己改了什么。

**验**：改完先 grep 关键字段，确认真的生效了。

```bash
python tools/misc/print_config.py my.py | grep -E "ann_file|img_prefix|samples_per_gpu|lr=|num_classes|max_epochs"
```

**一次训练几小时。路径写错等于白烧半天电。这 10 秒必须花。**

## 任何检测框架都要检查的五个字段

| 字段 | 错了会怎样 |
|---|---|
| 数据路径（`ann_file` / `img_prefix` / `data_root`） | 找不到文件，或读到空标注（**不报错但 loss 不降**） |
| 类别数（`num_classes`） | 报 shape mismatch，或类别错位 |
| batch（`samples_per_gpu` / `batch_size`） | OOM |
| **学习率与 batch 的配比** | **loss 直接 nan**（见下） |
| epoch / iteration 总数 | 训练时长完全不对 |

## ★ 学习率与 batch：一条必须背下来的规则

**线性缩放规则**：总 batch 变 k 倍，lr 也要变 k 倍。

**但关键是先搞清"这份配置默认几卡"**，不同框架不一样：

| 框架 | 默认假设 | 单卡跑要怎么改 |
|---|---|---|
| MMDetection 的 COCO 配置 | **8 卡 × 2 张 = 16** | lr **除以 8** |
| MMRotate 的 DOTA 配置 | **1 卡 × 2 张 = 2** | **不用改** |
| 大部分论文开源代码 | 看 README 的 "we train on N GPUs" | 按比例换算 |

**怎么判断**：① 看配置文件名里有没有 `_8x2_` 这种数字；② 看仓库 README 模型库表格里的 "batch size" 列；③ 看论文 Implementation Details 那一段。

**判断不了就用实验判断**：先按原样 dry-run 200 个 iter，**loss 出现 nan 就是 lr 太大，减半再试**。

# 4. 看到「②手把手带做」里一条命令都没有

**出现 219 处**，是数量最多的一类。但**其中大部分是读论文、写文档、发邮件，本来就不需要命令**——真正该有命令却没有的，集中在 M2–M10 的技术时段。

## 反推命令的四个入口，按顺序试

**入口一：仓库的 `tools/` 目录（最快，多数情况够用）**

```bash
ls tools/
# 典型：train.py  test.py  analysis_tools/  misc/  data/  deployment/
python tools/train.py --help      # ★ --help 会把所有参数列出来
```

**MM 系框架的固定入口**，记住能省无数时间：

| 你要做什么 | 命令 |
|---|---|
| 训练 | `python tools/train.py <config> --work-dir <目录>` |
| 评测 | `python tools/test.py <config> <ckpt> --eval <指标>` |
| 展开配置 | `python tools/misc/print_config.py <config>` |
| 画 loss 曲线 | `python tools/analysis_tools/analyze_logs.py plot_curve <log.json> --keys loss` |
| 算速度/FLOPs | `python tools/analysis_tools/get_flops.py <config>` |
| 收集环境信息（**报 issue 时必附**） | `python mmdet/utils/collect_env.py` |

**入口二：官方文档的 `get_started` / `train_test` 页** —— 一定有可复制的完整命令。

**入口三：仓库里搜现成的脚本**

```bash
grep -rn "python tools/" README.md docs/ | head -20
ls tools/*.sh          # 很多仓库有 dist_train.sh 之类的封装
```

**入口四：Issues 里搜 "how to"** —— 有人问过一模一样的问题。

## 命令跑之前的三个自问

1. **我在哪个目录？** MM 系脚本几乎都要求在仓库根目录跑。
2. **我在哪个环境？** `conda activate` 了吗？`which python` 确认一下。
3. **这条命令要跑多久？** 超过 10 分钟的**一律用 tmux**，别在前台跑。

```bash
tmux new -s work      # 开
# Ctrl+B 然后 D       # 脱离（关掉 SSH 也不会断）
tmux attach -t work   # 回来
```

# 5. 「跑起来了，但不知道对不对」

资料常说"启动训练"，却不说**怎么判断它是不是在正确地训练**。这一节补上。

## 训练启动后的黄金 200 个 iter

**盯前 200 个 iter 就能判断成败**，不要挂上就去睡。

| 现象 | 判断 | 动作 |
|---|---|---|
| total loss 稳步下降 | ✅ 健康 | 可以去睡了 |
| loss = `nan` / `inf` | ❌ lr 太高 | lr 减半（§3） |
| loss 完全不动 | ❌ 数据或标注有问题 | 可视化抽查几个样本 |
| loss 下降但 `acc` 一直 100% | ❌ 标注是空的 | 数据路径写错 |
| 每个 iter 好几秒 | ⚠️ GPU 没吃满 | 见下 |
| 显存占用几乎为 0 | ❌ 在用 CPU 训 | 检查 `--device` / `cuda.is_available()` |

## 四种崩法的处理顺序

**① OOM（爆显存）**
```text
batch 减半（并按规则改 lr）→ 开混合精度 fp16 → 开梯度检查点 with_cp
→ 最后才是换更小的 backbone
```

**② nan**
```text
lr 减半 → 延长 warmup → 加梯度裁剪 grad_clip → 查数据里有没有非法框（宽或高为 0）
```

**③ 太慢**
```bash
nvidia-smi -l 1     # 看 GPU 利用率
```
- 利用率长期 < 50% → **瓶颈在数据加载**，不在 GPU。调大 `workers_per_gpu`；**把数据从机械盘/网盘挪到 SSD**（这一条经常直接快好几倍）。
- 利用率一直很高但还是慢 → 就是模型大，正常，接受它。

**④ 不收敛**
```text
先确认数据对（可视化）→ 再确认 lr 对 → 再确认 config 里 num_classes 对
→ 最后才怀疑方法本身
```
**顺序不能反。** 新手最常见的错误是一上来就怀疑模型，改了三天模型，最后发现是标注路径写错了。

## 日志去哪看

```bash
ls work_dirs/<你的实验>/          # 里面有 .log 和 .log.json
tail -f work_dirs/<实验>/*.log    # 实时看
# 画曲线：
python tools/analysis_tools/analyze_logs.py plot_curve work_dirs/<实验>/*.log.json --keys loss
```

# 6. 「复现出来了，但数字和论文对不上」

这是 M2–M5 会反复遇到的。**排查顺序固定，按这个来能省你一周。**

## 按这个顺序查，不要跳步

| 顺序 | 查什么 | 为什么排这个位置 |
|---|---|---|
| **1** | **评测协议**：哪个 split？val 还是 test？单尺度还是多尺度？mAP07 还是 mAP12？ | **最常见，且改一下就对上了。**（见《名词逐个讲透》§5.3） |
| **2** | **数据预处理**：切图尺寸和 overlap 一样吗？有没有做定标/归一化？ | 遥感特有，差异极大 |
| **3** | **训练配置**：epoch 数、lr、batch、数据增强 | 论文的 Implementation Details 那一段逐条对 |
| **4** | **随机种子与波动**：跑 3 个 seed 看方差 | **差 0.5 个点以内多半就是噪声，不是 bug** |
| **5** | 环境差异：框架版本、CUDA 版本 | 影响小但存在 |
| **6** | 才轮到怀疑方法实现有 bug | 概率最低 |

## 什么叫"复现成功"

**不是"和论文一模一样"。** 学术界的实际标准：

- 差距在 **±1 个点以内** → 复现成功，正常写进报告
- 差距 **1–3 个点** → 可接受，但报告里要写清你的协议和论文的差异
- 差距 **> 3 个点** → 有实质问题，按上表从第 1 条重查

> **一条必须现在就养成的纪律**：**任何数字都必须连同"评测协议"一起记录。** 只写 "mAP 73.2" 是没有意义的，要写 "mAP 73.2（DOTA-v1.0 val，单尺度 1024/200 切图，VOC07 metric，单卡 batch2，12 epoch）"。
>
> 你 M5 做主实验大表、M6 写论文时，这条纪律的价值会体现出来——**没记协议的实验等于没做，因为你没法解释表里的数字**。

# 7. 把这 6 招用在剩下的 300 处

**从现在起，每翻开新的一天，先扫一眼有没有这 6 种写法：**

```text
看到「下下来」        → 打开 §1，三步法，先下小 split

数字对不上            → 打开 §6，按顺序查，别跳步
```

**每补完一处，花 2 分钟记进 `20-代码实验/自救记录.md`**：

```markdown
## <周次-天-时段> · <原文哪句话没写清>
- 我用了第几招：
- 实际做的动作 / 命令：
- 花了多久：
- 结论（下次直接抄）：
```

**半年后这份记录会比这套手册本身更值钱**——因为它是按你的机器、你的网络、你的踩坑史长出来的。

> **最后一句实话**：这套手册的问题不是作者不懂，是他默认你已经会那些"不用说的常识"。而这些常识恰恰是转行的人最缺的。**这 6 招就是那些没被说出口的常识。** 学会之后，你不但能补这套手册，还能读懂任何一个没写好 README 的开源项目——那是一项比会跑 baseline 值钱得多的能力。
