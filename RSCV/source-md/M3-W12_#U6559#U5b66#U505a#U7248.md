# D78 周一 · 设计 5 个消融配置 + 启动

> **预期管理**:今天设计并启动第一波消融。**核心纪律:每个消融只改一个变量**——这是消融能"归因"的命门。今天产出消融设计文档 + 启动前两个(A1/A2),后面几天陆续跑完读完。

## 上午段 · 设计 5 个消融配置

**① 先垫概念(消融是什么、为什么每次只改一个变量)**
- **消融实验(ablation)**= 每次**只去掉/替换你方法的一个部分**,看性能变化,从而证明"这个部分有没有用、有多大用"。**核心原则:每个消融只改一个变量**(控制变量)——这样性能变化才能干净地归因到那一个改动。
- **和通用 CV 一样、但对你更关键**:消融是所有方法类论文的标配证据。审稿人会问"你这几个组件,哪个真有用?会不会去掉两个性能也一样?"——消融表就是回答。**对你尤其重要**:你的卖点之一是"单卡高效",消融能证明"我没堆无用组件",每个组件都名副其实。
- **常见 5 个**:A1 去掉你的核心组件 / A2 把某组件换成简单版 / A3 换 loss / A4 换 backbone / A5 换数据增强策略。**命名要清晰**(`A1_wo_hrbranch`、`A2_simple_fuse`),日志完整。

**② 手把手带做**:在 `docs/消融设计.md` 列出 5 个消融配置,每个写清"改了哪一个变量、预期说明什么";为每个建一个 config(**基于 v1 的 config 只改一处**)。建 config 的正确姿势:
```yaml
# configs/abl_wo_hrbranch.yaml —— A1：只把"用不用高分辨率分支"这一行关掉
# 继承 v1 配置，只覆盖一个字段（其余全相同，保证可归因）
_base_: your_method.yaml
model:
  use_hr_branch: false        # ← 唯一改动：去掉核心组件
# 其余 lr/epochs/seed/data/aug 全部继承，不动
```
**③ 这一步合格的样子**:5 个消融配置定义清晰,每个只改一个变量,命名规范,且能 `diff` 出"相对 v1 只差一处"。
**④ 最常踩的坑**:① 一个消融改了多处 → 无法归因(性能变了不知是哪个改动的功劳);② 消融和你的 contribution 对不上(每个核心组件都该有一个对应消融,否则审稿人会问"这个 contribution 凭什么")。
**⑤ 卡住怎么自救(决策树)**:不知设哪些? → **你方法的每个创新组件配一个"去掉它"的消融**(对应一条 contribution),再加 backbone/loss/增强各一个凑够 5 个;config 不会继承? → 用框架的 `_base_` 继承机制,只写要覆盖的字段。
**⑥ 今天(这一步)你同时学会了什么**:你学会**设计控制变量的消融实验**。**做了**(消融设计文档 + 5 个 config)、**学了**(消融定义、每次只改一个变量、消融对应 contribution)、**会了**(为方法的每个组件设计可归因的对应消融)。

> **技能卡｜消融设计原则**:每个消融**只改一个变量**(用 config 继承 `_base_` 只覆盖一个字段)。每个核心组件配一个"去掉它"的消融,对应一条 contribution;再加 backbone/loss/增强维度。命名规范(`A1_wo_X`),`diff` 可见"只差一处"。改多处=无法归因。

# D79 周二 · A1/A2 分析(组件到底有没有用)

> **预期管理**:今天读 A1/A2 的结果——这是消融最核心的技能:**从"去掉后掉多少"判断一个组件的价值**。同时启动 A3。重点提醒:判断"有没有用"要和 std 比,别被单次波动骗了。

## 上午段 · A1 结果分析(并判断显著性)

**① 先垫概念(怎么从消融判断组件价值 + 显著性)**:A1 训完,看"去掉核心组件后性能下降多少"。**下降越多 → 组件越有用**;几乎不降 → 组件可有可无(考虑删)。**关键:下降是否"显著"**——要和 baseline 的 std 比,降幅 > std 才算真有贡献,否则可能只是噪声。
**② 手把手带做**:评估 A1,和完整方法(v1)对比;算"去掉组件的性能损失";**和 std 比判断显著性**;写一句结论(组件贡献多大、是否显著)。
```python
# 判断消融差异是否显著（降幅 vs 噪声）
def is_significant(full_mean, abl_mean, std, k=1.0):
    delta = full_mean - abl_mean
    sig = abs(delta) > k * std            # 降幅超过 std 才算显著
    print(f"Δ={delta:+.2f} (std={std:.2f}) → {'显著' if sig else '在噪声内'}")
    return sig
# 例：完整 76.3，A1 去组件后 74.5，std 0.4 → Δ=-1.8 远超 std → 组件显著有用
is_significant(76.3, 74.5, 0.4)
```
**③ 合格样例**:A1 vs v1 的差值 + 显著性判断 + 结论(组件有用/没用,显著/不显著)。
**④ 坑**:下降一点点(在 std 内)就认定"有用" → 要看是否超过 std(显著性);单 seed 不可靠,关键消融跑多 seed。
**⑤ 自救**:去掉组件反而更好 → 那它可能有害,**大胆考虑删**(论文要"每个组件都有用",留着有害组件反而扣分);降幅在 std 内 → 补多 seed 确认,或归到"贡献有限"。
**⑥ 今天(这一步)你同时学会了什么**:你学会**从消融判断一个组件的价值并验证显著性**。**做了**(A1 分析 + 显著性判断)、**学了**(去组件→看损失→比 std→判价值)、**会了**(用消融量化组件贡献并判断是否显著)。

> **技能卡｜消融解读**:看"去掉/替换后相对完整方法的变化 Δ",**Δ 要和 std 比**(超过才显著)。降得多=组件有用;几乎不降=可删;反而更好=有害,大胆删。论文要"每个组件都有用",没用的简化掉反而加分。关键消融跑多 seed。

# D80 周三 · A3 分析 + A4/A5 启动 + 消融可视化

> **预期管理**:今天读 A3、启动最后两个消融(A4/A5),并把已出结果画成柱状图。柱状图能让你和读者"一眼看出哪个组件贡献最大"——比纯表格直观得多。

## 上午段 · A3 结果分析(选 loss)

**① 先垫概念(为什么 loss 这一维值得单独消融)**:A3 训完,看"你的 loss vs 标准 loss"——若你的 loss 显著更好,说明它适配这个任务(可写成一条小贡献);若没差别,用标准 loss 更省事。**为什么旋转检测的 loss 特别值得试**:通用水平框检测用 IoU/L1 loss 就够;但旋转框多了"角度"这一维,角度的周期性(0° 和 180° 接近)会让朴素 L1 loss 在边界处梯度异常,所以学界专门设计了旋转 IoU loss、高斯建模 loss(GWD/KLD)等——你的方法用哪种、是否更适合你的场景,正是这个消融要回答的。
**② 手把手带做**:评估 A3,和完整方法对比,判断显著性,写结论(哪个 loss 更适合)。
**③ 合格样例**:A3 vs v1 差值 + 显著性 + 结论(确定用哪个 loss)。
**④ 坑**:loss 差异在 std 内却硬说"我的 loss 更好" → 不显著就如实写"持平,选其一即可"。
**⑤ 自救**:你的 loss 没更好 → 没关系,换回标准 loss,把创新点集中在真正有效的组件上(不是每个设计都得是创新)。
**⑥ 今天(这一步)你同时学会了什么**:你确定了更优的 loss 选择。**做了**(A3 分析)、**学了**(loss 对结果的影响、不显著就诚实)、**会了**(用消融选 loss)。

# ===== ① 消融批量运行：遍历配置（每个只改一处），收集结果 =====
ablation_cfgs = {
    "full":        "configs/your_method.yaml",
    "A1_wo_hr":    "configs/abl_wo_hrbranch.yaml",
    "A2_simple":   "configs/abl_simple_fuse.yaml",

def run_ablations(train_eval_fn):
    results = {}
    for name, cfg in ablation_cfgs.items():
        metric = train_eval_fn(cfg, seed=0)        # 调你的 train/eval，返回指标
        results[name] = metric
        print(f"{name:<12} {metric:.2f}")
    return results

# ===== ② 网格搜索（系统搜超参，非随意试）=====
import itertools
def grid_search(train_eval_fn, base_cfg):
    grid = {"lr": [1e-3, 5e-4, 1e-4], "epochs": [12, 24, 36]}
    table = []
    for lr, ep in itertools.product(grid["lr"], grid["epochs"]):
        m = train_eval_fn(base_cfg, lr=lr, epochs=ep, seed=0)
        table.append((lr, ep, m)); print(f"lr={lr} ep={ep} -> {m:.2f}")
    best = max(table, key=lambda r: r[2])
    print(f"最优: lr={best[0]} ep={best[1]} -> {best[2]:.2f}")
    return table, best

| 网格搜索跑不完 | 网格太大/单卡时间不够 | 短 epoch/小数据初筛 → top 跑足;或只搜最关键维 |
| 超参乱试、无法复现最优 | 没系统搜索/没记录 | 网格搜索 + 超参-性能表;固定 seed |
| 信号弱就想换课题 | 误判 v1、忽略消融 | v1 提升小正常,看消融有效性+改进方向再定 go/no-go |
| A4 换 backbone 接口报错 | 通道数变了没适配 | 在你的模块入口适配通道(也是迁移性的检验) |

## 六、把消融"写进论文"——Experiment 段落范例
> 会跑消融还要会"写"消融。给你一段可套用的论文式写法(英文骨架 + 中文注释),让消融表配上有说服力的文字。

```markdown
**Ablation Study.** （先点题：这一段证明每个组件都有用）
To validate the contribution of each component, we conduct ablation studies
on DOTA-v1.0 (Table 2), averaging over 3 random seeds.
（逐条解读，挂数字）
Removing the high-resolution branch (A1) drops mAP by 1.8 points, the largest
degradation, confirming it as the core of our gains, especially on dense small
objects. Replacing our attentive fusion with simple addition (A2) yields a
negligible change (-0.3, within std), indicating the gain comes from the
branch rather than the fusion complexity; we therefore adopt the simpler
fusion for efficiency. Our method also improves a stronger Swin-T backbone
(A4, +0.9), showing it is backbone-agnostic. Removing remote-sensing-specific
augmentation (A5) costs 1.2 points, verifying its necessity.
（收尾：呼应卖点）
These results show each retained component is justified, and the simplified
design further supports our single-GPU efficiency goal.
```
**写法要点**:① 开头一句点明"证明每个组件都有用";② 每条消融"动作 + 数字 + 结论"三件套;③ 不显著的诚实写"within std"并据此简化;④ 结尾呼应你的核心卖点(高效)。这套写法 M4 写论文 Experiment 章直接能用。

## 八、进阶：按"类别"读消融（找出方法对哪些遥感目标有效）
> 总 mAP 只是一个数。把消融的提升拆到**每个类别**，才知道你的方法到底帮了谁、伤了谁——这是定性负面案例的来源，也是 M4 改进的精确制导。

```python
# 按类别对比 完整方法 vs A1(去核心组件)，看高分辨率分支帮了哪些类
def per_class_delta(full_ap, abl_ap, classes):
    """full_ap/abl_ap: {类名: AP}；输出每类的提升，降序"""
    deltas = sorted(((c, full_ap[c] - abl_ap[c]) for c in classes),
                    key=lambda x: -x[1])
    for c, d in deltas:
        print(f"{c:<16} Δ={d:+.1f}")
    return deltas

# 示例输出（DOTA 部分类别）：
#   small-vehicle    Δ=+4.2   ← 小目标，提升最大（符合高分辨率分支的动机）
#   ship             Δ=+3.8   ← 密集小目标，受益大
#   storage-tank     Δ=+1.1
#   harbor           Δ=+0.3
#   ground-track     Δ=-0.2   ← 大目标，几乎不受影响（甚至略降）
#   plane            Δ=-0.5   ← 大目标，反而略降 → 负面案例从这类里找
```
**怎么用这张按类表**:① **验证动机**——高分辨率分支应在小目标类(small-vehicle/ship)提升最大,结果吻合就坐实了"机制如预期";② **找负面案例**——掉点的大目标类(plane)就是 D81 定性负面案例的来源;③ **指导 M4**——若发现"小目标涨、大目标略降",M4 可考虑"只在小目标尺度启用该分支",把副作用消掉。**一句话**:总 mAP 告诉你"行不行",按类 mAP 告诉你"为什么、接下来改哪里"。

> **技能卡｜按类别读结果**:别只看总 mAP,把提升拆到每个类(`per_class_delta`)。① 提升最大的类应吻合你的方法动机(验证机制);② 掉点的类=定性负面案例来源 + M4 精确改进目标。遥感类别尺度悬殊,按类分析尤其能暴露"方法只帮了某尺度"这类规律。
